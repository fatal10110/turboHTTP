# HTTP/2: review findings

Scope: connection, read loop, send path, streams, flow control, HPACK, connection manager. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (28 findings, 24 files read in full). The HTTP/2 slice is dense but carefully commented (ownership notes, RFC and issue references), maps most failures to UHttpException and shares request-field validation with HTTP/1.1. Through this lens the main risks are: (1) HTTP/2 is hard-wired into RawSocketTransport with no define or asmdef seam, so 23 files / 8,358 lines / 47 types / 52 async state machines ship in every player although Unity players cannot negotiate h2 without the opt-in BouncyCastle provider; (2) the option surface promises things the wire does not deliver (MaxFrameSize and MaxConcurrentStreams are never sent as configured, EnablePush defaults to true with no push support, header-size limits overlap); (3) request/response head handling has diverged from the HTTP/1.1 path (content-length ownership, caller Host, response-trailer filtering, field-name validation, 1xx cap); (4) Http2Connection is a 3,650-line class over six partials split by file rather than responsibility, and helper contracts hide real defects (cancellation swallowed in SendFrameWithPooledPayloadAsync loses stream WINDOW_UPDATEs, Http2ConnectionManager.Dispose races an in-flight connection init, a stall abort surfaces as ObjectDisposedException). Roughly 350 lines are dead or test-only code in the shipping assembly.

Not read in full: Runtime/Transport/RawSocketTransport.cs (read lines 1-1180, 1400-1470, 2395-2434: constructors, registration, DispatchAsync/DispatchCoreAsync/DispatchAttemptAsync, MapDispatchAttemptFailure, the proxy and HTTP/2 dispatch paths, Dispose; the HTTP/1.1 lease/Expect/CONNECT internals in between were only grepped)

**RFC conformance, protocol implementation, security** (19 findings, 24 files read in full). The HTTP/2 stack is largely conformant and carefully hardened: frame-size and per-type validation, idle/closed stream classification, CONTINUATION and header-list bounds, always-decode HPACK, flow-control accounting in both directions (padding, discarded DATA, negative windows), MAX_CONCURRENT_STREAMS queueing, GOAWAY drain and bounded replay all trace correctly. The main risk is a single wrong entry in the HPACK Huffman table (symbol 0x7B '{' is coded as 19 bits 0x7fffe instead of 15 bits 0x7ffe): any Huffman-coded response header containing '{' (report-to / nel JSON headers of common CDNs) tears the connection down with COMPRESSION_ERROR, and outgoing header values containing '{' are corrupted on the wire; the round-trip test passes because the table is self-consistent. Secondary risks: connections that fail in the read loop or on a write are never closed (RFC 9113 5.4.1), the HPACK encoder table grows to whatever SETTINGS_HEADER_TABLE_SIZE the peer sends, and the response pseudo-header rules of RFC 9113 8.3 (ordering, duplicates) are not enforced. The remaining findings are low-severity leniencies, option/wire mismatches (MAX_FRAME_SIZE never advertised, ENABLE_PUSH=1 by default) and edge cases in the upload/half-close path.

Not read in full: Runtime/Transport/RawSocketTransport.cs (2434 lines): read only the HTTP/2 dispatch path in full (lines 120-320, 380-560, 551-850, 838-1045: capability probe, retry policy, DispatchOnH2ConnectionAsync, DispatchAttemptAsync, MapDispatchAttemptFailure, DispatchViaProxyAsync H2 branch); the HTTP/1.1, proxy HTTP/1.1, TLS and pool paths were not read

**performance, resource management, concurrency, platform compatibility** (30 findings, 24 files read in full). The HTTP/2 slice is carefully built in most places: stream leases guard pooled-stream reuse against the read loop, started frames are finished with the connection token only, send-window and admission wake-ups are free of lost wake-ups, and every peer-controlled size on the receive side is bounded. The main correctness risk is the response-start hand-off: the handler work item touches the stream after dropping its reference, Fail/Cancel can race TryStartResponse, and an upload failure after the response started leaves the body source orphaned, so a pooled Http2Stream can be poisoned for an unrelated request and readers can hang. The main performance risks are a cold-start connection storm (every request of a burst dials its own TCP+TLS before the HTTP/2 connection is published), a default 64 KB stream window with one awaited WINDOW_UPDATE per consumed DATA frame (worse on real networks than the loopback numbers in #406 show), uncoalesced frame writes (two TLS records per frame) and an extra round trip for the SETTINGS ACK. Resource management is weak at the connection level: a connection whose read loop failed is never disposed until the same origin is requested again, there is no idle timeout or default reuse probe for HTTP/2 (unlike the 45 s rule for HTTP/1.1 on mobile), and the manager can publish a connection after its own Dispose. The read loop also awaits the write lock for control frames, which can deadlock with a back-pressuring peer until the 60 s stall timer kills the connection.

Not read in full: Runtime/Transport/RawSocketTransport.cs (2434 lines): only the HTTP/2 dispatch path was read (lines 140-310, 395-780, 840-1050, 1110-1170, 2395-2434); the HTTP/1.1, proxy-auth and response-parsing parts were not read

## Critical (1)

### http2-protocol-01: HPACK Huffman table codes '{' (0x7B) as 0x7fffe/19 bits instead of RFC 7541 Appendix B 0x7ffe/15 bits, breaking decode of conformant peers and corrupting encoded output

**critical** · rfc-compat · verdict **C** · `Runtime/Transport/Http2/HpackHuffman.cs:138` · RFC 7541 Appendix B, Section 5.2 · issue #456

- **Evidence.** HpackHuffman.cs:138 has `(0x7fffe, 19), // (123) '{'`; RFC 7541 Appendix B gives '{' (123) = 7ffe [15]. Verified numerically from the file: the Kraft sum of the 257 code lengths is 524273/524288 (not 1, so the code is incomplete) and becomes exactly 1 with 15 bits; the 19-bit code 1111111111111111110 is a prefix of the 23-bit codes of symbols 147,149,150,151,152,155,157,158,165,166,168,174,175,180,182,183 (0x7fffe0-0x7fffef). Decode side: InsertIntoTree (HpackHuffman.cs:302-320) marks an interior node as leaf 123, and no code has the RFC prefix `14 ones + 0`, so Decode hits `next == null` (HpackHuffman.cs:405-406) and throws HpackDecodingException; ReadLoopAsync maps that to GOAWAY(COMPRESSION_ERROR) + FailAllStreams (Http2Connection.ReadLoop.cs:94-106). The comment at HpackHuffman.cs:403 ('The HPACK code is complete, so this is unreachable') is false for this table. Encode side: EncodeCore (HpackHuffman.cs:347-374) emits the 19-bit code whenever HpackEncoder.EncodeString picks Huffman (HpackEncoder.cs:187-199). Present since the first implementation (git 87dcfe1). Tests: HpackHuffmanTests.RoundTrip_PrintableAsciiValues (Tests/Runtime/Transport/Http2/HpackHuffmanTests.cs:34) round-trips 32..126 through the same wrong table so it passes; the RFC vectors used contain no '{'; no test decodes bytes >= 0x80.
- **Failure scenario.** A server Huffman-encodes any response field containing '{' per the RFC (e.g. Cloudflare/Google `report-to: {"endpoints":[...` or `nel: {"report_to":...`, JSON in set-cookie or custom headers): the client throws on the 15-bit code, sends GOAWAY(COMPRESSION_ERROR) and fails every stream on the connection; an idempotent request is replayed once on a fresh connection and fails the same way, so the origin is unreachable over HTTP/2. Conversely a request header value such as `x-meta: {abcdefghijklmnop}` (Huffman shorter than raw) is sent with an 18-ones+0 code; a conformant server decodes a byte from the 0x93..0xB7 group plus misaligned garbage (corrupted value) or answers COMPRESSION_ERROR. Response values containing the 16 listed high bytes (UTF-8 continuation bytes) are also mis-decoded as '{' plus garbage.
- **Fix direction.** Change entry 123 to (0x7ffe, 15). Add a table self-check test (Kraft sum == 1, prefix-free) and decode/encode vectors produced by an independent implementation covering all 256 symbols, not a self round-trip.
- **Verifier.** Re-derived from the file, not the reviewer's text. HpackHuffman.cs:138 is `(0x7fffe, 19), // (123) '{'`; RFC 7541 Appendix B gives 7ffe [15]. A script over the 256 table entries plus EOS (0x3fffffff/30) gives a Kraft sum of 524273/524288 (an RFC-complete code sums to 1; the deficit 15/2^19 is exactly 2^-15 - 2^-19, i.e. one 15-bit code written as 19 bits), and the 19-bit code is a prefix of the 23-bit codes of symbols 147,149,150,151,152,155,157,158,165,166,168,174,175,180,182,183. No table entry starts with or is a prefix of the RFC code 111111111111110, so Decode walks to a null child and throws (HpackHuffman.cs:405-406; the 'code is complete, unreachable' comment at 403 is false). HpackDecoder.cs:293-295 calls it for every Huffman string; ReadLoop.cs:94-106 turns the exception into GOAWAY(COMPRESSION_ERROR)+FailAllStreams. Encode side: HpackEncoder.cs:187-199 uses Huffman whenever shorter and EncodeCore (HpackHuffman.cs:347-374) emits the wrong 19-bit code. No refuting test: HpackHuffmanTests.cs:34-41 round-trips 32..126 through the same table, the RFC C.4 vectors contain no '{', nothing decodes independent vectors; the fuzz seeds are the same C.3/C.4 vectors. Any conformant peer that Huffman-codes a field containing '{' (report-to / nel JSON values are the common case) kills the connection, and the idempotent replay fails the same way.

## High (3)

### http2-runtime-01: The response-start work item signals completion on an Http2Stream after dropping its lifetime reference, and Initialize never resets the completion source, so a late signal poisons the pooled stream for the next request.

**high** · concurrency · verdict **C** · `Runtime/Transport/Http2/Http2Stream.cs:661` · issue #731

- **Evidence.** InvokeResponseStartAsync releases its reference as soon as the handler task is pending (Http2Stream.cs:657-663, 'kept alive by the dispatch and the body source') and touches the stream after the await: TrySetResult (667) or _handlerFaulted/AbortRequestBody/bodySource.Abort()/TrySetException (671-681). The dispatch reference is not guaranteed: DispatchAsync leaves through its finally (Http2Connection.cs:513-525) without awaiting CompletionTask whenever the upload phase throws after the response started (SendDataAsync at Http2Connection.cs:445: OCE from _writeLock.WaitAsync(ct) at Send.cs:189 or WaitForSendWindowAsync at Send.cs:519, or a request-body source error). bodySource.Abort() runs CleanupAsync synchronously and its finally releases the body-source reference (Http2ResponseBodySource.cs:461-464); the count reaches 0, ReleaseLifetime returns the stream to the static LIFO pool (Http2Stream.cs:805-813) and PrepareForPool zeroes _completionSignaled and resets the source (238-243). The TrySetException that follows then wins the Exchange (791) and completes the freshly reset source. Initialize (168-209) resets _completionSignaled but never calls _completionSource.Reset(), so the next Rent returns a stream whose CompletionTask is already completed. No test covers a dispatch that leaves through the upload path while the handler is still pending (the RequestTimeout tests use a streaming handler that has already completed).
- **Failure scenario.** Buffered POST; the server sends response HEADERS before the upload ends, the upload is blocked on flow control, the request deadline fires. The cancel callback faults the body; the uploader throws OCE and DispatchAsync releases its reference; on another pool thread the handler's body read fails, the catch in InvokeResponseStartAsync calls bodySource.Abort() (count 0, stream pooled) and then TrySetException(HandlerCallbackException). The next HTTP/2 request in the process rents that object, sends HEADERS, and 'await stream.CompletionTask' (Http2Connection.cs:584) throws the previous request's exception immediately (or returns success with no response when the stale signal was TrySetResult); its stream leaves the active map without RST_STREAM. If the object was already re-rented, the late AbortRequestBody/TrySetException hit the live request directly.
- **Fix direction.** Hold the work item's reference until InvokeResponseStartAsync has signaled completion (release only in finally, and signal before aborting the body source). Reset the completion source in Initialize and tie late signals to a rental generation so a stale work item can never complete another rental.
- **Verifier.** Traced end to end. References: Initialize sets 1 (dispatch), TryStartResponse adds body-source and work-item refs (Http2Stream.cs:272, 286). InvokeResponseStartAsync drops the work-item ref when the handler is pending (657-663) and afterwards calls TrySetResult (667) or, in the catch, bodySource.Abort() then TrySetException (671-681). DispatchAsync releases its ref in finally without awaiting CompletionTask when the upload phase throws after the response started (Http2Connection.cs:445 -> 513-525; e.g. OCE from Send.cs:189/519 on the deadline, or a request-body error). Then the body-source ref is the last one: Abort -> BeginCleanup -> CleanupAsync runs synchronously (AbortStreamFromBodySourceAsync returns at once because the stream was already removed) and its finally calls ReleaseBodySourceLifetime (Http2ResponseBodySource.cs:461-464) -> count 0 -> Http2StreamPool.Return -> PrepareForPool zeroes _completionSignaled and resets the source (Http2Stream.cs:238-243). The following TrySetException/TrySetResult wins the Exchange (773/791) and completes the reset source of a pooled object; neither checks _disposed. Initialize (168-209) resets _completionSignaled but never _completionSource, so the next Rent from the static LIFO pool gets an already-completed CompletionTask: `await stream.CompletionTask` (Http2Connection.cs:584) returns/throws immediately for an unrelated request, which then leaves the active map without RST_STREAM (finally at 520-521). The same happens through HandlerCallbackSafetyWrapper, which aborts the body (TryAbort) before the pending callback completes. The ordering is a race between two thread-pool continuations after the deadline (uploader wake vs body-reader fault; both sources run continuations asynchronously, SingleReaderChannel.cs:288), and is deterministic when the handler is not parked in a body read. No test covers a dispatch leaving through the upload while the handler is pending.

### http2-runtime-05: Every request of a cold burst dials its own TCP+TLS connection before the HTTP/2 connection is published, and a request whose redundant dial fails is failed although a working HTTP/2 connection exists.

**high** · performance · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:604` · RFC 9113 Section 9.1 · issue #736 · also reported as http2-design-18, net-runtime-05

- **Evidence.** DispatchAttemptAsync checks the manager once (RawSocketTransport.cs:586), then calls _pool.GetConnectionAsync (604). The pool only bounds concurrency with the per-host semaphore and dials when no idle HTTP/1.1 connection exists (TcpConnectionPool.cs:455-530); h2 connections never enter the idle pool and the manager is not re-checked after the permit is granted. Only after the full handshake does GetOrCreateAsync find the published connection and dispose the fresh TLS stream (Http2ConnectionManager.cs:236-241, 313-319). The per-key init lock only deduplicates the HTTP/2 preface, not the dial, despite the class comment ('thundering herd prevention', Http2ConnectionManager.cs:14). If the dial throws, FallBackAfterFailedExtraDial returns null because there is no extra-dial claim (RawSocketTransport.cs:607-611, 1034-1038) and the request fails. No test asserts the number of dials for a cold burst.
- **Failure scenario.** App start: 50 requests to one origin are issued at once. On mobile (8 permits) all 50 perform a TCP+TLS handshake in waves of 8; 49 are thrown away. At 100 ms RTT the last requests wait about 2 s for handshakes they do not need, plus 49 certificate validations of CPU and battery. A server or middlebox that limits connections per client refuses some of the redundant dials and those requests fail with a connect error even though the HTTP/2 connection is up.
- **Fix direction.** Gate the dial per manager key: the first cold request dials, later requests for the same key await that pending attempt (and re-check the manager after it, and again after the per-host permit is granted); fall back to their own dial only when the first attempt did not yield h2. On a dial failure, re-check the manager before failing the request.
- **Verifier.** DispatchAttemptAsync checks the manager once (RawSocketTransport.cs:586) and then calls _pool.GetConnectionAsync (604). TcpConnectionPool.GetConnectionCoreAsync only takes the per-host permit and, with no idle HTTP/1.1 connection, dials (TcpConnectionPool.cs:461-530); rg finds no HTTP/2 awareness in the pool beyond storing the ALPN result, and the manager is not consulted after the permit is granted. lease.TransferOwnership releases the permit at once (TcpConnectionPool.cs:176-185), so each waiter of a cold burst is admitted, completes a full TCP+TLS handshake, and only then GetOrCreateAsync/GetOrCreateSlowAsync finds the published connection and disposes the fresh stream (Http2ConnectionManager.cs:236-241, 313-319). The init lock deduplicates the preface, not the dial; the extra-dial claim (_extraDials) only covers the saturated-origin case. A failed redundant dial fails the request: FallBackAfterFailedExtraDial returns null when there is no claim (RawSocketTransport.cs:607-611, 1034-1038) and nothing re-checks the manager. The only burst tests are for the saturated extra connection (IdleProbeAndExtraConnections.cs:115, 183). N-1 wasted handshakes for N concurrent first requests to an origin, serialized in waves of MaxConnectionsPerHost; latency, CPU (BouncyCastle on mobile) and server connection-rate limits are all affected.

### http2-runtime-06: The default 65535-byte stream receive window, credited only as the consumer reads, caps each HTTP/2 download at about 64 KB per round trip (#406 measures loopback and understates it).

**high** · performance · verdict **C** · `Runtime/Core/Http2Options.cs:13` · RFC 9113 Section 5.2 · issue #406

- **Evidence.** Http2Options._initialWindowSize = 65535 (Http2Options.cs:13) is advertised (Http2Settings.cs:108) and used as each stream's receive window (Http2Connection.cs:363). Credit returns only when a whole chunk has been consumed (Http2ResponseBodySource.cs:402-414 -> Lifecycle.cs:304-307); there is no window auto-tuning and no initial connection-level WINDOW_UPDATE (the connection window grows to the 1 MiB target only after the first DATA frame, Lifecycle.cs:353-389). So bytes in flight plus buffered per stream never exceed 65535.
- **Failure scenario.** Asset download over a link with 80 ms RTT: throughput is bounded by 65535 / 0.08 s, about 0.8 MB/s per stream, regardless of bandwidth; the same download over HTTP/1.1 uses the full TCP window. On loopback (RTT near 0) the cap barely shows, which is why the 3x gap in #406 is the small end of the effect.
- **Fix direction.** Raise the default stream window (1-4 MiB is common for clients, bounded by DefaultHttp2PerStreamReceiveBufferBytes and MaxConnectionBufferedBytes) and send a connection WINDOW_UPDATE right after the preface; consider RTT-based window growth later.
- **Verifier.** Tracked by #406, which lists the 64 KiB window as an unconfirmed suspect and measures loopback only (P3). Code confirms the suspect: Http2Options.cs:13 defaults InitialWindowSize to 65535, it is advertised (Http2Settings.cs:108) and used as every stream's receive window (Http2Connection.cs:363); credit is returned only per fully consumed chunk (Http2ResponseBodySource.cs:402-414 -> Lifecycle.cs:304-307); no auto-tuning, and the connection window starts at 65535 (Http2Connection.cs:67) and is raised to its target only by the first scheduled update after DATA was consumed. Bytes in flight per stream can therefore never exceed 65535, so throughput is bounded by 65535/RTT (about 0.8 MB/s at 80 ms) independent of bandwidth. That is arithmetic from the flow-control rules, not a measurement, and it is much larger than the loopback 3x in the issue, so the issue understates the WAN effect; worth adding to #406 rather than a new issue.

## Medium (17)

### http2-design-04: Http2Options.MaxFrameSize and MaxConcurrentStreams are documented as advertised settings but are never sent as configured

**medium** · code-smell · verdict **C** · `Runtime/Transport/Http2/Http2Settings.cs:102` · RFC 9113 Sections 4.2, 6.5.2 · issue #727 · also reported as http2-protocol-07, http2-runtime-27

- **Evidence.** Http2Settings.SerializeClientSettings (Http2Settings.cs:102-125) writes exactly four settings: ENABLE_PUSH, MAX_CONCURRENT_STREAMS hard-coded to 100 (line 107), INITIAL_WINDOW_SIZE and MAX_HEADER_LIST_SIZE. SETTINGS_MAX_FRAME_SIZE is never serialised, and the MaxConcurrentStreams property copied from the options (line 33) is never read. Http2Options documents both as 'Advertised ... in the initial SETTINGS frame' (Runtime/Core/Http2Options.cs:41-53, 86-99). The local MaxFrameSize is still used: as the inbound frame bound (Http2Connection.ReadLoop.cs:39), in the per-stream buffer size (Http2Connection.cs:182-186) and in HeaderBlockByteLimit (ReadLoop.cs:566-567). Tests/Runtime/Transport/Http2/Http2SettingsTests.cs:17-41 asserts a 24-byte, four-setting payload, i.e. it pins the missing MAX_FRAME_SIZE; no test sets Http2Options.MaxFrameSize or MaxConcurrentStreams. Documentation~/Modules/Transport.md:63 shows 'options.Http2.MaxConcurrentStreams = 50' as the HTTP/2 tuning example.
- **Failure scenario.** A user sets Http2.MaxFrameSize = 1 MiB to raise download throughput (#406): the server is never told, keeps sending 16,384-byte frames, and the only effects are a larger per-stream buffer budget and a client that now accepts frames up to 1 MiB that the peer was never allowed to send (RFC 9113 Section 4.2 requires FRAME_SIZE_ERROR above the advertised size). A user who follows the docs and sets MaxConcurrentStreams = 50 (or 0) changes nothing on the wire: 100 is always advertised.
- **Fix direction.** Serialise MAX_FRAME_SIZE when it differs from 16,384 and MAX_CONCURRENT_STREAMS from the option, or remove both options. Keep the inbound bound at 16,384 until the peer has acknowledged the larger value. Replace the docs example, and make the settings test assert the configured values.
- **Verifier.** Traced. SerializeClientSettings writes four settings with MAX_CONCURRENT_STREAMS hard-coded to 100 and no MAX_FRAME_SIZE (Http2Settings.cs:102-125); the MaxConcurrentStreams copied from options (Http2Settings.cs:33) is never read on the local side (all readers use _remoteSettings: Admission.cs:72, Http2Connection.cs:351). The local MaxFrameSize is still used as the inbound frame bound (ReadLoop.cs:39), in the per-stream buffer size (Http2Connection.cs:182-186) and HeaderBlockByteLimit (ReadLoop.cs:566-567), so raising it only loosens what the client accepts. Http2Options documents both as 'Advertised ... in the initial SETTINGS frame' (Http2Options.cs:41-53, 86-99) and Documentation~/Modules/Transport.md:63 uses MaxConcurrentStreams = 50 as the tuning example. Http2SettingsTests.cs:17-41 pins the 24-byte, four-setting payload; no test sets either option. For a client that rejects push, the MAX_CONCURRENT_STREAMS part is cosmetic; the MAX_FRAME_SIZE part makes a public option a no-op on the wire. #406 (download throughput) does not track it.

### http2-design-09: Request content-length is transport-owned on HTTP/1.1 but caller-owned and never generated on HTTP/2

**medium** · code-smell · verdict **C** · `Runtime/Transport/Http2/Http2Connection.cs:379` · RFC 9110 Section 8.6; RFC 9113 Section 8.1.1 · issue #715

- **Evidence.** HTTP/1.1: Http11RequestSerializer skips caller Content-Length/Transfer-Encoding (IsFramingHeader, Http11RequestSerializer.cs:320-326, 509-513) and writes Content-Length from the body's known length (lines 339-348). HTTP/2: the header loop (Http2Connection.cs:379-402) only drops IsHttp2ForbiddenHeader names (Http2Connection.Send.cs:560-568: connection, transfer-encoding, keep-alive, proxy-connection, upgrade, host), so a caller-supplied content-length is forwarded verbatim without being compared with the body, and nothing adds content-length for a buffered or known-length body (no 'content-length' on the request side anywhere in Runtime/Transport/Http2; no Core code sets the request header either). No HTTP/2 test covers request content-length.
- **Failure scenario.** The same UHttpRequest behaves differently depending on ALPN, which the caller does not choose: (a) a request carrying a stale or wrong Content-Length header works on HTTP/1.1 (replaced) but is malformed on HTTP/2 and reset by the server with PROTOCOL_ERROR (RFC 9113 Section 8.1.1); (b) every POST/PUT with a known-length body goes out on HTTP/2 without content-length, against the RFC 9110 Section 8.6 SHOULD, so origins, WAFs or frameworks that require a length answer 411 or treat the upload as unbounded only on the HTTP/2 path.
- **Fix direction.** Build the request head in one place for both protocols: treat content-length as transport-owned on HTTP/2 too (drop the caller's value, emit the body's known length), sharing the body-mode decision the HTTP/1.1 serializer already makes.
- **Verifier.** Traced. HTTP/1.1 skips caller Content-Length/Transfer-Encoding and writes its own from the body mode (Http11RequestSerializer.cs:320-348, 509-513). The HTTP/2 header loop drops only IsHttp2ForbiddenHeader names (Http2Connection.cs:379-402; Send.cs:560-568: connection, transfer-encoding, keep-alive, proxy-connection, upgrade, host), so a caller content-length is lower-cased and forwarded verbatim, and nothing generates one: rg for content-length in Runtime shows no request-side producer in Http2/ or Core (only the response checks in ReadLoop.cs and RedirectInterceptor.cs:205 removing it). SendStreamingDataAsync does know the length (session.ContentLength, Send.cs:262) but only uses it to bound the read. No HTTP/2 test covers a request content-length. Part (a) (stale caller value becomes a malformed request, RFC 9113 Section 8.1.1) is a protocol-dependent behaviour difference; part (b) (missing content-length, RFC 9110 Section 8.6 SHOULD) is legal on HTTP/2 and its interop impact depends on the origin.

### http2-design-15: Http2ConnectionManager.Dispose does not fence an in-flight connection init: the new connection is published into the disposed manager and leaked, and disposing the init semaphores breaks their holders and waiters

**medium** · best-practices · verdict **C** · `Runtime/Transport/Http2/Http2ConnectionManager.cs:465` · issue #718 · also reported as http2-runtime-13

- **Evidence.** GetOrCreateAsync checks _disposed only on entry (Http2ConnectionManager.cs:227, 258). GetOrCreateSlowAsync then awaits initLock.WaitAsync and newConnection.InitializeAsync (lines 307, 333; InitializeAsync waits at least one round trip for the SETTINGS ACK) and calls TryPublish (lines 339, 380-408), which never looks at _disposed. Dispose (lines 465-489) disposes the connections published so far, then disposes every SemaphoreSlim in _initLocks (lines 483-487). When Dispose runs during that await: TryPublish adds the connection to _connections of a disposed manager (published = true), the finally block's initLock.Release() throws ObjectDisposedException (line 355), and the catch at lines 364-373 skips cleanup because published is true. The codebase documents the semaphore hazard itself for _writeLock (Http2Connection.Lifecycle.cs:653-658: 'SemaphoreSlim.Dispose never completes async waiters, and a Release after Dispose throws'). RawSocketTransport.Dispose (RawSocketTransport.cs:2425-2432) does not cancel in-flight requests. The disposed path also throws ObjectDisposedException synchronously from a ValueTask-returning method (lines 227-231).
- **Failure scenario.** UHttpClient/transport is disposed (scene unload, shutdown) while the first request to an h2 origin is still initialising its connection: the request fails with ObjectDisposedException mapped to UHttpErrorType.Unknown, and the initialised Http2Connection (socket, TLS state, read loop, keep-alive and maintenance loops) stays alive unowned until the server closes it; it is never Dispose()d, so its stream is only released by finalisation. A second request queued on the same init lock is never granted and ends only when its own token fires. With Enter Play Mode without domain reload the leaked loops survive into the next session.
- **Fix direction.** Do not dispose the init semaphores (or drain them first); re-check _disposed after InitializeAsync and again after TryPublish and dispose/unpublish the connection when the manager was disposed meanwhile; return a faulted ValueTask (or a UHttpException) instead of throwing synchronously.
- **Verifier.** Traced. GetOrCreateAsync checks _disposed only on entry (Http2ConnectionManager.cs:227, 258). GetOrCreateSlowAsync then awaits initLock.WaitAsync and InitializeAsync (307, 333; at least one RTT, up to the 5 s ACK timeout) and calls TryPublish (339, 380-408), which never reads _disposed, unlike RemoveExactAndRetire (510, 525-527). If Dispose (465-489) runs in that window it clears _connections and disposes the init semaphores; TryPublish then TryAdds into the cleared dictionary, published = true, initLock.Release() in the finally (355) throws ObjectDisposedException on the disposed SemaphoreSlim, and the catch (364-373) skips cleanup because published is true. The transferred TLS stream is not owned by the pool any more (lease.TransferOwnership, RawSocketTransport.cs:625), and neither RawSocketTransport.Dispose (2425-2432) nor UHttpClient.DisposeOwnedComponents (UHttpClient.cs:590-606) cancels in-flight requests, so nothing closes the connection: its read loop and maintenance loop run until the peer closes it, and after that it is never Dispose()d (see http2-runtime-11). Waiters queued on the disposed semaphore are not completed by Dispose and end only at their own token. The synchronous ObjectDisposedException from a ValueTask-returning method (227-231) is real but harmless to the awaiting caller. Narrow window (shutdown during a first request's HTTP/2 init) and a bounded leak, hence medium at most.

Preface and SETTINGS are separate writes too (Http2Connection.cs:232-243). So every frame is at least two TLS records and two sends; a WINDOW_UPDATE/RST_STREAM is a 9-byte and a 4-byte record.

### http2-runtime-09: Each DATA payload is copied from the leased frame buffer into a second pooled buffer, and each frame allocates a lease, a frame object and task objects, with no read buffering.

**medium** · performance · verdict **C** · `Runtime/Transport/Http2/Http2ResponseBodySource.cs:296` · issue #724

- **Evidence.** ReadFrameLeaseAsync reads the 9-byte header and the payload with separate ReadAsync calls on the TLS stream (Http2FrameCodec.cs:117, 136, 260) and allocates an Http2Frame, an Http2FrameReadLease and a Task<Http2FrameReadLease> per frame (151-158). TryEnqueueData then rents another buffer and BlockCopies the payload (Http2ResponseBodySource.cs:296-299) although the read loop already owns an exclusively leased buffer of the right size; the consumer copies a third time into its destination (546-547).
- **Failure scenario.** A 100 MiB download performs 6400 extra 16 KB copies and pool rent/return pairs and at least three small allocations per frame on the read loop, part of the per-frame cost behind #406.
- **Fix direction.** Transfer ownership of the frame's rented payload buffer to the body source (offset/length for padded frames) instead of copying; reuse one Http2Frame/lease per connection (struct or reset); read through a 16-64 KB buffered reader so header and payload usually come from one stream read.
- **Verifier.** Covered by #406 (suspect 'Per-DATA-frame overhead in the read loop or the body queue'). ReadFrameLeaseAsync reads header and payload with separate ReadExactAsync calls on the unbuffered TLS stream (Http2FrameCodec.cs:117, 136, 258-266) and allocates an Http2Frame (class, Http2Frame.cs:74), an Http2FrameReadLease (class, Http2FrameCodec.cs:13) and the Task<Http2FrameReadLease> per frame (114, 151-158). TryEnqueueData rents a second buffer and BlockCopies the payload out of the already exclusively leased frame buffer (Http2ResponseBodySource.cs:296-299); the consumer copies again in TryReadCurrentChunk (546-547). Not a correctness defect; per-frame copy and allocation cost on the download hot path.

### http2-runtime-10: InitializeAsync waits for the server's SETTINGS ACK before the first request may be sent, adding one round trip to every new HTTP/2 connection.

**medium** · performance · verdict **C** · `Runtime/Transport/Http2/Http2Connection.cs:265` · RFC 9113 Section 3.4 · issue #714

- **Evidence.** InitializeAsync writes the preface and SETTINGS, starts the read loop and then awaits _settingsAckSource (Http2Connection.cs:248-267); Http2ConnectionManager.GetOrCreateSlowAsync awaits InitializeAsync before it returns the connection (Http2ConnectionManager.cs:333), and the transport dispatches only afterwards (RawSocketTransport.cs:629-642). The ACK can only arrive one full round trip after the client SETTINGS were sent. RFC 9113 Section 3.4 lets the client send frames immediately after its preface; the defaults for the peer's settings apply until its SETTINGS arrive (the admission and window code already handles later changes).
- **Failure scenario.** On a 150 ms RTT mobile link the first request on each new connection takes TCP + TLS 1.3 + one extra RTT + the request itself: about 600 ms instead of 450 ms; the same cost recurs after every GOAWAY, idle close or network change.
- **Fix direction.** Publish the connection and allow dispatch once preface and SETTINGS are written and the read loop runs; keep the SETTINGS ACK deadline as a background liveness check that fails the connection (and its streams as retryable) when it expires.
- **Verifier.** Traced. Http2Connection.InitializeAsync writes preface + SETTINGS, starts the read loop and awaits _settingsAckSource (Http2Connection.cs:232-266); the source is completed with success only by an inbound SETTINGS frame carrying ACK (Http2Connection.ReadLoop.cs:829-836), not by the server preface. Http2ConnectionManager.GetOrCreateSlowAsync awaits InitializeAsync before TryPublish/return (Http2ConnectionManager.cs:333-351) and RawSocketTransport dispatches only after GetOrCreateAsync returns (RawSocketTransport.cs:629-642). The ACK needs the server to have read the client SETTINGS, so HEADERS leave one RTT later than RFC 9113 Section 3.4 allows. No comment or issue documents this as a deliberate trade-off (rg for 'SETTINGS ACK' in Http2/, agent guides and Documentation~ finds only the timeout constant and the wait itself). No guard refutes it; the admission code already handles later SETTINGS (remote MaxConcurrentStreams defaults to int.MaxValue, Http2Settings.cs:15; limit re-checked at Http2Connection.cs:351). Cost is per new connection, not per request.

### http2-runtime-12: HTTP/2 connections have no idle timeout and the reuse probe is off by default, so the first request after a silent NAT drop or app resume waits for the deadline or up to PingInterval + PingTimeout.

**medium** · platform-compat · verdict **P** · `Runtime/Transport/Http2/Http2ConnectionManager.cs:184` · RFC 9113 Section 6.7 · issue #717

- **Evidence.** SelectConnection returns any connection whose read loop still runs (Http2ConnectionManager.cs:184-216; Http2Connection.cs:140-151); nothing closes a connection that has been idle. Http2Options.ReuseProbeIdleThreshold defaults to zero (Http2Options.cs:21, 205-206) with the argument that PINGs on idle connections cost battery, but this probe only runs when a request is about to use the radio anyway. Liveness PINGs run on a free-running 30 s timer and only while streams are open (Liveness.cs:42-51, 75), so a request on a black-holed connection is detected after up to 30 s + 10 s, later than the default 30 s/45 s request timeout (UHttpRequest.cs:147, PlatformConfig.cs:21-26). For HTTP/1.1 the project already uses a 45 s idle timeout on mobile for exactly this reason (PlatformConfig.cs:31-35, #47); the HTTP/2 manager has no equivalent. A connection failure before the response is replayed only for idempotent methods (RawSocketTransport.cs:217-219).
- **Failure scenario.** Android or iOS on a carrier NAT, app idle for a few minutes or resumed from background: the next https request reuses the pooled HTTP/2 connection, HEADERS go into the kernel buffer, no answer comes, and the request ends with Timeout (or, with a longer timeout, with a network error after the PING cycle); a POST is not replayed. Needs a device or a network emulator that drops the flow silently to confirm the timing.
- **Fix direction.** Apply ConnectionPoolOptions.ConnectionIdleTimeout to HTTP/2 connections with no open streams (close with GOAWAY and retire them), and enable the reuse probe by default on mobile with a threshold below typical NAT timeouts, or start the first liveness PING relative to the request start.
- **Verifier.** Code is as described: Http2ConnectionManager has no idle timeout (no 'idle' logic in the file; SelectConnection returns any connection with AcceptsNewStreams, lines 184-216); ReuseProbeIdleThreshold defaults to TimeSpan.Zero (Http2Options.cs:21, 205-217) so the probe at Http2Connection.cs:330 is skipped; liveness PINGs run on a free-running Task.Delay(_pingInterval) loop and only when _activeStreams is non-empty (Liveness.cs:42-51, 75), so detection on a black-holed connection takes up to PingInterval + PingTimeout (30 s + 10 s) against a default 30 s/45 s request timeout (UHttpRequest.cs:147, PlatformConfig.cs:19-27). No SO_KEEPALIVE is set (platform.md:68; no keepalive socket option in Runtime/Transport/Tcp). HTTP/1.1 has both a 45 s mobile idle timeout and a 10 s reused-connection first-byte timeout (PlatformConfig.cs:36, 44); HTTP/2 has neither. The default-off probe is a documented decision (#238 closed, Transport.md:69), but its stated reason (idle PINGs cost battery) does not apply to a probe sent only when a request is about to go out. The actual failure depends on NAT/radio behaviour and cannot be settled statically; needs-device-validation.

### http2-runtime-14: The read loop awaits _writeLock to write control frames, so a DATA write blocked by TCP back-pressure stops all inbound processing until the 60 s stall timer kills the connection.

**medium** · concurrency · verdict **P** · `Runtime/Transport/Http2/Http2Connection.Lifecycle.cs:101` · RFC 9113 Section 10.5 · issue #686

- **Evidence.** The read loop awaits the write lock inline for SETTINGS ACK (ReadLoop.cs:899), PING ACK (ReadLoop.cs:944), connection and stream WINDOW_UPDATE (ReadLoop.cs:207, 304, 307 -> Lifecycle.cs:389, 101) and RST_STREAM (ReadLoop.cs:210, 415). An uploader holds the same lock for the whole socket write of a DATA frame (Send.cs:189-241), which is finished with the connection token only. While the read loop waits, no frame is read: no WINDOW_UPDATE for uploads, no PING ACK, no response data. The only bound is FailConnectionIfSendStalled after Http2StallTimeoutSeconds = 60 (Lifecycle.cs:499-511), which fails every stream on the connection. The inline wait gives natural back-pressure against PING/SETTINGS floods, so a fix has to keep a bound.
- **Failure scenario.** Large upload and large download run on one connection against a server whose frame loop awaits its own flushes (Kestrel-style output back-pressure). A transient makes the client's DATA write block; the read loop then needs the lock for a connection WINDOW_UPDATE and stops reading; the server's output fills, its loop blocks on a flush and stops reading the client's DATA. Both sides wait until the client's 60 s stall timer fails the connection and all its streams. Confirm with a bidirectional soak against Kestrel with small socket buffers.
- **Fix direction.** Never block the read loop on the write lock: put control frames (ACKs, WINDOW_UPDATE, RST_STREAM) into a small bounded outbound queue that the current or next lock holder drains, with ENHANCE_YOUR_CALM/connection failure when the bound is exceeded.
- **Verifier.** Structure confirmed: the read loop awaits _writeLock inline for SETTINGS ACK (ReadLoop.cs:899), PING ACK (ReadLoop.cs:944), WINDOW_UPDATE (ReadLoop.cs:207, 223, 304, 307 -> Lifecycle.cs:364-389 -> 101) and RST_STREAM (ReadLoop.cs:86, 210, 229 -> Lifecycle.cs:72-85 -> 101), and an uploader holds the same lock across the whole socket write of a DATA frame (Send.cs:189-241, WriteFrameLockedAsync with the connection token only, Send.cs:75-92). While the read loop waits, ReadFrameLeaseAsync is not called, so nothing inbound is processed; the only bound is FailConnectionIfSendStalled (Lifecycle.cs:499-511). No queue or try-lock path exists. The full mutual stall needs a peer that stops reading while its own writes are blocked and enough pending output to fill the client's TCP receive buffer, which depends on the server implementation and socket buffer sizes; with event-driven servers the effect is only that inbound processing is delayed by each blocked DATA write. Not settled statically.
