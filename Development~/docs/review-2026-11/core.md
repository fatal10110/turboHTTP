# Core: review findings

Scope: client API, request/response model, headers, interceptor pipeline, dispatch bridges, pooling internals. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (37 findings, 71 files read in full). All 71 files of Runtime/Core (about 10.7k lines) were read in full. The request lease model, dispatch bridges, pooling internals and error typing are carefully owned, ConfigureAwait(false) is consistent, the JSON bridge and editor-monitor hook are small reflection-free registries, and link.xml roots only four types. The main architectural risk is that client policy is stamped on requests as string-keyed metadata at CreateRequest instead of being applied at send: standalone requests, replaced metadata, redirect hops and WithProxy each skip part of it (cleartext policy, proxy and bypass rules, default headers), and the client's ProxySettings snapshot is shared by reference through public metadata. Extensibility is weaker than the public surface suggests: a third-party IHttpTransport cannot read stream bodies, third-party interceptors cannot declare an ordering role, two cache orderings stay unenforced, and the plugin system (about 13% of Core, no first-party consumer) is rooted in default builds while its capability checks hash the request body several times per request. The rest are validation gaps on public entry points (timeouts, BaseUrl, leading-slash relative URLs on Unix-like runtimes, an unsupported environment proxy), an always-on timeline with one Editor consumer, dead or duplicated code, and API-shape cleanups that are cheap now and breaking after 1.0.

**RFC conformance, protocol implementation, security** (15 findings, 70 files read in full). Core is in decent shape on this lens: the bridges uphold the handler contract (exactly one terminal outcome, caller cancellation surfaces as OperationCanceledException, 4xx/5xx are normal responses), the buffered cap is enforced incrementally on the read path, WireHost is careful about what reaches the wire, diagnostics log exception types only, and ProjectJsonBridge no longer uses reflection. The main risks are at API-contract level rather than in framing: relative URLs with a leading slash resolve to file:// on every Unix-like target, client-level policy (AllowCleartext, proxy, redirect limits) travels in mutable per-request metadata and is silently absent for standalone requests, the client's own ProxySettings instance is handed out through request metadata, and the buffered collector drops HTTP/2 trailers whenever the body source can be detached. The plugin capability model does not hold as a boundary: every plugin, including Capabilities.None, receives proxy credentials, default headers, the transport and all interceptor instances through OptionsSnapshot, and the read-only guard can be bypassed by mutating after forwarding. Wire-level injection is stopped by the transport's HttpFieldValidator, so the weak header validation in Core is defence-in-depth only. HttpMethod has no extension point for other methods (only the seven enum values), which is a feature gap rather than a defect.

**performance, resource management, concurrency, platform compatibility** (25 findings, 70 files read in full). Core's ownership plumbing is in good shape through this lens: the request lease is CAS-based and completes exactly once, both dispatch bridges use RunContinuationsAsynchronously completion sources guarded against late callbacks, body sessions defer disposal correctly, and the pooling primitives are simple and bounded. The main risk is platform behaviour of UHttpClient.ResolveUri: on Unix runtimes a relative URL that starts with '/' parses as an absolute file:// URI, so the documented BaseUrl + "/path" usage is expected to fail on iOS/Android/macOS/Linux while working in the Windows Editor. Second are the finalizer decisions: a dropped UHttpStreamingResponse never aborts its body source (permanent HTTP/1.1 lease and per-host permit leak, and an empty finalizer in release builds), while UHttpResponse's finalizer returns pooled buffers that a copied-out Body sequence can still reference. The rest is avoidable per-request cost: double header/metadata clones in UHttpRequest.Clone/CopyWithSharedContent, the Dictionary<string, List<string>> header storage, RequestContext snapshots and always-on timeline events, a full-body hash run six times per request by the plugin capability guard, and a full-size temporary array in GetBodyAsString for any body above 16 KB. Smaller check-then-act and ordering weaknesses exist in UHttpClient dispose, UHttpRequest.BeginSend and the buffered collector's failure path. Static state in Core is benign across Enter Play Mode without domain reload, except that HttpTransportFactory caches a factory exception for the life of the domain.

### core-design-01: Client-level policy (AllowCleartext, Proxy, DefaultHeaders, DefaultTimeout, redirect settings) is stamped on requests only in CreateRequest, so requests built with the public constructor or with replaced metadata are sent without it.

**high** · architecture · verdict **C** · `Runtime/Core/UHttpClient.cs:747` · also reported as core-protocol-03, docs-accuracy-06

- **Evidence.** UHttpClient.ApplyDefaultMetadata (UHttpClient.cs:747-760) and ApplyDefaultHeaders (:182) run only from CreateRequest (:169-191). SendBufferedAsync/SendStreamingAsync (:377, :446) accept any UHttpRequest and apply nothing. The public constructor (UHttpRequest.cs:115-131) starts with empty metadata and a hard-coded 30 s timeout (UHttpRequest.cs:147) while the client default is PlatformConfig.RecommendedTimeout (45 s on mobile, UHttpClientOptions.cs:40). ### core-design-02: ResolveUri treats a leading-slash relative URL as absolute on Unix-like runtimes, so the documented client.Get('/path') with BaseUrl becomes file:///path on macOS, Linux, iOS and Android.

**high** · platform-compat · verdict **C** · `Runtime/Core/UHttpClient.cs:733` · also reported as core-protocol-01, core-runtime-01, docs-accuracy-01

- **Evidence.** ResolveUri (UHttpClient.cs:731-745) first calls Uri.TryCreate(url, UriKind.Absolute, ...) and returns the result when it succeeds; BaseUrl is only used otherwise. On Mono and .NET for Unix a string starting with '/' is an implicit absolute file path, so TryCreate succeeds with scheme 'file' (the reason Mono has the DotNetRelativeOrAbsolute UriKind workaround). Nothing in Core rejects non-http schemes; the transport later throws 'Unsupported URI scheme: file' (Runtime/Transport/RawSocketTransport.cs:451-458). README.md:111, Documentation~/QuickStart.md:162, Documentation~/Modules/Core.md:55 and Samples~/02, 04, 05 all use client.Get('/...') with BaseUrl. The only resolution test uses 'users' without a slash (Tests/Runtime/Core/UHttpClientTests.Builders.cs:90-95); UHttpRequestBuilderJsonTests.cs:38 uses '/api' but never checks the URI.
- **Failure scenario.** BaseUrl = 'https://api.example.com'; client.Get('/data').SendBufferedAsync() works in the Windows Editor and fails on an Android, iOS, macOS or Linux player with UHttpException(InvalidRequest, 'Unsupported URI scheme: file'). Confirm by asserting client.Get('/x').Uri on a macOS Editor or an Android player.
- **Fix direction.** When BaseUrl is set, resolve against it unless the parsed absolute URI has an http or https scheme (or check for '://' before trying absolute). Reject other schemes in CreateRequest with InvalidRequest. Add a test for '/path' that asserts the resolved URI and runs on a non-Windows runner.
- **Verifier.** ResolveUri returns the Uri.TryCreate(url, UriKind.Absolute) result with no scheme check (Runtime/Core/UHttpClient.cs:731-734); BaseUrl is only reached when that fails. I ran Uri.TryCreate("/data", UriKind.Absolute) on .NET 8 on Linux in the scratchpad: it returns true with file:///data ("/api/users?x=1" becomes file:///api/users%3Fx=1). Nothing in Core rejects the scheme; the transport throws InvalidRequest 'Unsupported URI scheme' (Runtime/Transport/RawSocketTransport.cs:451-458). The pattern is documented and sampled: README.md:111, Documentation~/QuickStart.md:162, Documentation~/Modules/Core.md:55/121, Samples~/02, 04, 05. Tests only resolve "users" (Tests/Runtime/Core/UHttpClientTests.Builders.cs:90-95); UHttpRequestBuilderJsonTests.cs:38 uses "/api" but never asserts the URI. Not executed on Unity: Mono/IL2CPP on macOS, Linux, iOS and Android apply the same implicit-Unix-file-path rule for UriKind.Absolute (the reason Mono has DotNetRelativeOrAbsolute), so the same failure is expected there, but it needs one device/Mac Editor assertion (needs-device-validation). Windows Editor resolves against BaseUrl, which explains why it went unnoticed. No issue tracks it.

### core-design-08: Interceptor ordering is enforced for two pairs only and only for first-party types; Cache outside Redirect and Cache outside Cookie are accepted, and third-party interceptors cannot declare a role.

**medium** · architecture · verdict **C** · `Runtime/Core/Pipeline/InterceptorOrdering.cs:53` · 9111 section 3 and 4.1

- **Evidence.** InterceptorOrdering.Rules holds Cache-outside-Auth and Concurrency-outside-Retry (InterceptorOrdering.cs:53-70). InterceptorRole.Redirect exists (:13) but no rule uses it for ordering, and there is no Cookie role. IInterceptorRole and InterceptorRole are internal (:10, :23), so a third-party cache or auth interceptor, or a user decorator around a first-party one, has role None and is never checked. RedirectHandler forwards only the final non-3xx response to the outer handler (Runtime/Middleware/RedirectHandler.cs:132-147) and Runtime/Cache contains no redirect handling, so a cache placed outside the redirect interceptor stores the final hop's response under the original URL. The cache builds its Vary key from the request headers it sees (Runtime/Cache/CacheInterceptor.Variants.cs:54), and CookieInterceptor adds Cookie inside it when the cache is outside. Tests/Runtime/Core/InterceptorOrderTests.cs has no case for either order.
- **Failure scenario.** Interceptors = [CacheInterceptor, RedirectInterceptor]: GET /latest -> 302 (not cacheable) -> /v2/file 200 max-age=3600 is stored under /latest; after the server repoints /latest the client keeps serving v2 for an hour. Interceptors = [CacheInterceptor, CookieInterceptor]: a response with Vary: Cookie is matched against a request that has no Cookie header yet, so the entry stored for one session is served after the jar switches to another.
- **Fix direction.** Add Cache-outside-Redirect and Cache-outside-Cookie rules (give CookieInterceptor a role), and make the role contract usable outside the first-party assemblies (public interface or attribute) so custom cache/auth interceptors and decorators take part in validation.
- **Verifier.** Rules hold only Cache-outside-Auth and Concurrency-outside-Retry (Runtime/Core/Pipeline/InterceptorOrdering.cs:53-70); InterceptorRole.Redirect is used only for the FollowRedirects warning (UHttpClient.cs:152); IInterceptorRole/InterceptorRole are internal (:10, :23), so a third-party or decorated interceptor has role None. The cookie scenario is weaker than stated: a response with Vary: Cookie is not stored unless CachePolicy.AllowVaryCookie is set (Runtime/Cache/CacheInterceptor.cs:614-618, default false), and Set-Cookie responses are not stored by default (:590). ### core-protocol-02: The buffered collector discards HTTP/2 response trailers whenever the body source can be detached

**medium** · protocol-impl · verdict **C** · `Runtime/Core/Pipeline/ResponseCollectorHandler.cs:208` · RFC 9110 Section 6.5; RFC 9113 Section 8.1

- **Evidence.** CollectAsync tries body.TryDetachBufferedBody first (ResponseCollectorHandler.cs:159). On that path it never asks for trailers (line 190: 'if (!detached) trailers = await body.GetTrailersAsync') and builds the response with 'trailers: HttpHeaders.Empty' (line 208). DetachedBufferedBody carries no trailers. The Core sources refuse to detach when trailers exist (BufferedResponseBodySource.cs:38, SegmentedResponseBodySource.cs:71), but Http2ResponseBodySource.TryDetachBufferedBody (Runtime/Transport/Http2/Http2ResponseBodySource.cs:90-110) only requires the stream to be complete and the trailers task to be completed without fault; it does not check that the trailers are empty. The read loop sets the trailers and then completes the body (Http2Connection.ReadLoop.cs:694-697), and OnResponseStartAsync runs from a queued thread-pool work item (Http2Stream.cs:288, 636-655), so for a small response the read loop has usually processed DATA and the trailing HEADERS before the collector runs. No test asserts buffered HTTP/2 trailers (only HTTP/1.1: RawSocketTransportTests.cs:2275).
- **Failure scenario.** An HTTP/2 server answers with HEADERS, one DATA frame and trailing HEADERS (grpc-status, a digest, Server-Timing) in one flight. SendBufferedAsync returns a UHttpResponse whose Trailers is empty; the same response read slowly (or through SendStreamingAsync) has the trailers. The result depends on a race between the read loop and the queued response-start callback.
- **Fix direction.** Make the detach contract carry trailers: either add trailers to DetachedBufferedBody and pass them to UHttpResponse, or have the collector read GetTrailersAsync before detaching and have Http2ResponseBodySource refuse to detach when its trailers are not empty. Add a deterministic test with a completed HTTP/2 stream that has trailers.
- **Verifier.** Traced. ResponseCollectorHandler.cs:159 tries TryDetachBufferedBody first; on that path line 190 skips GetTrailersAsync and line 208 builds the response with trailers: HttpHeaders.Empty. The Core sources honour the implied contract (BufferedResponseBodySource.cs:38 refuses when _trailers.Count != 0), and Tests/Runtime/Pipeline/BufferedDispatchBridgeTests.cs:73 (DetachedBufferedBody_SkipsTrailersAndSourceDispose) pins 'detached means no trailers'. Http2ResponseBodySource.TryDetachBufferedBody (Runtime/Transport/Http2/Http2ResponseBodySource.cs:94-110) only requires terminal state Completed and a completed, non-faulted trailers task; it never checks that the result is empty. The read loop sets the trailers and then completes the body (Http2Connection.ReadLoop.cs:694-697 -> Http2Stream.cs:452-454 SetTrailers, 492-494 Complete), and response start is a queued thread-pool item (Http2Stream.cs:288), so when DATA and trailing HEADERS are processed before the collector runs the source detaches and the trailers are dropped; otherwise the read path returns them. Result is race dependent, as stated. No buffered HTTP/2 trailer test exists (only the streaming one, Http2ConnectionTests.StreamingResponses.cs:17-76). HTTP/1.1 is not affected (Http11ResponseBodySource.cs:99-121 detaches only empty bodies). The fix belongs in the Transport source and/or the Core detach contract.

### core-runtime-02: A dropped UHttpStreamingResponse never aborts its body source: the HTTP/1.1 lease and per-host permit leak for the life of the transport, and release builds keep an empty finalizer

**medium** · resource-management · verdict **C** · `Runtime/Core/UHttpStreamingResponse.cs:77`

- **Evidence.** The finalizer (77-87) only counts and logs under DEBUG || UNITY_EDITOR || DEVELOPMENT_BUILD; in release builds its body is empty, yet the type still has a finalizer, so every streaming response is registered for finalization for no effect. It never calls _bodySource.Abort(). The source is the only owner of the transport resources: Http11ResponseBodySource keeps the ConnectionLease (Http11ResponseBodySource.cs:59) and releases it only in CompleteBody/CloseBody (660-684); ConnectionLease (TcpConnectionPool.cs:152) releases the per-host SemaphoreSlim permit only from Dispose/ReturnToPool/TransferOwnership; neither type has a finalizer (the only finalizers in Runtime outside vendored code are the four in Core). The attached release callbacks (request hold, RequestContext.CompleteAfterResponse) are never run either.
- **Failure scenario.** Application code drops a streaming response with an unread body (an exception between SendStreamingAsync and the using, or a forgotten dispose) MaxConnectionsPerHost times for one host over HTTP/1.1 (8 on mobile): every permit of that host is gone, later requests to it wait for a permit until their timeout, and a release build logs nothing.
- **Fix direction.** Give the dropped response a backstop in every build: from the finalizer queue a static thread-pool callback that calls Abort() on the body source (no managed callbacks on the finalizer thread), or make the lease itself finalizer-safe. If the finalizer stays diagnostics-only, compile the whole finalizer out of release builds.
- **Verifier.** UHttpStreamingResponse.cs:77-87: the finalizer body exists only under DEBUG || UNITY_EDITOR || DEVELOPMENT_BUILD and only counts and logs; in release it is an empty finalizer; it never calls _bodySource.Abort(). I looked for another backstop and found none for HTTP/1.1: the only finalizers in Runtime outside vendored code are in Core (UHttpRequestBody.cs:386 and 463, UHttpResponse.cs:280, this one); the request deadline ends with the dispatch ('using var timeoutCts', RawSocketTransport.cs:439-441) and Http11ResponseBodySource keeps the ConnectionLease (Http11ResponseBodySource.cs:46-59) with no timer, so the lease and its per-host permit are released only by reading to the end, Dispose or Abort. HTTP/2 has a stall watchdog that aborts an unread buffered body (StreamingOptions.Http2StallTimeoutSeconds, StreamingOptions.cs:71-80), so the permanent leak is HTTP/1.1 only. It needs an application bug (a response dropped without dispose, with an unread body), which the type's contract forbids, hence medium: the cost of that bug is a permanent per-host permit loss with no log in release builds.

### core-runtime-03: UHttpResponse's finalizer returns pooled body buffers to ArrayPool while a copied-out Body sequence can still reference them

**medium** · resource-management · verdict **P** · `Runtime/Core/UHttpResponse.cs:280`

- **Evidence.** ~UHttpResponse (280-283) calls Dispose(false), which returns _pooledBodyBuffer through ByteArrayPool.Return (298-299) and disposes _segmentedBodyOwner (304-305): SegmentedBuffer.Dispose -> PooledSegment.ReturnToPool -> ArrayPool.Shared.Return (SegmentedBuffer.cs:186-228, PooledSegment.cs:86-92), or the HTTP/2 ArrayPoolMemoryOwner (Http2ResponseBodySource.cs:161-164). Body (37-44) hands out a ReadOnlySequence<byte> struct that references those arrays but not the response; GetBodyAsString (153-164) and JsonExtensions.cs:33 keep reading the sequence after their last use of the response object and nothing calls GC.KeepAlive. architecture.md ("Ownership transfer") forbids returning a buffer another thread may still touch.
- **Failure scenario.** Code keeps the sequence, a segment or a Memory slice but not the response (var body = (await req.SendBufferedAsync()).Body;): the GC finalizes the response, its 16 KB segments go back to ArrayPool.Shared, the next response collector rents them, and the caller reads another request's bytes (silent corruption and cross-request data exposure). Without the finalizer return the same mistake would only cost garbage. Under a precise GC the window also exists inside (await ...).GetBodyAsString() / AsJson<T>() on a temporary response.
- **Fix direction.** On the finalizer path do not return buffers to the pool: leave them to the GC and account them with ByteArrayPool.Abandon so the #292 leak counter stays exact; keep pool returns for explicit Dispose. Add GC.KeepAlive(this) at the end of the GetBodyAsString overloads.
- **Verifier.** Code is as described: ~UHttpResponse (UHttpResponse.cs:280-283) runs Dispose(false), which returns _pooledBodyBuffer through ByteArrayPool.Return (298-299) and disposes _segmentedBodyOwner (304-305), i.e. hands the body arrays back to ArrayPool. Body (37-44) returns a ReadOnlySequence<byte> struct that references the arrays but not the response, and GetBodyAsString (153-164) has no GC.KeepAlive(this). So code that keeps the sequence or a slice while the response becomes unreachable can read arrays re-rented by another request. The XML remarks (29-36) forbid use after Dispose, but dropping the response is the same mistake made silently, and the finalizer turns it from garbage into cross-request corruption for no real gain (unreturned ArrayPool arrays are just collected). Plausible rather than confirmed: it needs caller misuse plus GC and finalizer timing; the in-method window on a temporary response is narrow under Boehm's conservative stack scan on Mono/IL2CPP and cannot be settled statically. architecture.md:111 ('A finalizer never calls pool callbacks') is about callbacks; the comments at 296-303 argue thread safety of the return, not aliasing, so the documented trade-off does not cover this.

### core-runtime-04: The plugin capability guard hashes the whole buffered request body about six times per request and re-wraps the plugin interceptor on every request

**medium** · performance · verdict **C** · `Runtime/Core/PluginContext.cs:150`

- **Evidence.** RequestMutationSignature.Capture stores request.Content.GetHashCode() (150). BufferedRequestBody and OwnedMemoryRequestBody override GetHashCode with ComputeStableHash, a byte-at-a-time loop over the entire body (UHttpRequestBody.cs:242-254, 328-331, 391-397); Capture also hashes every header name and value (200-218). For a plugin without the full capability set one request runs Capture in the InvocationGuard constructor (270), the GuardedNextAsync pre-check (320 -> 396), ObservedHandler.OnRequestStart (634), InvocationGuard.OnRequestStart (358; the argument is computed before RecordForwarded's early return at 529, so MutateResponses plugins pay it too), the GuardedNextAsync finally (348) and the post-dispatch check (299).
