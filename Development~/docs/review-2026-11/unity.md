# Unity integration: review findings

Scope: main-thread dispatch, asset handlers and decoders, mobile bridges, Unity WebSocket, UniTask, bootstrap, native plugins. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (42 findings, 69 files read in full). The Unity slice is carefully written at the micro level (ownership of Unity objects on cancel, the WebSocket component's generation logic, the JNI thread, the iOS task table), but its modularity story does not hold. TurboHTTP.Unity is one assembly that welds the dispatcher to texture, audio, temp-file, mobile and JNI code; its link.xml (merged into every build by TurboHttpLinkerProcessor) preserves all decoders including the always-throwing stubs, its 11 RuntimeInitializeOnLoad hooks create a GameObject, a PlayerLoop system and per-frame work with one allocation per frame in every player, and it hard-depends on the Audio, UnityWebRequest(+Audio) and ImageConversion engine modules that package.json does not declare. TurboHTTP.Complete cannot be excluded from a UPM install (no define constraint, AlwaysLinkAssembly), so the lean path that architecture.md describes is not reachable by a customer, and 10 of its 15 asmdef references are dead. The main behavioural risks in this lens are the dispatcher's unenforced lifetime contracts (destroyed GameObject and replaced PlayerLoop are both terminal, low-memory shedding is reported as cancellation and silently drops WebSocket lifecycle callbacks), reconfiguration that disposes semaphores still in use, coroutine cleanup that lives in an iterator finally Unity never runs, and several features that are half-implemented or collect data nobody reads (background replay queue with no consumer, Android guard that is a no-op costing two blocking JNI calls per request, WorkManager placeholder that retries forever, adaptive byte counting). The UniTask WebSocket adapters still use Task.AsUniTask(), which the HTTP adapter's own comment says throws without a SynchronizationContext.

**RFC conformance, protocol implementation, security** (26 findings, 69 files read in full). All 69 in-scope files were read in full (Plugins/iOS/TurboHttpSecTrustVerifier.mm is outside the listed scope and was not reviewed). The slice has no wire protocol; the solid parts are the iOS background-task bridge (begin/end/expiry are balanced exactly once, no lock held across UIKit), the JNI thread marshalling, path-traversal checks with a canonical second check, unpredictable temp-file names, bounded dispatcher queues and the WebSocket bridge's drop accounting. The main risk is the experimental Android background path: the WorkManager placeholder job retries forever and is orphaned by a normal process death, it persists the full request URL (query secrets included) as its key, and expiry-cancelled requests surface as caller cancellations (silently, for coroutine users). The second cluster is unbounded decoding of hostile media: textures have no default pixel/byte bound although the docs claim one, the MaxPixels pre-check fails open, audio has no size bound at all and its temp files live in the shared external cache on Android. The third cluster is API contracts that do not hold: adaptive networking can only shorten timeouts under the defaults, CoroutineWrapper swallows exceptions thrown by onSuccess, client.WebSocket() forwards default (credential) headers while dropping the proxy, the WebSocket UniTask adapters throw off the main thread after the operation started, and the AIFF decoder plays AIFF-C data as noise.

**performance, resource management, concurrency, platform compatibility** (29 findings, 71 files read in full). The Unity slice is careful about the hard cases it already met: Unity objects created for a cancelled request are destroyed, the native bridges avoid the main thread and pool-thread JNI attachment, P/Invoke callbacks are static and kept alive, and most static state is reset for Enter Play Mode without domain reload. The main risks are in the plumbing around MainThreadDispatcher: it allocates every frame and about 15 objects per dispatched callback, it stops for good if its PlayerLoop hook or GameObject disappears, and low-memory shedding drops WebSocket lifecycle callbacks that are documented as never dropped. Resource ownership is weakest in CoroutineWrapper (cleanup lives in an iterator finally Unity never runs for a stopped coroutine) and in the two semaphores that Configure disposes or swaps while operations hold them. The asset helpers double-buffer bodies (texture header check, audio and download-to-file flattening) and the texture scheduler runs decode work under its own lock. On mobile the opt-in Android background path pays three blocking JNI hand-offs per request for a no-op guard and leaves a WorkManager job that retries forever once the process dies; device-only claims are marked plausible.

## High (1)

### unity-protocol-01: The Android deferred-work WorkManager job returns Result.retry() forever and nothing cancels it after the process dies, so each queued request leaves an immortal job that keeps waking the app

**high** · protocol-impl · verdict **C** · `Plugins/Android/TurboHttpBackground.androidlib/src/main/java/com/turbohttp/background/TurboHttpBackgroundWorker.java:24` · also reported as unity-design-18, unity-runtime-18

- **Evidence.** TurboHttpBackgroundWorker.doWork (lines 21-25) always returns Result.retry(). TurboHttpBackgroundPlugin.enqueueDeferredWork (TurboHttpBackgroundPlugin.java:52-58) enqueues a OneTimeWorkRequest with no constraints, no attempt cap and ExistingWorkPolicy.KEEP. The only cancel is cancelDeferredWork (java:63-76), reached from AndroidBackgroundWorkBridge.TryMarkReplayComplete (Runtime/Unity/Mobile/Android/AndroidBackgroundWorkBridge.cs:246-266), which only BackgroundNetworkingInterceptor.TryDequeueReplayable calls (Runtime/Unity/Mobile/BackgroundNetworkingInterceptor.cs:51-68). Both the replay queue (BoundedRequestQueue, BackgroundNetworkingInterceptor.cs:222-272) and _queuedWorkIds (AndroidBackgroundWorkBridge.cs:34) are in-memory, so a new process knows no keys; AndroidBackgroundPluginJni.CancelDeferredWork (AndroidBackgroundPluginJni.cs:133-140) is also a no-op until EnsureInitialized ran in that process. The worker comment says the host app can 'rehydrate its policy and state', but no managed API lists or restores persisted work. No test covers a process restart; Documentation~/PlatformNotes.md:147-158 does not mention it. WorkManager's merged manifest adds RECEIVE_BOOT_COMPLETED, so the jobs are rescheduled after reboot too.
- **Failure scenario.** App built with TURBOHTTP_BACKGROUND_NETWORKING and UseBackgroundNetworking() is paused for more than 5 s with a GET in flight: the request is queued and enqueueUniqueWork persists a job. The OS then kills the paused process (the normal outcome). WorkManager starts the app process to run the worker, which returns retry; the backoff grows to the 5 h cap and the cycle continues across reboots indefinitely. Every distinct dedupe key (by default every distinct URL) adds another job; a later process cannot cancel them because it does not know the keys.
- **Fix direction.** Give the placeholder a terminal state: return success/failure after one run (or cap on getRunAttemptCount), tag all work and cancel by tag at startup (cancelAllWorkByTag) so a cold start clears orphans, and make CancelDeferredWork initialize the plugin instead of returning early. Until a cold-started process can actually replay, do not enqueue persistent work at all.
- **Verifier.** Traced. TurboHttpBackgroundWorker.java:21-25 returns Result.retry() unconditionally; TurboHttpBackgroundPlugin.java:52-58 enqueues an unconstrained OneTimeWorkRequest with ExistingWorkPolicy.KEEP and no attempt cap or tag. The only cancel path is cancelUniqueWork (java:63-76) <- AndroidBackgroundWorkBridge.TryMarkReplayComplete (AndroidBackgroundWorkBridge.cs:246-266) <- BackgroundNetworkingInterceptor.TryDequeueReplayable (BackgroundNetworkingInterceptor.cs:51-68), which nothing in Runtime/ calls (tests only) and Documentation~ never mentions, so even a live process leaves the job retrying unless the app calls that API. Replay queue (cs:222-272) and _queuedWorkIds (bridge cs:34) are in-memory, and AndroidBackgroundPluginJni.CancelDeferredWork (cs:133-140) returns early before EnsureInitialized, so a new process can neither know nor cancel the keys. No guard found. #266 covers device validation of begin/end/expiry only; #267 (closed) introduced the enqueue. Mitigation: feature is experimental and opt-in (TURBOHTTP_BACKGROUND_NETWORKING); WorkManager retry cadence/boot persistence is platform behaviour not run here.

### unity-design-01: Runtime/Unity/link.xml preserves all ten decoder types (including the three always-throwing stubs) although nothing reaches them by reflection, and thereby roots TurboHTTP.Unity in every player build

**medium** · pluggability · verdict **C** · `Runtime/Unity/link.xml:2`

- **Evidence.** link.xml:3-12 lists IImageDecoder, IAudioDecoder, DecodedImage, DecodedAudio, DecoderRegistry, StbImageSharpDecoder, WavPcmDecoder, AiffPcmDecoder, NVorbisDecoder, NLayerMp3Decoder with preserve="all". Editor/TurboHttpLinkerProcessor.cs:146-150 merges every Runtime/**/link.xml whose owning DLL is in the linker input directory, and TurboHTTP.Unity.dll always is (asmdef has no platform or define constraint, Runtime/Unity/TurboHTTP.Unity.asmdef:5-11). The decoders are only ever created statically (Runtime/Unity/Decoders/DecoderRegistry.cs:417-425, new StbImageSharpDecoder() etc.) and resolved through the IImageDecoder/IAudioDecoder interfaces; there is no Type.GetType/Activator path, so the rules protect nothing. Decoders/ is 1,188 lines (DecoderRegistry 427, Aiff 255, Wav 225, stubs 176, rest 105), all kept with every member.
- **Failure scenario.** An HTTP-only project (no textures, no audio, no TurboHTTP.Unity type referenced from its code) builds with Managed Stripping High: the merged link.xml names TurboHTTP.Unity, so UnityLinker processes the assembly instead of dropping it, keeps ~1.2k lines of decoder code plus DecoderRegistry's static state, and (because the assembly is now linked) keeps its RuntimeInitializeOnLoad hooks, see unity-design-02. The stubs tracked by #158 cannot even be stripped.
- **Fix direction.** Delete Runtime/Unity/link.xml (the static new-expressions already root what is used) or reduce it to types that are genuinely reached by name. If some startup hook must survive stripping, put [Preserve] on that method instead of preserving unrelated types.
- **Verifier.** Runtime/Unity/link.xml:3-12 preserves ten Decoders types with preserve="all". No reflection reaches them: rg for Type.GetType/Activator/GetTypes in Runtime/Unity, Runtime/Unity.WebSocket, Runtime/Bootstrap has no hit; decoders are created with new in DecoderRegistry.AddDefaultDecoders_NoLock (Decoders/DecoderRegistry.cs:417-425). Editor/TurboHttpLinkerProcessor.cs:146-150 merges the file whenever TurboHTTP.Unity.dll is in the linker input (asmdef has no platform/define constraint), so UnityLinker is told to keep these types in every stripped build, including the #158 always-throwing stubs. File dates from the phase-15 commit d308f8e with no stated reason. #158 tracks the stubs, not the link.xml. The statically certain cost is ~1.2k lines of unstrippable decoder code; that naming the assembly also keeps its RuntimeInitializeOnLoad hooks alive in projects that reference no TurboHTTP.Unity type is UnityLinker behaviour (consistent with Runtime/Bootstrap/AssemblyInfo.cs:6-8) and only matters at stripping Low or above. Removing the file must be paired with unity-design-05, which currently depends on it.

### unity-design-02: TurboHTTP.Unity runs eleven startup hooks unconditionally: a DontDestroyOnLoad GameObject, a PlayerLoop system, lowMemory subscriptions and a temp-file sweep are installed in every player, with no way to take one feature without the others

**medium** · pluggability · verdict **C** · `Runtime/Unity/MainThreadDispatcher.cs:242`

- **Evidence.** MainThreadDispatcher.cs:242-250 [RuntimeInitializeOnLoadMethod(BeforeSceneLoad)] always calls EnsureInstanceReady, which creates the '[TurboHTTP MainThreadDispatcher]' GameObject (697-699); Awake installs a PlayerLoop system and an Application.lowMemory handler (280-283). AudioClipHandler.cs:123-127 (BeforeSceneLoad) calls UnityTempFileManager.EnsureStartupSweep, a synchronous Directory.Exists/GetFiles(AllDirectories)/File.Delete on the main thread (UnityTempFileManager.cs:166-191). TextureDecodeScheduler.cs:97-122 forces creation of the Shared instance and subscribes lowMemory. Further SubsystemRegistration hooks: AudioClipHandler.cs:109, DecoderRegistry.cs:75, UnityTempFileManager.cs:108 and 414, LifecycleCancellation.cs:114, StreamedAudioTempFiles.cs:62, MainThreadDispatcher.cs:218 and, on every platform including desktop and iOS, AndroidBackgroundExpirySignal.cs:85 (AndroidAppPauseSource). LifecycleCancellation adds a second hidden GameObject with its own per-frame Update poll (LifecycleCancellation.cs:229-238, 277-280) and AndroidAppPauseListener a third (AndroidAppPauseListener.cs:12-19). The asmdef (TurboHTTP.Unity.asmdef) has no defineConstraints and none of the hooks checks whether the feature is used.
- **Failure scenario.** A project that only wants UseAdaptiveNetworking (or only PathSafety downloads, or nothing from TurboHTTP.Unity at all but links it, see unity-design-01) gets a dispatcher GameObject in the DontDestroyOnLoad scene, a system appended to its PlayerLoop, a drain call with two lock acquisitions and one allocation every frame (unity-design-10), a main-thread file-system sweep before the first scene, and static roots for the texture scheduler, temp-file manager and decoder registry. The dispatcher (1,033 + 722 lines), the temp-file manager and the scheduler are therefore unstrippable in any build that links the assembly.
- **Fix direction.** Create the dispatcher lazily on first main-thread use (keep only a cheap BeforeSceneLoad hook that records the main thread id), run the temp-file sweep lazily from the first audio call on a worker thread, and make the reset hooks no-ops that do not instantiate singletons. Longer term split the assembly: TurboHTTP.Unity (dispatcher, lifecycle, coroutines), TurboHTTP.Unity.Assets (texture/audio/decoders/temp files), TurboHTTP.Unity.Mobile.
- **Verifier.** Traced: MainThreadDispatcher.BootstrapBeforeSceneLoad (MainThreadDispatcher.cs:242-250) always calls EnsureInstanceReady, which creates the DontDestroyOnLoad GameObject (:697-699); Awake subscribes Application.lowMemory and installs the PlayerLoop system (:280-283). AudioClipHandler.RuntimeInitialize (AudioClipHandler.cs:123-127) -> UnityTempFileManager.EnsureStartupSweep, a synchronous Directory.GetFiles(AllDirectories)+delete on the main thread when the temp root exists (UnityTempFileManager.cs:166-191). TextureDecodeScheduler.ResetStaticState touches Shared and subscribes lowMemory (TextureDecodeScheduler.cs:97-121). No feature-use check and no defineConstraints in TurboHTTP.Unity.asmdef. Two details overstated: the LifecycleCancellation driver GameObject is created lazily on the first Bind with a non-null owner (LifecycleCancellation.cs:138-143, 229-238), and AndroidAppPauseListener is compiled only under UNITY_ANDROID && !UNITY_EDITOR && TURBOHTTP_BACKGROUND_NETWORKING (AndroidAppPauseListener.cs:1). The remaining SubsystemRegistration hooks are cheap static resets. #182 (oversized files) does not track this.

### unity-design-09: Low-memory shedding is reported as cancellation, so WebSocket connected/closed callbacks are dropped despite the documented never-dropped guarantee and texture loads look user-cancelled

**medium** · architecture · verdict **C** · `Runtime/Unity/MainThreadDispatcher.cs:1000` · also reported as unity-runtime-05

- **Evidence.** HandleLowMemory drops up to LowMemoryDropCount user items with a plain OperationCanceledException (1000-1003); DispatchWorkItem.Fail turns that into tcs.TrySetCanceled (535-541). UnityWebSocketBridge.ObserveDispatchResult maps a canceled dispatch to OnUserLaneFailed(new OperationCanceledException) (UnityWebSocketBridge.cs:359-364), and OnUserLaneFailed only re-dispatches on the control lane when the exception is MainThreadDispatchRejectedException (529-542); everything else falls to 549-552: the callback is discarded and logged. Lifecycle callbacks take the user lane first (HandleConnected 214, HandleClosed 253, DispatchLifecycle 314-320). The bridge documents 'Connected and closed callbacks are never dropped' (44-50) and MainThreadDispatchRejectedException's remarks say drops fault with that type 'so a drop can be told apart from the caller's own cancellation' (MainThreadDispatchRejectedException.cs:42-45); Reconfigure and DropOldest follow it (MainThreadWorkQueue.cs:283-285, 388-392), low memory does not. TextureDecodeScheduler.OnLowMemory faults queued decodes with OperationCanceledException as well (TextureDecodeScheduler.cs:290-291). No test covers low-memory shedding of bridge callbacks.
- **Failure scenario.** On a phone under memory pressure Application.lowMemory fires while an OnClosed (or OnConnected) callback is still in the user queue. The callback is shed; UnityWebSocketClient never raises OnDisconnectedEvent for that connection (its only path is the bridge's OnClosed, UnityWebSocketClient.cs:827,846), so reconnect UI waiting for the event never runs. A GetTextureAsync caller in the same frame receives TaskCanceledException although its token was never cancelled, which most callers swallow as a user cancel, so the image silently never appears.
- **Fix direction.** Shed with MainThreadDispatchRejectedException (add a LowMemory reason) in both the dispatcher and the texture scheduler, so the bridge's control-lane fallback applies and callers can tell shedding from cancellation. Add a test that sheds a queued lifecycle callback and asserts it still runs.
- **Verifier.** HandleLowMemory drops user items with a plain OperationCanceledException (MainThreadDispatcher.cs:1000-1003) via WorkQueue.DropUserWork (MainThreadWorkQueue.cs:518-547, oldest first, default LowMemoryDropCount 128); DispatchWorkItem.fail maps it to tcs.TrySetCanceled (:535-541). UnityWebSocketBridge sends Lifecycle items through the user lane (UnityWebSocketBridge.cs:214, 253, 327), ObserveDispatchResult turns a cancelled task into OperationCanceledException (:359-364), and OnUserLaneFailed re-dispatches on the control lane only for MainThreadDispatchRejectedException (:529-535); otherwise the callback is discarded and logged (:549-552). That contradicts the documented 'Connected and closed callbacks are never dropped' (:48-49) and MainThreadDispatchRejectedException's remark that drops are distinguishable from cancellation. The other drop paths do use the rejected exception (MainThreadWorkQueue.cs:283-285, 388-392, 474-478). One correction: UnityWebSocketClient has a second OnDisconnected path (ReleaseConnectionAsync, UnityWebSocketClient.cs:554-557), but it runs only when the component itself disconnects/reconnects and also uses the sheddable user lane, so a server-initiated close whose OnClosed is shed is still lost. TextureDecodeScheduler.OnLowMemory faults with OperationCanceledException (TextureDecodeScheduler.cs:290-291), so callers see an OperationCanceledException (not TaskCanceledException) without having cancelled. No test exercises low-memory shedding of bridge callbacks. Window is the queue residency at the moment Application.lowMemory fires.

### unity-design-10: The dispatcher clones its settings object every frame and on every ExecuteAsync call

**medium** · performance · verdict **C** · `Runtime/Unity/MainThreadDispatcher.cs:932`

- **Evidence.** DrainQueueWithinFrameBudget starts with var settings = GetSettings() (932), and GetSettings returns _settings.Clone() under LifecycleLock (146-152; Clone allocates a new MainThreadDispatcherSettings, MainThreadWorkQueue.cs:99-112). The drain is called once per frame from the PlayerLoop system even when the queue is empty (906-925), in every player because of the unconditional bootstrap (unity-design-02). ExecuteAsync and ExecuteAsync<T> also clone only to read AllowInlineExecutionOnMainThread (352, 427). UnityPerformanceBudgetTests has no idle-allocation budget for the dispatcher.
- **Failure scenario.** Every frame of every game that links TurboHTTP.Unity allocates one settings object (about 64 bytes) and takes two locks while idle: roughly 3.8 KB/s of garbage at 60 fps that shows up as a permanent per-frame GC Alloc entry in the profiler, against the project rule that hot paths stay allocation-free. Each queued WebSocket message adds another clone.
- **Fix direction.** Keep the validated settings as an immutable snapshot published with Volatile.Write and read the fields directly in the drain and in ExecuteAsync; clone only in the public GetSettings().
- **Verifier.** DrainQueueWithinFrameBudget begins with GetSettings() (:932), which returns _settings.Clone() under LifecycleLock (:146-152); MainThreadDispatcherSettings is a sealed class and Clone allocates a new instance (MainThreadWorkQueue.cs:56, 99-112). The drain is entered once per frame from the PlayerLoop system whenever the state is Ready, before the queue is checked (:911-925, :945), and the dispatcher is created unconditionally at BeforeSceneLoad (:242-250), so every idle frame allocates one settings object and takes LifecycleLock plus the queue lock. ExecuteAsync and ExecuteAsync<T> clone again to read one bool (:352, :427); HandleLowMemory clones too (:997). UnityPerformanceBudgetTests has only a dispatcher.idle_queue_depth budget, no allocation budget. Small per-frame garbage, but permanent and against the allocation rule in CLAUDE.md section 4.

### unity-design-11: AudioClipHandler.Configure and UnityTempFileManager.Configure dispose and replace semaphores that in-flight operations still hold, and the temp-file manager releases a different semaphore than it acquired

**medium** · best-practices · verdict **C** · `Runtime/Unity/UnityTempFileManager.cs:229` · also reported as unity-runtime-12, unity-runtime-13

- **Evidence.** AudioClipHandler.Configure replaces _decodeLimiter and disposes the old one when MaxConcurrentDecodes changes (AudioClipHandler.cs:148-155); AsAudioClipAsync captured the old instance (190) and calls limiter.Release() in finally (216-219). SemaphoreSlim.Release throws ObjectDisposedException after Dispose and pending WaitAsync callers are never completed. UnityTempFileManager.Configure does the same with _ioLimiter (UnityTempFileManager.cs:157-162), and WriteBytesAsync reads the field twice: await _ioLimiter.WaitAsync (229) and _ioLimiter.Release() (263); ProcessDeleteQueueAsync likewise (319, 334). ResetStaticState repeats both swaps (AudioClipHandler.cs:115-119, UnityTempFileManager.cs:125-129). AudioPipelineV2Tests only reconfigures while idle.
- **Failure scenario.** A settings screen calls AudioClipHandler.Configure(new AudioClipPipelineOptions { MaxConcurrentDecodes = 4, TempMaxConcurrentIo = 4 }) while clips are loading. A load that already decoded its AudioClip hits limiter.Release() on the disposed semaphore: ObjectDisposedException replaces the result and the created clip is never destroyed or returned. Loads waiting in WaitAsync on the old limiter hang forever. A WriteBytesAsync that waited on the old I/O limiter releases the new, full one: SemaphoreFullException escapes the finally and the load fails after the file was written.
- **Fix direction.** Never dispose a limiter that may be held: capture the instance in a local for wait and release, let replaced semaphores be collected, or implement resizing by adjusting permits on one long-lived semaphore.
- **Verifier.** AudioClipHandler.Configure swaps and disposes _decodeLimiter when MaxConcurrentDecodes changes (AudioClipHandler.cs:148-155); AsAudioClipAsync captured the old instance (:190) and calls limiter.Release() in finally (:216-219), which throws ObjectDisposedException on a disposed SemaphoreSlim, and waiters parked in WaitAsync (:192) on the disposed instance are never released unless their token fires. UnityTempFileManager.Configure does the same with _ioLimiter (UnityTempFileManager.cs:157-162); WriteBytesAsync reads the field at wait (:229) and again at release (:263), ProcessDeleteQueueAsync likewise (:319, :334), so after a swap the release goes to the new, full semaphore (SemaphoreFullException) and the old permit is never returned. ResetStaticState repeats both swaps (AudioClipHandler.cs:115-119, UnityTempFileManager.cs:125-129). No lock or generation check covers in-flight holders; AudioPipelineV2Tests reconfigures only while idle (:16, :36). Needs Configure with a changed limit while loads are in flight, an edge case.

### unity-design-15: UnityExtensions.DownloadTo*Async and PathSafety re-implement TurboHTTP.Files.FileDownloader with diverged behaviour: the whole body is buffered in memory and capped at 100 MB

**medium** · architecture · verdict **C** · `Runtime/Unity/UnityExtensions.cs:127`

- **Evidence.** DownloadToUnityPathAsync calls client.Get(url).SendBufferedAsync (127) and hands the buffered body to PathSafety.WriteAtomicAsync (131-136); multi-segment bodies are copied once more by ToBodyMemory (146-155). Buffered responses are capped by UHttpClientOptions.MaxBufferedResponseBodySize, default 100 MB (Runtime/Core/UHttpClientOptions.cs:107-123). Runtime/Files/FileDownloader.cs streams to destinationPath + '.part' with resume, validators and incremental SHA-256 and throws ChecksumMismatchException (86-141, 591-593, 707-735). PathSafety has its own root containment (69-95), its own temp naming ('.tmp-<guid>', 307-313), validates the checksum only after the temp file is written (142-143) and reports a mismatch as InvalidOperationException (211-212). Documentation~/Modules/Unity.md recommends DownloadToPersistentDataAsync for 'pack.zip' and for AssetBundles 'or FileDownloader' as equivalents. The duplication exists because Unity may reference only Core.
- **Failure scenario.** An app follows the docs and downloads a 300 MB asset pack with DownloadToPersistentDataAsync: the request fails at the 100 MB buffered-body limit after downloading 100 MB; with the limit raised, 300 MB (twice that for a multi-segment body) sits in managed memory on a phone before the first byte reaches disk, there is no resume, and a checksum mismatch surfaces as a different exception type than the Files module uses.
- **Fix direction.** Keep only path resolution (ResolvePathWithinRoot against persistentDataPath/temporaryCachePath) in TurboHTTP.Unity and route the transfer through one streaming implementation: either a streaming-to-file primitive in Core that both modules use, or a documented Unity-to-Files reference exception. Until then document the buffering and the size limit on the Unity helpers and make PathSafety internal.
- **Verifier.** Traced. DownloadToUnityPathAsync buffers the whole body with client.Get(url).SendBufferedAsync (Runtime/Unity/UnityExtensions.cs:127) and passes it to PathSafety.WriteAtomicAsync (131-136); ToBodyMemory copies a multi-segment body again with body.ToArray() (146-155). Buffered bodies are capped at 100 MB by default and a larger body fails the request (Runtime/Core/UHttpClientOptions.cs:107-123). PathSafety writes the temp file first and validates the SHA-256 afterwards (PathSafety.cs:142-143), throws InvalidOperationException on mismatch (211-212), uses '.tmp-<guid>' naming (307-313) and is a public static class (36). Runtime/Files/FileDownloader.cs streams to '.part' with resume and ChecksumMismatchException (34, 55, 86-124). Documentation~/Modules/Unity.md:49-57 shows DownloadToPersistentDataAsync for 'pack.zip' and for AssetBundles '(or FileDownloader)' with no word about buffering or the size cap; only QuickStart.md:167 warns about buffered responses in general. TurboHTTP.Unity.asmdef references only TurboHTTP.Core, but that does not force buffering: Core already has SendStreamingAsync, so the helper could stream to the temp file without a Files reference. No guard, test or issue refutes it; #122 (AssetBundle handler) does not cover it.

### unity-design-16: UHttpClient.WebSocket(...) copies three client options and silently ignores the rest, including the proxy; it also leaks the client on a failed connect and hides the bridge type

**medium** · architecture · verdict **C** · `Runtime/Unity.WebSocket/UnityWebSocketExtensions.cs:44`

- **Evidence.** BuildWebSocketOptions (44-54) copies TlsBackend, AllowCleartext and DefaultHeaders from client.GetOptionsSnapshot(). UHttpClientOptions.Proxy (Runtime/Core/UHttpClientOptions.cs:76) is not mapped to WebSocketConnectionOptions.ProxySettings (Runtime/WebSocket/WebSocketConnectionOptions.cs:115), nor are timeouts. WebSocket(Uri) creates the bridge and client and awaits ConnectAsync without try/finally (38-41), unlike UnityWebSocketClient which disposes on failure (UnityWebSocketClient.cs:404-409). The return type is Task<IWebSocketClient>, so ReceiveAsCoroutine, OnMessageDropped, OnReconnecting/OnReconnected need a downcast. The Uri overload is async, so a null client faults the task while the string overload validates the URL synchronously (19-23, 33-36); neither method has XML docs.
- **Failure scenario.** An app configured with options.Proxy (corporate network, or a privacy proxy) calls client.WebSocket("wss://..."): the WebSocket connects directly, bypassing the proxy the HTTP requests of the same client use, and fails where direct egress is blocked. Each failed connect leaves an undisposed WebSocketClient behind.
- **Fix direction.** Map every option that has a WebSocket counterpart (proxy, cleartext, TLS backend, DNS/connect timeouts) or accept an Action<WebSocketConnectionOptions> so the caller sees what is applied; dispose the bridge when ConnectAsync throws; return UnityWebSocketBridge; validate arguments synchronously in a non-async wrapper.
- **Verifier.** Main claim holds, one sub-claim is wrong. BuildWebSocketOptions copies only TlsBackend, AllowCleartext and DefaultHeaders (Runtime/Unity.WebSocket/UnityWebSocketExtensions.cs:44-54); UHttpClientOptions.Proxy (Runtime/Core/UHttpClientOptions.cs:76) is never mapped to WebSocketConnectionOptions.ProxySettings (WebSocketConnectionOptions.cs:115, default None), and RawSocketWebSocketTransport.cs:84 uses only that setting, so a client configured with a proxy opens its WebSocket directly. Documentation~/Modules/WebSocket.md:20 says the helper 'inherits the TLS backend and cleartext setting', so the narrow mapping is documented, but the proxy bypass is not warned about and the DefaultHeaders copy is not mentioned. Also confirmed: both overloads lack XML docs (14, 28), the Uri overload is async so a null client faults the task while the string overload throws synchronously for a bad URL (19-25 vs 33-36), and the return type IWebSocketClient hides UnityWebSocketBridge members (ReceiveAsCoroutine, OnMessageDropped, OnReconnecting/OnReconnected at UnityWebSocketBridge.cs:41-51, 157). Refuted part: 'leaks the client on a failed connect'. WebSocketClient.ConnectAsync catches the failure and runs CleanupAfterFailedConnectAsync (Runtime/WebSocket/WebSocketClient.cs:186-192, 595-631), which disposes the connection, the owned transport, the queue and the listener CTS; the bridge holds only event subscriptions on that same client (UnityWebSocketBridge.cs:53-70) and no static registration, so the undisposed pair holds no socket and is collectable. The missing try/finally at 38-41 is a hygiene gap, not a resource leak.

### unity-design-17: Background replay is half-implemented: expired requests are queued with no consumer, the only drain API is undocumented, and the interceptor never disposes what it queued
