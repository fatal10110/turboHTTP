# HTTP/1.1: review findings

Scope: request serializer, response parser, body sources, chunked coding, Expect: 100-continue. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (20 findings, 14 files read in full). The HTTP/1.1 slice is functionally careful (shared outgoing field validator, transport-owned framing, bounded lines, consistent ConfigureAwait(false), defensive option clone) and has no reflection, LINQ, Regex or heavy dependency. Its main design risk is duplication that has already diverged: the stale-connection retry exists in a direct and a proxy copy (the proxy copy lacks the first-byte watchdog and the fresh-socket retry), CONNECT has its own second head parser and a second handshake implementation in the WebSocket transport, list/whitespace parsing exists in six scanners, and received fields are validated by three unrelated routines for HTTP/1.1 headers, HTTP/1.1 trailers and HTTP/2. The error contract is implicit: serializer and parser throw BCL exception types that three mappers and one message-string match classify, so caller errors (short body, trailers on a known-length body) surface as retryable NetworkError or Unknown. Structurally, RawSocketTransport (2,434 lines) owns the Expect/417/stale-retry/CONNECT state machines, which makes them testable only through sockets, and the body decoder is welded to ConnectionLease. For build size, link.xml preserves RawSocketTransport with preserve=all and the transport constructs the HTTP/2 manager unconditionally, so the whole HTTP/1.1 + HTTP/2 stack (and about 570 lines of unreachable code) is rooted in every build, including WebSocket-only and SslStream-only (no ALPN) configurations. Behavioural defects already reported by the protocol and runtime lenses for this domain (empty-body Content-Length, Connection: close, leftover bytes after a response, char.IsWhiteSpace trimming, Abort during a pending read) are referenced here only as symptoms of the structural issues, not repeated.

**RFC conformance, protocol implementation, security** (21 findings, 14 files read in full). The HTTP/1.1 slice is in good shape on the classic desync vectors: framing headers are transport-owned on the request side, Transfer-Encoding/Content-Length precedence, duplicate/invalid Content-Length, EOF in every parser state, 1xx/101/HEAD/204/304 handling, chunk-size overflow, header-line/trailer byte caps and the Expect: 100-continue early-final-response rules are implemented and tested. The main remaining risks are on connection reuse and interop rather than parsing: bytes that follow a complete response in the reader buffer are silently dropped and the connection is pooled, a request that carried 'Connection: close' is still reused, the non-Expect send path never looks for an early error response while uploading, and bodiless POST/PUT/PATCH go out without Content-Length (the caller cannot add it). On the receive side the parser deviates from the RFC in three places that affect real data: obs-fold is rejected although a user agent MUST unfold it, field values are trimmed with char.IsWhiteSpace (which eats the obs-text bytes 0x85/0xA0 and tolerates VT/FF around Content-Length), and NUL/bare CR inside field values are passed to the application. ConnectReplyReader is noticeably more lenient than the main parser and does not skip 1xx. Nothing found here is critical; no open issue tracks any of these.

**performance, resource management, concurrency, platform compatibility** (19 findings, 14 files read in full). The HTTP/1.1 slice is in good shape on single-consumer paths: lease ownership is exactly-once (CAS terminal state plus the lock-guarded ConnectionLease), the head and body reads are raced against their token without trusting Mono/IL2CPP to end a socket read, abandoned buffers stay out of the pool, the over-read is handed from head parse to body source through one shared reader, and no clause ladder in the slice is exposed to the IL2CPP filtered-catch nesting bug (#320). The main risk is that this safety is built on the assumption that reads and Abort/DisposeAsync are serialized by the caller, which Core's UHttpStreamingResponse/ResponseBodyStream do not do: a dispose from another thread during a pending read returns the reader's pooled buffer under a live socket read (non-cancellable token) or starts a second concurrent read on the same reader (DisposeAsync drain). Second, a completed body returns its connection to the pool while silently discarding any bytes the reader over-read past the message, which hides the desync signal the pool's Socket.Available check is meant to catch. On performance, the body read path has one real throughput bug (the reader-owned body buffer is sized by the first large read and caps every later read) plus per-fill/per-header allocations already tracked by #434/#120, three writes per request chunk, and CTS/timer churn in the default first-byte watchdog. The buffered ParseAsync path (ParsedResponse, ParsedResponsePool, DispatchOnStreamAsync) is production-dead and only exercised by tests.

## High (2)

### http1-protocol-02: POST/PUT/PATCH with an empty body are sent with neither Content-Length nor Transfer-Encoding, and a caller-set Content-Length: 0 is stripped

**high** · rfc-compat · verdict **C** · `Runtime/Transport/Http1/Http11RequestSerializer.cs:340` · RFC 9110 Section 8.6 · reviewer rated it medium

- **Evidence.** ResolveBodyWriteMode returns RequestBodyWriteMode.None for an empty buffered body and for Length <= 0 (Http11RequestSerializer.cs:215-234). AppendHeaders writes Content-Length only for KnownLength (340-345) and removes every caller Content-Length/Transfer-Encoding through IsFramingHeader (322, 509-513), independent of the method. Tests only assert the GET case (Http11SerializerTests.cs:500) and that caller framing headers are stripped (625-637); RawSocketTransportConnectionReuseTests.cs:92 sends 'POST /empty' this way.
- **Failure scenario.** client.Post(url).SendBufferedAsync() or a PUT with an empty body goes out as 'POST /x HTTP/1.1' with no Content-Length. Servers and gateways that require a length on methods that define content answer 411 Length Required (http.sys/IIS, S3-style PUT, several CDNs/WAFs), and the caller cannot work around it because headers.Set('Content-Length','0') is removed by the serializer.
- **Fix direction.** Emit 'Content-Length: 0' when the body is empty and the method is POST, PUT or PATCH (the methods HttpMethodExtensions.HasBody already names); keep omitting it for GET/HEAD/DELETE/OPTIONS. Add a serializer test per method.
- **Verifier.** Traced. EmptyRequestBody reports an empty buffered body (Runtime/Core/UHttpRequestBody.cs:257-269), ResolveBodyWriteMode returns None for it and for Length <= 0 (Http11RequestSerializer.cs:215-234), AppendHeaders emits Content-Length only for KnownLength (340-345) and drops any caller Content-Length/Transfer-Encoding via IsFramingHeader (322, 509-513) for every method. No method check exists anywhere in the serializer. Tests assert only the GET case (Http11SerializerTests.cs:502-510) and that a caller 'Content-Length: 0' is stripped (625-637). RFC 9110 Section 8.6: a user agent SHOULD send Content-Length when the method defines content, 'even when the value is 0' for POST. Raised to high: servers that answer 411 to a length-less POST/PUT (http.sys/IIS, S3 PUT) reject every empty-body POST/PUT/PATCH and the caller has no workaround because the header is removed.

### http1-runtime-01: Abort()/Dispose from another thread during a pending body read returns the reader's pooled buffers while the socket read still targets them, and leaves the read to be ended by the platform alone

**high** · concurrency · verdict **C** · `Runtime/Transport/Http1/Http11ResponseParser.cs:1100`

- **Evidence.** Http11ResponseBodySource.cs:12-13 states that reads and disposal/abort are 'expected to be serialized by the caller', but the only caller does not serialize: UHttpStreamingResponse.Dispose -> StartBodyDispose calls _bodySource.Abort() whenever EOF was not reached (Runtime/Core/UHttpStreamingResponse.cs:157-159), ResponseBodyStream.Dispose -> AbortBody (ResponseBodyStream.cs:180-186, UHttpStreamingResponse.cs:142-147); neither checks for an in-flight ReadAsync. Abort -> CloseBody (Http11ResponseBodySource.cs:254-258, 676-684) calls _reader.Dispose() BEFORE _lease.Dispose(). BufferedStreamReader.Dispose (Http11ResponseParser.cs:1090-1111) keeps buffers out of the pool only when _raceRead is pending or _bodyReadState != Idle. A body-phase read whose token cannot be cancelled never leaves Idle: ReadBodyAsync returns 'new ValueTask<int>(pending)' at 1415-1417 without touching _bodyReadState. In streaming mode the transport token is CancellationToken.None (RawSocketTransport.cs:1826-1830), so a consumer that reads with no token (ResponseBodyStream.Read passes CancellationToken.None at ResponseBodyStream.cs:62; ReadAsync(buffer) / CopyToAsync default token) takes this path. Every chunk-size line, chunk CRLF, trailer line and every read with a destination below 4096 bytes goes through FillBufferAsync into the reader's _buffer (1364-1376). So Dispose runs ByteArrayPool.Return(_buffer) at 1108 while _stream.ReadAsync(_buffer, ...) is still pending. For a raced (cancellable) pending read the buffers are abandoned correctly, but Abort does not complete the pending ValueTask: only the read's own completion or the token does (1431-1502). architecture.md lists this contract explicitly ('Never return a buffer while an OS operation or another thread may still touch it ... HTTP/2 abort vs read').
- **Failure scenario.** Unity app streams a chunked response (SSE or a chunked download) on a background continuation with 'await stream.ReadAsync(buf)' (no token); the main thread calls response.Dispose() in OnDestroy while the read is pending in a chunk-size/CRLF refill. Abort returns the 4 KB _buffer to ArrayPool.Shared and only then shuts the socket down. Bytes that were already queued in the kernel (data arriving in the same instant, which is the normal state of an active download) are still delivered to the pending recv after shutdown and are written into an array the pool can hand out again at once (the next BufferedStreamReader on that thread rents the same 4096 bucket): bytes of one response land in another request's header/body buffer. Independently, the pending read is completed only if the platform ends it; the code base documents that IL2CPP does not always do that after shutdown/close (#293, #384: 53 of 600 abandons on the iOS simulator), in which case the consumer's ReadAsync task never completes when it has no token.
- **Fix direction.** Make the reader own an in-flight flag for every body-phase stream read (not only raced ones) and abandon the buffers in Dispose whenever a read is in flight. Arm the existing IValueTaskSource race for non-cancellable reads too, and let CloseBody/Abort win it (CAS Pending->Abandoned, fail the pending read with ObjectDisposedException) instead of relying on the socket to end the read. Add a test with AbandonedReadStream: Abort during a pending CancellationToken.None read must complete the read and must not return the read target to the pool.
- **Verifier.** Traced. Core does not serialise abort against reads: UHttpStreamingResponse.Dispose -> StartBodyDispose calls _bodySource.Abort() whenever EOF was not reached (Runtime/Core/UHttpStreamingResponse.cs:155-160), ResponseBodyStream dispose -> AbortBody (ResponseBodyStream.cs:180-186; UHttpStreamingResponse.cs:142-148). Streaming mode passes CancellationToken.None as the transport token (RawSocketTransport.cs:1826-1830) and ResponseBodyStream.Read passes None (ResponseBodyStream.cs:62), so GetEffectiveReadToken returns a non-cancellable token (Http11ResponseBodySource.cs:640-641). Every chunk-size/CRLF/trailer read and every read with a destination under 4096 bytes goes FillBufferAsync -> ReadBodyAsync(_buffer) (Http11ResponseParser.cs:1364-1376), which returns 'new ValueTask<int>(pending)' at 1415-1417 without leaving BodyReadIdle. CloseBody then runs _reader.Dispose() before _lease.Dispose() (Http11ResponseBodySource.cs:676-684) and Dispose returns _buffer to the shared pool because _raceRead is null and the state is Idle (1099-1110), while the stream read still targets it. HoldingNetworkStream deliberately lets a read pending under dispose end later (Tcp/HoldingNetworkStream.cs:12-17), so the read can still complete with data into a pooled array; this breaks the rule in architecture.md:109-110. The window for another renter to be hit is narrow, and the 'read never completes without a token' part depends on the platform (#293/#384 behaviour), but the ownership violation itself is static. No test aborts during a pending non-cancellable body read.

## Medium (9)

### http1-design-02: Serializer and parser signal failures with BCL exception types that three separate mappers and one message-string match classify, so caller errors become retryable NetworkError or Unknown

**medium** · best-practices · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:805`

- **Evidence.** The HTTP/1.1 layer throws FormatException / IOException / NotSupportedException / InvalidOperationException (e.g. Http11ResponseParser.cs:274, 286, 518; Http11RequestSerializer.cs:249, 391) and three sites translate them independently: MapDispatchAttemptFailure (RawSocketTransport.cs:794-828), the five-clause ladder in Http11ResponseBodySource.ReadAsync (:155-226; the IOException and SocketException clauses are identical, and the 'Malformed HTTP response:' / 'Unsupported HTTP response:' / 'Request timed out after' strings repeat RawSocketTransport.cs:813, 818, 835) and ConnectReplyReader (:208-214, 310-313). Stale-connection detection is IsStaleReusedConnectionFailure = ex is IOException || SocketException || a FormatException whose Message equals 'Empty HTTP status line' (:356-387; the parser comment at Http11ResponseParser.cs:269-271 and Http11ResponseParserStrictnessTests.cs:70 pin the text). Because the single catch in DispatchAttemptAsync (:746) covers request serialization and response parsing alike, the type cannot tell who failed: (a) the serializer's own IOException 'Request body ended before the declared Content-Length was fully produced' (Http11RequestSerializer.cs:391) passes IsStaleReusedConnectionFailure and is then mapped to NetworkError (:805-806), which UHttpError.IsRetryable treats as retryable (Runtime/Core/UHttpError.cs:72-74); (b) ValidateTrailerCompatibility's InvalidOperationException (Http11RequestSerializer.cs:249; WithRequestTrailers on a known-length body, which HTTP/2 accepts) falls to the default arm and becomes UHttpErrorType.Unknown (:827-828) while the sibling caller error HttpFieldValidationException gets InvalidRequest (:822-826); (c) a FormatException or NotSupportedException thrown by a caller's body stream or factory is reported as 'Malformed/Unsupported HTTP response' (:809-818); (d) an ObjectDisposedException from a disposed transport (:435-436) escapes DispatchAsync as a raw exception because its catch only handles UHttpException and OperationCanceledException (:178-187). No test covers (a); Http11SerializerTests.cs:296-320 assert the raw InvalidOperationException at serializer level only.
- **Failure scenario.** PUT with WithBodyFactory(factory, contentLength: 100) whose stream yields 50 bytes, on a reused connection: attempt 1 writes the head and 50 bytes, throws IOException, is classified as a stale connection (TransportRetryStale), the connection is destroyed, a new one is dialled and the partial upload is sent again; the caller then gets NetworkError, which a Retry interceptor replays again. A caller bug is reported as a network failure and multiplied into several partial uploads. Separately, request.WithBody(bytes).WithRequestTrailers(...) fails with Unknown on HTTP/1.1 only.
- **Fix direction.** Give the HTTP/1.1 layer its own internal failure type with a kind (ClosedBeforeStatusLine, MalformedResponse, UnsupportedFraming) and a separate type for request-body/request-shape faults, and map them in one shared function used by the dispatch path, the body source and the CONNECT reader. Classify body-source and request-shape failures as non-retryable InvalidRequest and never as stale.
- **Verifier.** Sub-claims (a)-(c) traced, (d) rejected. (a) The serializer's own IOException for a short body (Http11RequestSerializer.cs:389-393) passes IsStaleReusedConnectionFailure (RawSocketTransport.cs:356-363, type test only) and, for an idempotent replayable request on a reused lease, triggers the stale retry (665-714) and a second partial upload, then maps to NetworkError (805-806), which UHttpError.IsRetryable treats as retryable (Runtime/Core/UHttpError.cs:69-74). No test covers it (the message appears only in the serializer and Http2Connection.Send.cs:283). (b) ValidateTrailerCompatibility throws InvalidOperationException (Http11RequestSerializer.cs:249); neither WithRequestTrailers (UHttpRequest.cs:292-307) nor SetRequestTrailers (UHttpRequestBody.cs:47-63) checks the body length, and the default arm maps it to Unknown (827-828) while HttpFieldValidationException gets InvalidRequest (822-826). (c) The single catch at 746 covers serialization and parsing, so a FormatException/NotSupportedException from a caller body stream is reported as a malformed/unsupported response (809-818). Stale detection does rest on the message string 'Empty HTTP status line' (380-387). (d) ObjectDisposedException from a disposed transport (435-436) escaping is the normal .NET contract, not a defect.

### http1-design-04: Received header and trailer fields are validated by three unrelated routines (HTTP/1.1 header, HTTP/1.1 trailer, HTTP/2) that accept different inputs

**medium** · architecture · verdict **C** · `Runtime/Transport/Http1/Http11ResponseParser.cs:741` · RFC 9110 Sections 5.5 and 6.5.1; RFC 9113 Section 8.2.1

- **Evidence.** Outgoing fields share one validator (HttpFieldValidator, called from Http11RequestSerializer.cs:517-518 and Http2Connection.Send.cs:457, 472). Incoming fields do not: (1) ParseResponseHeaderLine (Http11ResponseParser.cs:698-723) checks that the name is a token and does nothing to the value; (2) AddResponseTrailer (:741-759) uses a different, lenient line parser (TryParseHeaderLine :725-739 trims the name, so 'X-A : v' is accepted as a trailer but rejected as a header), silently drops bad names and TrailerFieldValidator-prohibited names, yet throws FormatException for a CR in the value (:752, 949-953), which fails the whole response although the comments at :939-940 and Http11ResponseBodySource.cs:428-429 say invalid trailers are skipped/ignored (Http11ResponseParserTests.cs:227 pins the throw); (3) HTTP/2 GetMalformedResponseFieldReason (Runtime/Transport/Http2/Http2Connection.ReadLoop.cs:757-787) rejects NUL/CR/LF and leading/trailing SP/HT in values with a stream error, and HTTP/2 trailers (:694 stream.AppendTrailers) never pass through TrailerFieldValidator.IsProhibitedResponseTrailer, whose only caller is Http11ResponseParser.cs:754. TrailerFieldValidator and HttpFieldValidator sit in Transport/Internal, but there is no counterpart for received fields.
- **Failure scenario.** The same origin answering over HTTP/1.1 and HTTP/2: a trailer 'content-length: 5' or 'authorization: x' is returned by GetTrailersAsync on HTTP/2 and dropped on HTTP/1.1; a field value containing NUL or a bare CR is a stream error on HTTP/2, accepted verbatim as an HTTP/1.1 header and a fatal 'Malformed HTTP response' as an HTTP/1.1 trailer. Code that consumes trailers (status trailers, cache commit) behaves differently per negotiated protocol.
- **Fix direction.** Introduce one internal ResponseFieldValidator in Transport/Internal (name token, value octet rules, prohibited-trailer policy returning Accept / Drop / Reject) and call it from the HTTP/1.1 header path, the HTTP/1.1 trailer path and the HTTP/2 header and trailer paths; decide drop-versus-reject once and correct the comments.
- **Verifier.** Traced all three paths. (1) HTTP/1.1 headers: ParseResponseHeaderLine (Http11ResponseParser.cs:698-723) validates only the name; the line reader splits on LF only and DecodeLineFromBuffer strips just the terminating CR/LF (:1515-1533), so a bare CR or NUL inside a field value reaches HttpHeaders verbatim. RFC 9110 Section 5.5 requires reject-or-replace for CR/LF/NUL, so this is a real gap, not only an inconsistency. (2) HTTP/1.1 trailers: AddResponseTrailer (:741-759) uses the lenient TryParseHeaderLine (:725-739, trims the name so 'X-A : v' passes), silently drops bad and prohibited names, but ValidateHeaderValue (:949-953) throws FormatException for CR, failing the whole response; the comments at :939-940 and Http11ResponseBodySource.cs:428-429 say such trailers are skipped. The throw is pinned by tests (Tests/Runtime/Transport/Http11ResponseParserTests.cs:227-235; the cited path Tests/.../Http1/Http11ResponseParserTests.cs does not exist, the file is one directory up) and Http11ResponseBodySourceTests.cs:168. (3) HTTP/2: GetMalformedResponseFieldReason (Http2Connection.ReadLoop.cs:757-787) rejects NUL/CR/LF and edge whitespace with a stream error, and trailers go straight to stream.AppendTrailers (:694 -> Http2Stream.cs:452-455 -> SetTrailers) with no prohibited-name filter; TrailerFieldValidator.IsProhibitedResponseTrailer has a single caller (Http11ResponseParser.cs:754). No shared received-field validator exists in Transport/Internal. The H2 trailer difference itself is harmless under RFC 9110 Section 6.5.1 (trailers are kept separate from headers), so medium rests on the H1 header-value gap and the protocol-dependent behaviour. No open issue tracks it.

### http1-design-06: RawSocketTransport (2,434 lines) owns the HTTP/1.1 exchange state machines, so they cannot be exercised without a pool and sockets, and the body decoder is welded to ConnectionLease

**medium** · architecture · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:2018`

- **Evidence.** HTTP/1.1-specific logic that is private to RawSocketTransport instead of living in Http1/: the Expect: 100-continue state machine (SendOnLeaseWithExpectContinueAsync, WaitForAbortedReadAsync, ReadExpectContinueFinalHeadAsync, CompleteExpectContinueHead, TrySendRequestBodyAsync and helpers, :2018-2364, about 350 lines), the 417 repeat (:1640-1669, 531-541), the stale-connection policy and first-byte watchdog (:284-300, 344-395, 1981-2016), the forward-proxy Basic-407 interception and drain (:1671-1763, 1809-1824) and CONNECT (:1429-1568), next to registration, cleartext policy, HTTP/2 routing/replay and error mapping. Nothing in Http1/ composes 'send the request, maybe wait for 100, read the head'; the only stream-level seam, DispatchOnStreamAsync(Stream ...) (:1846), is unreferenced. Visible consequences: the direct and proxy retry blocks are copies that diverged (http1-design-01); HTTP/2 re-implements the Expect wait and lacks the 417 repeat (open #391); Http11ResponseBodySource fuses the chunked / length / close decoders with lease return, drain policy and timeout mapping, so the fuzz target and the unit tests must create a real Socket, a PooledConnection and a ConnectionLease with a null pool and a SemaphoreSlim(0,1) to decode bytes from a MemoryStream (Tools~/fuzz/Targets.cs:110-124; Tests/Runtime/Transport/Http1/Http11ResponseBodySourceTests.cs:37-40, 246-249); and a BufferedStreamReader is created per response (:1941, 1949, 2026) although its read-ahead belongs to the connection, which is the root of the 'bytes after a complete response are discarded and the connection pooled' defect the protocol and runtime lenses report. Open #182 lists four oversized files, the largest 929 lines; this file and Http11ResponseParser.cs (1,610 lines) are not on it.
- **Failure scenario.** Every Expect / 417 / stale-retry behaviour needs a loopback TcpListener test (RawSocketTransportTests.cs is 2,918 lines), so interleavings such as 'the 100 arrives while the body send fails' are reachable only through timing; a fix in one copy of the retry block does not reach the other (this has already happened); the streaming decoder cannot be reused or unit-tested without pool types.
- **Fix direction.** Extract an Http11Exchange in Http1/ that takes (Stream, reader, request, options) and returns a ParsedResponseHead (one-shot send, Expect: 100-continue, 1xx handling), a stale-retry policy object, and split Http11ResponseBodySource into a pure decoder over the reader plus a small owner that settles the lease through a callback; make the reader a per-connection object. Do pure moves first and add both files to #182.
- **Verifier.** Structural claims check out. RawSocketTransport.cs is 2,434 lines and privately owns the Expect: 100-continue machine (SendOnLeaseWithExpectContinueAsync :2018 through TrySendRequestBodyAsync :2338), the 417 repeat (:1642-1669), stale-connection policy and first-byte watchdog (:284-395, :1981), forward-proxy 407 drain (:1695-1763) and CONNECT (:1429-1568) next to registration, HTTP/2 routing and error mapping. DispatchOnStreamAsync (:1846), SendOnStreamAsync (:2366) and EmitParsedResponseAsync (:1587) have no caller in Runtime, Tests or Tools~ (rg), so Http11ResponseParser.ParseAsync is reached at runtime only from dead code (tests and the fuzz target call it directly). Http11ResponseBodySource does need a real Socket + PooledConnection + ConnectionLease(null, SemaphoreSlim(0,1)) to decode a MemoryStream (Tools~/fuzz/Targets.cs:109-124; Tests/Runtime/Transport/Http1/Http11ResponseBodySourceTests.cs:37-40). A BufferedStreamReader is created per response (:1949, :2026, and inside ParseHeadAsync at Http11ResponseParser.cs:217). RawSocketTransportTests.cs is 2,918 lines. #182 lists four other files (PluginContext, MainThreadDispatcher, UHttpClient, DecompressionHandler), so this is not tracked; #391 confirms the HTTP/2 417 gap cited as a consequence. This is a maintainability/testability finding with no direct runtime failure of its own; I did not re-trace the sibling claims it leans on (http1-design-01 diverged retry copies, discarded read-ahead bytes).

### http1-design-09: HTTP/1.1 response limits are private constants with no option, and they disagree with the HTTP/2, CONNECT and WebSocket limits for the same thing

**medium** · best-practices · verdict **C** · `Runtime/Transport/Http1/Http11ResponseParser.cs:156` · RFC 9112 Section 2.3; RFC 9110 Section 5.4

- **Evidence.** MaxHeaderLineLength = 8192, MaxTotalHeaderBytes = 102400, MaxTotalTrailerBytes = 32 KB and Max1xxResponses = 10 (Http11ResponseParser.cs:156-160) and the chunk-size line cap of 256 (Http11ResponseBodySource.cs:16, Http11ResponseParser.cs:866) are compile-time constants; RawSocketTransport passes no limit to the parser and neither StreamingOptions nor ConnectionPoolOptions has an HTTP/1.1 header setting. HTTP/2 exposes Http2Options.MaxHeaderListSize (Runtime/Core/Http2Options.cs:106; default 64 KB, Runtime/Transport/Http2/Http2Settings.cs:18), CONNECT replies use 8 KB per line and 16 KB per block (ConnectReplyReader.cs:73-76) and the WebSocket handshake 8 KB in total (Runtime/WebSocket/WebSocketHandshakeValidator.cs:114). An over-limit head is a FormatException mapped to NetworkError 'Malformed HTTP response: HTTP header line exceeds maximum length' (RawSocketTransport.cs:809-813), which is retryable.
- **Failure scenario.** An origin that sends one 10 KB field line (a large Content-Security-Policy, a Set-Cookie carrying a signed session, a long Link or Report-To) works over HTTP/2 (64 KB list limit, configurable) and fails on every attempt over HTTP/1.1 with a retryable NetworkError and no way to raise the limit; conversely 80 KB of small headers pass on HTTP/1.1 and are refused on HTTP/2 by default. The application sees protocol-dependent failures it cannot configure away.
- **Fix direction.** Add HTTP/1.1 limits to the transport options (max field-line bytes, max header bytes, max trailer bytes, max interim responses), default them consistently with Http2Options.MaxHeaderListSize, pass them to the parser and body source, and report an over-limit head as a non-retryable error.
- **Verifier.** Constants are compile-time and unreachable from options: MaxHeaderLineLength 8192, MaxTotalTrailerBytes 32 KB, MaxTotalHeaderBytes 102400, Max1xxResponses 10 (Http11ResponseParser.cs:156-160), chunk-size line 256 (Http11ResponseBodySource.cs:16; Http11ResponseParser.cs:866). The head parser applies them directly (:272, :282, :293-295) and no Core option carries an HTTP/1.1 header limit (rg for MaxHeader in Runtime/Core finds only Http2Options.MaxHeaderListSize, Http2Options.cs:106; default 64 KB at Http2Settings.cs:18). CONNECT uses 8 KB/16 KB (ConnectReplyReader.cs:73-76), the WebSocket handshake 8 KB (WebSocketHandshakeValidator.cs:114). An over-limit line throws FormatException('HTTP header line exceeds maximum length') (:1163, :1177, :1529), mapped to NetworkError 'Malformed HTTP response: ...' (RawSocketTransport.cs:809-813), and UHttpError.IsRetryable returns true for NetworkError (UHttpError.cs:72-74), so the retry module repeats a deterministic failure. Scenario holds: a single field line over 8,192 bytes passes on HTTP/2 (64 KB list, configurable) and fails every time on HTTP/1.1 with no way to raise the limit; the reverse case (about 80 KB of small fields) passes on HTTP/1.1 and is rejected on HTTP/2 by default (ReadLoop.cs:610-620). 8 KB per line meets the RFC 9112 Section 2.3 recommendation of at least 8000 octets, so this is a configurability/consistency defect, not a protocol violation; lines that long are uncommon but occur (large CSP, Link, Report-To). No open issue tracks it (#121 covers other client options).

### http1-protocol-03: A connection is returned to the pool after a request that carried 'Connection: close' whenever the response does not echo close

**medium** · rfc-compat · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:1832` · RFC 9112 Section 9.6

- **Evidence.** The serializer forwards a caller Connection header verbatim (Http11RequestSerializer.cs:320-337; keep-alive is only auto-added when none is set, 359-360). Reuse is decided only from the response: Http11ResponseParser.IsKeepAlive (Http11ResponseParser.cs:598-644) -> ParsedResponseHead.KeepAlive -> Http11ResponseBodySource._keepAlive (Http11ResponseBodySource.cs:61) -> CompleteBody calls _lease.ReturnToPool() (667-671). DispatchOnLeaseAsync (RawSocketTransport.cs:1798-1840) never looks at the request's Connection field; rg for 'close' in Runtime/Transport finds only the response parser and ConnectReplyReader.
- **Failure scenario.** Caller sets 'Connection: close' (to force a fresh connection per call, or behind a load balancer that needs it). Server answers 'HTTP/1.1 200 OK, Content-Length: 2' without a Connection field and then closes, as the RFC tells it to. The client pools the connection; the next request is written into a socket the server is closing. A non-idempotent POST whose bytes were committed cannot be retried (CanRetryHttp11RequestAfterTransportFailure, 284-300) and fails with NetworkError. If the server does not close, the client keeps using a connection it promised to close.

### http1-protocol-04: Bytes that follow a complete response in the reader buffer are silently discarded and the connection is pooled as clean

**medium** · security · verdict **C** · `Runtime/Transport/Http1/Http11ResponseBodySource.cs:660` · RFC 9112 Section 9.3 (persistence requires a self-defined message length on both sides) · also reported as http1-runtime-03

- **Evidence.** BufferedStreamReader.FillBufferAsync reads up to the whole 4 KB buffer regardless of message framing (Http11ResponseParser.cs:1364-1399), in the head phase and for small body reads (1331-1338). When the body completes, CompleteBody disposes the reader and calls _lease.ReturnToPool() (Http11ResponseBodySource.cs:660-674); for HEAD/204/304/Content-Length: 0 this happens in the constructor (82-86). BufferedStreamReader.Dispose (1090-1111) returns the buffer without checking _end > _start, and the reader exposes no 'has buffered data' query. The same happens after a drained proxy 407 (RawSocketTransport.cs:1798 'using var head' then CompleteLeaseDispatch -> ReturnToPool, 1701-1703). The only later guard is TcpConnectionPool.HasUnexpectedData (Runtime/Transport/Tcp/TcpConnectionPool.cs:802-808), which looks at Socket.Available, i.e. kernel bytes only; its own comment says it cannot see plaintext already buffered in the TLS stream.
- **Failure scenario.** A peer (misbehaving origin that sends a body on a HEAD/304 response, an origin with a header-injection bug, or a desynchronised intermediary) sends response A followed by extra bytes X in the same read. A is delivered, the part of X that reached the reader buffer is thrown away, and the connection is reused. Whatever part of X was not in that buffer (still in transit, or sitting decrypted inside the TLS stream where Socket.Available is 0) is parsed as the status line/response of the next, unrelated request on that connection: either a forged response is attributed to it, or it fails with 'Malformed HTTP response' and is not retried (FormatException is not a stale-connection failure).
- **Fix direction.** Give BufferedStreamReader a HasBufferedData property and make Http11ResponseBodySource.CompleteBody (and the proxy-407 drain path) dispose the lease instead of pooling it when unread bytes remain after the message end. Add a test: 'HTTP/1.1 200 OK, Content-Length: 1, body a' immediately followed by a second response in the same write must not leave a pooled connection.
- **Verifier.** Traced. Head-phase and framing reads fill the whole 4 KB reader buffer regardless of message length (Http11ResponseParser.cs FillBufferAsync 1364-1399, ReadAsync 1331). CompleteBody disposes the reader and pools the lease (Http11ResponseBodySource.cs:660-671; from the constructor for Empty/Content-Length 0 at 82-86). BufferedStreamReader.Dispose (1090-1111) returns the buffer without looking at _end > _start and the type has no buffered-data accessor (rg HasBuffered|Buffered finds none). Same for the drained 407 (RawSocketTransport.cs:1798, 1809-1823 -> CompleteLeaseDispatch 1701-1703). The only later guard, HasUnexpectedData, reads Socket.Available (TcpConnectionPool.cs:802-808) and its own comment says it cannot see plaintext buffered in the TLS stream. So leftover bytes split between the reader buffer and SslStream's decrypted record (or bytes still in flight) are attributed to the next request. Needs a misbehaving or injectable peer, so medium. No test with trailing bytes after a keep-alive response exists.

### http1-protocol-06: Field values and framing tokens are trimmed with char.IsWhiteSpace, which removes the obs-text bytes 0x85/0xA0 and accepts VT/FF/CR as optional whitespace

**medium** · rfc-compat · verdict **C** · `Runtime/Transport/Http1/Http11ResponseParser.cs:777` · RFC 9110 Sections 5.5, 5.6.3; RFC 9112 Section 6.3

- **Evidence.** TrimWhitespace (Http11ResponseParser.cs:777-793) uses char.IsWhiteSpace. Lines are decoded as Latin-1 (DecodeLineFromBuffer, 1532), so bytes 0x85 and 0xA0 become U+0085/U+00A0, both whitespace for char.IsWhiteSpace, as are 0x0B, 0x0C and 0x0D. It is applied to every header value (722), trailer names and values (736-737), the status code (686), Transfer-Encoding and Connection tokens (544, 613-614), and Content-Length is trimmed again with string.Trim() (578, 583). RFC 9110 Section 5.6.3 defines OWS as SP / HTAB only and Section 5.5 makes 0x80-0xFF (obs-text) part of the value.
- **Failure scenario.** (1) Data corruption: a server sends a raw UTF-8 value whose last byte is 0xA0 or 0x85, e.g. 'Location: /caf/voil' + C3 A0 (a-grave) or a Content-Disposition filename ending in Cyrillic 'kha' (D1 85). The final byte is stripped, so the redirect target or filename the application sees is a different, invalid byte sequence. (2) Lenient framing: 'Content-Length: <VT>42' and 'Transfer-Encoding: <FF>chunked' are accepted as 42/chunked although a conforming intermediary treats them as invalid or as an unknown coding, which is the disagreement response-smuggling relies on.
- **Fix direction.** Trim only SP and HTAB (one shared helper for the parser, the trailer path and ExpectContinueHelper), and parse Content-Length from the already-trimmed value without string.Trim(). Add tests for a value ending in 0xA0/0x85 (must be preserved) and for VT/FF around Content-Length and Transfer-Encoding (must be rejected).
- **Verifier.** Traced. TrimWhitespace uses char.IsWhiteSpace (Http11ResponseParser.cs:777-793); lines are decoded as Latin-1 (1532), so bytes 0x85/0xA0 become U+0085/U+00A0, both whitespace, as are VT/FF/CR. It is applied to every header value (722), trailer name/value (736-737), status code (686), Transfer-Encoding tokens (544) and Connection tokens (613-614); Content-Length is trimmed again with string.Trim() before long.TryParse(NumberStyles.None) (578, 583). Result: a raw UTF-8 value whose last byte is 0xA0 or 0x85 loses that byte, and 'Content-Length: <VT>42' / 'Transfer-Encoding: <FF>chunked' are accepted although RFC 9110 Section 5.6.3 limits OWS to SP/HTAB. No guard downstream (HttpHeaders.Add stores the value as given, Runtime/Core/HttpHeaders.cs:49-64). The chunk-size path already uses an ASCII-only helper (IsAsciiWhitespace 1574-1580), so the header path is the inconsistent one.

### http1-protocol-07: Response header values containing NUL, bare CR or other control characters are delivered to the application unchanged

**medium** · security · verdict **C** · `Runtime/Transport/Http1/Http11ResponseParser.cs:722` · RFC 9110 Section 5.5; RFC 9112 Section 2.2

- **Evidence.** ReadLineAsync splits on LF only and DecodeLineFromBuffer strips at most one trailing CR (Http11ResponseParser.cs:1515-1533), so 'X: a<CR>b<CR><LF>' yields the line 'X: a<CR>b'. ParseResponseHeaderLine validates the name but copies the value as is (722) and HttpHeaders.Add performs no value check (Runtime/Core/HttpHeaders.cs:49-64). NUL and every other C0 control pass the same way. The code is inconsistent with itself: trailer values with CR are rejected (ValidateHeaderValue, 949-953) and ConnectReplyReader replaces a bare CR with SP (ConnectReplyReader.cs:360-370).
- **Failure scenario.** A hostile or compromised origin returns 'Set-Cookie: id=1<CR>...' , 'Location: /x<NUL>y' or 'X-Request-Id: a<CR>FAKE LOG LINE'. The value reaches cookie storage, redirect handling, the HTTP monitor, loggers and any native plugin the game hands it to: NUL truncates C strings, bare CR forges lines in logs/Editor console, and a stored value that later goes back out in a request header makes the serializer's HttpFieldValidator reject every such request (InvalidRequest) until the state is cleared.
- **Fix direction.** In ParseResponseHeaderLine reject the message (FormatException, as for the other field-line errors) or replace each CR/NUL with SP, and reject remaining C0 controls except HTAB and DEL; apply the same rule to trailers so both paths agree. Add strictness tests for bare CR and NUL inside a value.
- **Verifier.** Traced. ReadLineAsync splits on LF only (IndexOfLf 1341-1350) and DecodeLineFromBuffer strips one trailing CR (1521-1524), so an interior bare CR or NUL stays in the line. ParseResponseHeaderLine validates the name only and copies the trimmed value (Http11ResponseParser.cs:715-722); HttpHeaders.Add does no value check (Runtime/Core/HttpHeaders.cs:49-64). The trailer path does reject CR/LF (ValidateHeaderValue 949-953 via AddResponseTrailer 752), so the two paths disagree. RFC 9110 Section 5.5: a recipient of CR, LF or NUL in a field value MUST reject the message or replace each with SP. Interior NUL and other C0 controls are not whitespace and are never trimmed, so they reach the application, cookie storage and logs unchanged.

### http1-runtime-02: DisposeAsync() during a pending read starts a second, concurrent drain read on the same BufferedStreamReader and resets the shared value-task source under the first reader

**medium** · concurrency · verdict **C** · `Runtime/Transport/Http1/Http11ResponseBodySource.cs:279`

- **Evidence.** UHttpStreamingResponse.DisposeAsync -> DisposeAsyncCore awaits _bodySource.DisposeAsync() with no check for a read in flight (Runtime/Core/UHttpStreamingResponse.cs:111-118, 227-232). Http11ResponseBodySource.DisposeAsync (279-316) only checks _terminalState; with keep-alive and a chunked body (ShouldAttemptDisposeDrain always true, 460-463) or <= 64 KB of Content-Length left it calls DrainWithinBudgetAsync -> ReadAsync (470-492). That re-enters ReadChunkedAsync/ReadContentLengthAsync and the reader while the consumer's read is suspended inside them: FillBufferAsync resets _start/_end to 0 (Http11ResponseParser.cs:1366-1367) and issues a second _stream.ReadAsync into the same _buffer; ReadBodyAsync then calls _bodyReadCore.Reset() and overwrites _bodyReadAwaiter/_bodyReadToken/_bodyReadRegistration (1419-1426). Reset() clears the continuation the first reader registered and bumps the version, and OnBodyReadCompleted (1431-1455) reads _bodyReadAwaiter, which now belongs to the second read, so the first read's completion calls GetResult() on a task that may not be complete (a blocking wait on the I/O completion thread). _chunkBytesRemaining/_awaitingChunkTerminator (non-volatile, 36-39) are mutated by both flows.
- **Failure scenario.** One task loops 'await body.ReadAsync(buf, token)' on a keep-alive chunked stream and is waiting for the next chunk; another task calls 'await response.DisposeAsync()' to stop it. The drain issues a second read on the socket and resets the value-task source: the first reader's continuation is dropped, so its ReadAsync never completes (or throws InvalidOperationException for a stale token), chunk framing state is consumed by the wrong flow, and after the 2 s drain timeout the body is closed with the first read still unresolved. With TLS the second read can instead fail with the stream's 'read already in progress' error, which lands in DisposeAsync's catch-all and falls into the Abort path of http1-runtime-01.
- **Fix direction.** Track 'read in flight' in the body source (one Interlocked flag set around ReadAsync) and make DisposeAsync skip the drain and take the abort path when it is set; never start a drain read while another read owns the reader. Cover it with a test that disposes asynchronously while a read is pending on a stream that never answers.
- **Verifier.** Traced. UHttpStreamingResponse.DisposeAsync -> DisposeAsyncCore awaits _bodySource.DisposeAsync() with no in-flight check (Runtime/Core/UHttpStreamingResponse.cs:111-118, 227-237). Http11ResponseBodySource.DisposeAsync checks only _terminalState (279-283); for keep-alive chunked bodies ShouldAttemptDisposeDrain is always true (460-463), so DrainWithinBudgetAsync -> ReadAsync (492) re-enters ReadChunkedAsync and the reader while the consumer's read is suspended. FillBufferAsync zeroes _start/_end (Http11ResponseParser.cs:1366-1367) and ReadBodyAsync issues a second _stream.ReadAsync into the same _buffer, then Reset()s _bodyReadCore and overwrites _bodyReadAwaiter/_bodyReadToken/_bodyReadRegistration (1415-1426): the first reader's registered continuation is dropped, and the first read's OnBodyReadCompleted (1431-1455) takes the second read's awaiter, calls GetResult on it, and the second completion then falls into the 'abandoned' branch and disposes the stream (1459-1470). Nothing in the body source tracks a read in flight. The class comment (lines 12-13) puts the duty on the caller, but the sync Dispose path tolerates a concurrent read (Abort) and the async one does not. Needs a consumer that calls DisposeAsync from another flow during a pending read, so medium.
