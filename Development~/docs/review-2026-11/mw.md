# Middleware and Auth: review findings

Scope: cookies, redirects, decompression, default headers, Auth. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (29 findings, 23 files read in full). Middleware and Auth are clean leaf assemblies: both reference only Core, nothing in an always-included assembly names their types, there is no link.xml, [Preserve], ModuleInitializer or static registry, and the old reflection bridge to JSON (#67) is gone, so an unused interceptor is fully strippable. The main risks are design inconsistencies between the interceptors rather than module boundaries: DefaultHeadersInterceptor has none of the origin binding AuthInterceptor got in #56 and re-adds credentials on cross-origin redirect hops, the sensitive-header set exists as four diverged lists, RedirectInterceptor's documented constructor defaults are dead for every client-created request, and only one of four request-rewriting interceptors follows the copy/restore contract in architecture.md. Error mapping is inconsistent (the same over-limit body is NetworkError in Core and Unknown in decompression; server-driven redirect failures are InvalidRequest and carry full URLs in messages and timeline events). The OAuth layer has the weakest API shape: no forced-refresh or 401 path, protocol parsing routed through the application's replaceable JSON serializer, untyped failures, a mutated caller request and an unreachable default token store. Streaming decompression is, on Unity's Mono/IL2CPP class libraries, very likely a sync-over-async bridge over the network on every read, which the analyzer baseline describes as a path only synchronous callers take. Splitting the Middleware asmdef is not worth it for size (about 4.3k source lines in total); the more useful step is to make the redirect-hop observer and request-derivation contracts public so cookies and redirects stop being coupled through internals.

**RFC conformance, protocol implementation, security** (30 findings, 23 files read in full). The slice is solid where earlier reviews already pushed: Authorization is origin-bound in either interceptor order, Set-Cookie and Cookie are computed per redirect hop, secure cookies cannot be shadowed from insecure origins, cookie prefixes and IP hosts are handled, method rewriting and the https->http block follow RFC 9110, and gzip/zlib layers verify their trailers. The main risk is decompression as a DoS surface: the content-coding chain is unbounded in length (allocation and recursion per coding) and only the outermost layer's output is limited, so a tiny nested body can burn unbounded CPU that the buffered path cannot cancel. The second risk is credential and data scoping around redirects: DefaultHeadersInterceptor re-adds credentials on cross-origin hops when it sits inside the redirect interceptor, redirect URLs bypass the redaction policy through exception messages and timeline events, and the proxy decision of the first URL is reused for every hop. The cookie jar deviates from RFC 6265 in ways that matter for interop and safety (quote stripping asserted by a test, DateTime.TryParse instead of the cookie-date algorithm, control characters stored and later rejected by the serializer, a trailing-dot bypass of the public-suffix check). Auth has no 401/WWW-Authenticate handling or Basic encoder to review; the OAuth client's defects are a redirect_uri that is re-serialized through Uri.ToString(), fail-open issuer validation, and refresh-token races.

**performance, resource management, concurrency, platform compatibility** (21 findings, 23 files read in full). Ownership of pooled buffers in this slice is sound: the decoded SegmentedBuffer, the drain buffers and the wrapped body source are released exactly once on the success, failure and abort paths I traced, the OAuth semaphore is never released without being acquired, and there is no LINQ, Regex, reflection or culture-sensitive parsing in scope. The main risks are concurrency and platform ones. RedirectHandler re-dispatches from inside the previous hop's response callback, so with the documented canonical order (and the shipped sample 05) a same-host redirect makes ConcurrencyInterceptor hold one permit per hop and can deadlock with no timeout. Streaming decompression is the only path the real transport ever uses, and on Unity 2021.3's class library (DeflateStream IL inspected for unityjit and unityaot) it is async-over-sync: every read lands in the GetResult() bridge with CancellationToken.None, which drops consumer cancellation and the 2 s dispose bound, parks a pool thread per in-flight compressed body, and probably delivers streamed data only in destination-sized quanta. The decompression wrapper also overrides the transport's drain/RST policy on dispose and allocates about 16 KB of unpooled buffers per compressed response; the interceptor chain makes up to four double-cloned request copies per send. CookieJar and OAuthClient are thread-safe for their own state, but the jar scans all cookies per request and does its parsing and eviction under the write lock, and the OAuth refresh gate turns a token-endpoint outage into a serial queue that request timeouts do not bound.

## High (5)

### mw-protocol-01: DecompressionHandler accepts an unbounded number of content codings, so one response header forces thousands of stacked inflaters (memory bomb and unbounded recursion depth).

**high** · security · verdict **C** · `Runtime/Middleware/DecompressionHandler.cs:742` · RFC 9110 section 8.4 · issue #783

- **Evidence.** TryResolveCompression (DecompressionHandler.cs:727-782) appends every gzip/x-gzip/deflate token to `resolved` with no cap, and CreateDecompressionStream (684-700) builds one InflateLayerStream per token. Each InflateLayerStream allocates an 8 KB input array in its field initializer (InflateLayerStream.cs:76) and a DeflateStream at StartBody (445-447); every read recurses through all layers (InflateLayerStream.Read 166-197 -> DeflateStream.Read -> InflaterInput.Read 792-800 -> ReadForInflater 618-639 -> _source.Read of the layer below). The only bound is the header size: 8192 chars per HTTP/1.1 line (Http11ResponseParser.cs:156), about 1630 codings; 256 KB of decoded header list on HTTP/2 (UHttpClientOptions.cs:14), about 51,000 codings. No test covers a chain limit (Tests/Runtime/Middleware has only 2-layer cases).
- **Failure scenario.** A hostile or compromised server (or an on-path attacker on http) answers over HTTP/2 with `content-encoding: gzip,gzip,...` repeated ~51k times: the handler allocates ~420 MB of 8 KB arrays before reading one body byte (OOM on mobile). With ~1600 nested gzip layers over HTTP/1.1 (body about 40 KB) the first read recurses ~1600 x several managed/native frames; a stack overflow is not catchable and kills the player. Same class as curl CVE-2022-32206.
- **Fix direction.** Cap the chain (curl allows 5; 2-3 covers real servers) and fail with a UHttpException beyond the cap, counting codings across all Content-Encoding field lines (see mw-protocol-09). Add a regression test with a long chain.
- **Verifier.** No cap exists: TryResolveCompression (Runtime/Middleware/DecompressionHandler.cs:742-782) appends every gzip/x-gzip/deflate token and CreateDecompressionStream (:691-699) builds one InflateLayerStream per token, each with an 8 KB array in a field initializer (InflateLayerStream.cs:76); layers read each other recursively (Read :166-197, ReadForInflater :618-639). No test or guard limits the chain. Correction to the numbers: the default HTTP/2 bound is MaxHeaderListSize = 64 KB (Core/Http2Options.cs:15, enforced at Http2Connection.ReadLoop.cs:617), not 256 KB (UHttpClientOptions.cs:14 is only the ceiling when the user raises the setting), so the default is about 13,000 codings / ~105 MB, not 51k / 420 MB. HTTP/1.1: 8192-char line (Http11ResponseParser.cs:156) = ~1630 codings / 13 MB. Measured with a copy of InflateLayerStream.cs in a scratch .NET 8 program: 13,000 gzip layers over a 12-byte garbage body allocate 103 MB and die with an uncatchable stack overflow on a 1 MB thread stack (6,000 layers also overflow); 1,630 valid nested layers (38.5 KB body) survive a 1 MB stack but overflow a 512 KB stack. Not run on Unity Mono/IL2CPP. DecompressionInterceptor is opt-in, so not a default-path crash.

### mw-protocol-02: The decoded-size limit only counts the outermost layer's output, so stacked codings (or zero-output DEFLATE input) burn unbounded CPU that the timeout cannot interrupt.

**high** · security · verdict **C** · `Runtime/Middleware/DecompressionHandler.cs:202` · issue #774

- **Evidence.** The limit is checked against `output.Length` of the top stream only (DecompressBufferedBody 200-223) and `_bytesRead` of the top stream (DecompressionBodySource.ReadAsync 309-326). Bytes passed between stacked InflateLayerStreams are never counted, and DEFLATE can consume any amount of input for zero output (empty stored blocks `00 00 00 FF FF`, empty gzip members), so the limit never trips. The buffered path is a synchronous loop without a CancellationToken (187-232); in the streaming path ct is only seen by the top-level ReadAsync, and lower layers read synchronously through BodySourceStream.Read with CancellationToken.None (548-564) wherever DeflateStream.ReadAsync falls back to Read. `_maxCompressedBodySizeBytes` (66) applies only to a known Content-Length. Measured in a scratch program with the same pull model (three stacked GZipStreams): 651 wire bytes -> 145 KB -> 100 MB -> 0 output bytes, 129 ms on a desktop core; each extra layer multiplies the work by roughly 700-1000.
- **Failure scenario.** Response `Content-Encoding: gzip, gzip, gzip, gzip` with a ~1 KB body (four nested layers over empty stored blocks) needs ~100 GB of inflate work and yields no output: in the buffered path the handler thread spins for minutes to hours and neither the request timeout nor the caller's token stops it; in the streaming path one ReadAsync never returns. With a 32 MB compressed body (the allowed maximum) two layers already give ~30 GB of work.
- **Fix direction.** Bound what every lower layer may produce (for example total intermediate bytes <= k x maxDecompressedBodySizeBytes, or a consumed-input budget per produced byte), count compressed input for unknown-length bodies, and add a cancellation/disposed checkpoint to the buffered loop and to InflateLayerStream's refill path. Keep it together with the chain cap of mw-protocol-01.
- **Verifier.** The limit only sees the outermost decoder's output: DecompressBufferedBody checks output.Length (DecompressionHandler.cs:202-223) and DecompressionBodySource checks _bytesRead (:309-326); bytes handed between stacked InflateLayerStreams are never counted, and _maxCompressedBodySizeBytes applies only to a known Content-Length (:66). The buffered loop takes no CancellationToken (:187-232); lower layers refill synchronously (InflateLayerStream.cs:628) and BodySourceStream.Read uses CancellationToken.None (DecompressionHandler.cs:559-563). The only reader is ResponseCollectorHandler.cs:180 (one ReadAsync at a time), so nothing aborts a read that produces no output; a lower layer does re-check disposal on entry (InflateLayerStream.cs:168/258), but nobody disposes while the single reader is stuck. Measured with a copy of InflateLayerStream.cs on .NET 8: a 909-byte body under three gzip layers expands to 218 KB, then 150 MB of empty stored blocks, yields 0 output bytes and takes 478 ms; each further layer multiplies the work by about 700, and the limit never trips. Distinct from mw-protocol-01: a chain cap of 3-5 does not bound this.

### mw-protocol-03: DefaultHeadersInterceptor placed inside RedirectInterceptor re-adds Authorization/Cookie/API-key default headers on cross-origin redirect hops.

**high** · security · verdict **C** · `Runtime/Middleware/DefaultHeadersInterceptor.cs:37` · RFC 9110 section 15.4 · issue #787 · also reported as mw-design-01

- **Evidence.** RedirectInterceptor.BuildRedirectRequest strips Authorization, Proxy-Authorization and Cookie on a cross-origin hop (RedirectInterceptor.cs:133-138) from its own copy of the request and redispatches through `next` (RedirectHandler.cs:242). DefaultHeadersInterceptor.Wrap (29-53) then runs again for the hop and adds every default header the hop request lacks (line 37; with overrideExisting it replaces unconditionally) with no origin check. AuthInterceptor received origin binding for exactly this pattern (#56, AuthInterceptor.cs:112-128); InterceptorOrdering has no rule for it (Core/Pipeline/InterceptorOrdering.cs:53-70) and the documentation lists RedirectInterceptor first (Documentation~/Modules/Interceptors.md:12), so an interceptor added later is inside it. DefaultHeadersInterceptorTests has no redirect case.
- **Failure scenario.** Interceptors = [RedirectInterceptor, DefaultHeadersInterceptor({Authorization: 'Bearer T'})]. api.example.com answers `302 Location: https://cdn.other.net/x`; the hop request reaches cdn.other.net carrying `Authorization: Bearer T`. With the order reversed the header is stripped, so the interceptor order decides whether the credential leaks.
- **Fix direction.** Bind credential default headers (at least Authorization, Proxy-Authorization, Cookie) to the origin of the first request seen on the RequestContext, as AuthInterceptor does, or let RedirectInterceptor mark cross-origin derived hops in the context and skip those headers there. Add both-order regression tests like AuthRedirectOrderTests.
- **Verifier.** RedirectInterceptor.BuildRedirectRequest strips Authorization/Proxy-Authorization/Cookie on a cross-origin hop (RedirectInterceptor.cs:133-138) and RedirectHandler redispatches through the inner chain (RedirectHandler.cs:242). DefaultHeadersInterceptor.Wrap runs again for that hop and sets every default header the request lacks, with no origin check (DefaultHeadersInterceptor.cs:33-51), so a stripped Authorization or Cookie default comes back. No guard: InterceptorOrdering has only the Cache/Auth and Concurrency/Retry rules (Core/Pipeline/InterceptorOrdering.cs:53-70), DefaultHeadersInterceptor has no IInterceptorRole, Documentation~/Modules/Interceptors.md:207 only says it 'adds headers to every request', and DefaultHeadersInterceptorTests has no redirect case. Needs the user to put a credential header into DefaultHeadersInterceptor and list it after RedirectInterceptor; that order is the documented default position for RedirectInterceptor. Custom headers such as X-Api-Key are not stripped by the redirect interceptor in either order, so the order dependence concerns Authorization, Proxy-Authorization and Cookie only.

### mw-runtime-01: RedirectHandler dispatches the next hop from inside the previous hop's OnResponseStartAsync, so the previous hop's inner interceptor frames (and its ConcurrencyInterceptor permit) are still held: same-host redirects deadlock, and no timeout ends the wait.

**high** · concurrency · verdict **C** · `Runtime/Middleware/RedirectHandler.cs:242` · issue #797

- **Evidence.** RedirectHandler.OnResponseStartAsync (RedirectHandler.cs:132-266) awaits `_dispatch(newRequest, this, _context, _cancellationToken)` at :242, i.e. while the previous hop's transport is still awaiting the handler callback (RawSocketTransport.cs:1889 in EmitParsedResponseHeadAsync; Http2Stream.cs:651-665), so the previous hop's `next(...)` has not returned for any interceptor below Redirect. ConcurrencyInterceptor.cs:60-70 acquires before `next` and releases in `finally` after it returns, so hop N still holds its permit when hop N+1 calls ConcurrencyLimiter.AcquireAsync (ConcurrencyLimiter.cs:92-101: one global and one per-authority semaphore, cancellable only by the caller token or dispose). The request deadline exists only inside the transport (RawSocketTransport.cs:439-440 CancelAfter), which hop N+1 never reaches; ApplyTotalRedirectTimeoutBudget (RedirectInterceptor.cs:155-174) only shortens request.Timeout. The documented canonical order puts Redirect (#2) outside Concurrency (#8) (Documentation~/Modules/Interceptors.md:55-62, 'Holds a permit only while a request is on the wire'), and Samples~/05-AdvancedFeatures/AdvancedFeaturesExample.cs:44,63 ships RedirectInterceptor + ConcurrencyInterceptor(maxConnectionsPerHost: 2). No test combines the two interceptors (rg over Tests/Runtime: only InterceptorOrderTests names both).
- **Failure scenario.** Sample 05 client, GET https://httpbin.org/redirect/2 (three hops on one authority): hops 1 and 2 hold both per-host permits, hop 3 waits for a third and the request never completes unless the caller cancels its own token. With the default limit of 6: six concurrent requests that each get one same-host 302 each hold one permit and wait for a second, so all six hang and every later request to that host queues behind them. Every hop also takes a global permit, so long cross-host chains shrink maxTotalConnections the same way.
- **Fix direction.** Unwind before re-dispatching: let RedirectHandler discard the 3xx body, record the next hop request and return, and have RedirectInterceptor.Wrap loop `await next(hopRequest, redirectHandler, ...)` after the previous `next` returned, so each hop releases what its inner interceptors hold. Add a test with ConcurrencyInterceptor(1, 1) and a same-host redirect.
- **Verifier.** RedirectHandler.OnResponseStartAsync awaits _dispatch(newRequest, this, ...) for the next hop (RedirectHandler.cs:242) while the previous hop's transport is still awaiting that callback (RawSocketTransport.cs:1889-1894; HTTP/2: Http2Stream.cs:651-667, the dispatch awaits the completion set after the handler returns). The handlers between forward the callback inline (Retry/RetryDetectorHandler.cs:81/94, Cache/CacheStoringHandler.cs:62-160), so the previous hop's ConcurrencyInterceptor is still inside 'await next' and holds its permit until the finally (RateLimit/ConcurrencyInterceptor.cs:60-70). The next hop's AcquireAsync waits on the caller token and the limiter's dispose token only (ConcurrencyLimiter.cs:92-101); the request deadline lives in the transport of each hop (RawSocketTransport.cs:439-440), which the waiting hop never reaches, and ApplyTotalRedirectTimeoutBudget only shortens request.Timeout (RedirectInterceptor.cs:155-174). No ordering rule covers Redirect/Concurrency (InterceptorOrdering.cs:53-70); the documented canonical order puts Redirect (#2) outside Concurrency (#8) (Documentation~/Modules/Interceptors.md:55-62) and Samples~/05-AdvancedFeatures/AdvancedFeaturesExample.cs:44,63 ships exactly that with maxConnectionsPerHost: 2, so a same-authority chain of three hops never completes. No test combines the two interceptors.

### mw-runtime-02: On Unity's Mono/IL2CPP class library every streamed compressed read ends in the sync bridge BodySourceStream.Read, which reads with CancellationToken.None: the consumer's token and the 2 s dispose-drain bound are lost, and Abort() is a no-op once DisposeAsync has started.

**high** · concurrency · verdict **C** · `Runtime/Middleware/DecompressionHandler.cs:559` · issue #779

- **Evidence.** DecompressionBodySource.ReadAsync -> ReadFromDecompressionStreamAsync (DecompressionHandler.cs:459-472) -> InflateLayerStream.ReadCoreAsync `await CurrentInflater().ReadAsync(buffer, cancellationToken)` (InflateLayerStream.cs:228). In Unity 2021.3.45f2's System.dll (unityjit and unityaot profiles, type metadata and IL read with System.Reflection.Metadata) DeflateStream overrides only Read(byte[],int,int), BeginRead (ReadMethod.BeginInvoke) and EndRead; mscorlib's Stream.ReadAsync(Memory) -> ReadAsync(byte[]) -> BeginEndReadAsync, and DeflateStreamNative.UnmanagedRead calls Stream.Read on the base stream. So the inflater pulls input synchronously: InflaterInput.Read -> ReadForInflater `_source.Read(_in, ...)` (InflateLayerStream.cs:618-628) -> BufferedStream -> BodySourceStream.Read (DecompressionHandler.cs:548-564), which blocks on `_inner.ReadAsync(..., CancellationToken.None).GetAwaiter().GetResult()`. For streaming sends the transport adds no token of its own (RawSocketTransport.cs:1826-1830; Http11ResponseBodySource.cs:26-28 'body reads are governed only by the consumer token'). DisposeAsync (393-435) sets `_disposeStarted`, then drains through the same ReadAsync with a 2 s token (404-405) that is only checked between reads; Abort (372-380) returns immediately when `_disposeStarted` is set, and UHttpStreamingResponse.AbortBody (UHttpStreamingResponse.cs:142-148) is a no-op after dispose. The baseline rationale for the two GetResult sites (Tools~/ci/analyzer-baseline.txt:34-37, 'the library itself reads asynchronously') does not hold on these runtimes. No test reads or disposes a stalled compressed body with a cancellable token (rg 'Cancel' Tests/Runtime/Middleware/Decompression*.cs: only CancellationToken.None).
- **Failure scenario.** Unity player or Editor, SendStreamingAsync of a gzip response; the server stalls mid-body or the mobile network drops and leaves a half-open socket. `await body.ReadAsync(buffer, cts.Token)` does not return when cts is cancelled. `await response.DisposeAsync()` never completes: the drain read is blocked, its 2 s token is never observed, and a pool thread, the 16 KB drain buffer, the connection and its per-host slot stay held. A later Abort cannot release them because it is ignored once dispose started. (Buffered sends are bounded by the transport read token.)
- **Fix direction.** Feed the inflater only from `_in` that InflateLayerStream fills asynchronously with the caller's token (so the bridge never blocks; treat a starved inflater read as 'need input', see mw-runtime-03), or at least pass the token of the read in progress to BodySourceStream.Read. Make Abort always abort the inner source, also while DisposeAsync drains. Add a PlayMode test with a held compressed source: cancel a read, then DisposeAsync.
- **Verifier.** Re-traced, including the class-library part. Unity 2021.3.45f2 unityaot-linux System.dll (read with System.Reflection.Metadata): DeflateStream declares only Read(byte[],int,int), BeginRead, EndRead (no ReadAsync / Read(Span) override); BeginRead IL = newobj ReadMethod + callvirt ReadMethod::BeginInvoke; DeflateStreamNative.UnmanagedRead IL calls Stream::Read on the base stream; mscorlib Stream.ReadAsync(Memory) -> ReadAsync(byte[]) (token checked once) -> BeginEndReadAsync. So InflateLayerStream.cs:228 runs the inflater's synchronous read on a pool thread, which pulls through InflaterInput.Read (792-800) -> ReadForInflater `_source.Read` (618-628) -> BufferedStream -> BodySourceStream.Read, blocking in `_inner.ReadAsync(..., CancellationToken.None).GetAwaiter().GetResult()` (DecompressionHandler.cs:559-563). Streaming sends give the inner source no transport token (RawSocketTransport.cs:1826-1830, Http11ResponseBodySource.cs:26-28) and ResponseBodyStream registers nothing on the caller token (ResponseBodyStream.cs:145-160), so a body-phase read on a stalled HTTP/1.1 connection ignores cancellation. UHttpStreamingResponse.DisposeAsync always calls _bodySource.DisposeAsync (UHttpStreamingResponse.cs:111-118, 228-238); DecompressionBodySource.DisposeAsync sets _disposeStarted (395) and drains through the same read with a 2 s token that is only checked between reads (404-405, 299); Abort returns at 374-375 and AbortBody at UHttpStreamingResponse.cs:144-145, so nothing can release it. No refuting guard or test (Tests/Runtime/Middleware/Decompression*.cs use only CancellationToken.None, no held source). Limits of the claim: header/trailer phases read asynchronously with the token (InflateLayerStream.cs:246); sync Dispose()/Body.Dispose() before DisposeAsync still abort (UHttpStreamingResponse.cs:155-160); HTTP/2 has its own stall timeout; buffered sends are bounded by the transport token. Not run on a device, but the path is fixed by the shipped IL.

Add a test that sends a client-created request through a RedirectInterceptor with non-default constructor values.
- **Verifier.** Traced. ### mw-design-11: AuthInterceptor has no target scope and overwrites an explicit per-request Authorization header: the provider's token goes to whatever origin each request addresses

**medium** · architecture · verdict **C** · `Runtime/Auth/AuthInterceptor.cs:118` · RFC 6750 section 5.3 · issue #740

- **Evidence.** IsBoundOrigin binds to the origin of the first request seen on each RequestContext (AuthInterceptor.cs:112-123), so the 'origin' the credential is bound to is simply the URL of every new request; AuthRedirectOrderTests.cs:107-131 (SeparateRequests_EachBindToTheirOwnOrigin) asserts that https://a.test and https://b.test both receive the same bearer token. The constructor takes only a provider and a scheme (AuthInterceptor.cs:42). The header is written with WithHeader, which replaces an existing value (AuthInterceptor.cs:73-74, UHttpRequest.cs:175-180), while DefaultHeadersInterceptor and DecompressionInterceptor respect an existing header and CookieInterceptor merges. Documentation~/Modules/Auth.md recommends WithBearerToken for single requests without saying the interceptor wins.
- **Failure scenario.** One UHttpClient with AuthInterceptor(OAuthTokenProvider) is used for the game API and for a CDN or analytics endpoint: the OAuth access token is sent to the third party on every direct request. client.Get(otherApi).WithBearerToken(otherToken) sends the provider's token to the other API instead of the one the caller set.
- **Fix direction.** Let the interceptor be constructed with the origins (or a predicate) it may authenticate, and skip requests that already carry Authorization unless told to override. Keep the per-context binding only as the redirect guard it was added for.
- **Verifier.** Traced. IsBoundOrigin stores the first URI seen per RequestContext and returns true (Runtime/Auth/AuthInterceptor.cs:118-123), so every new request binds to its own origin; the constructor has no origin/predicate parameter (AuthInterceptor.cs:42). Tests/Runtime/Auth/AuthRedirectOrderTests.cs:106-131 asserts https://a.test and https://b.test both receive 'Bearer secret-token'. Explicit header is overwritten: WithBearerToken sets Authorization via WithHeader (AuthBuilderExtensions.cs:15), then the interceptor copies the request and calls WithHeader("Authorization", ...) (AuthInterceptor.cs:73-74), which is HttpHeaders.Set = replace (UHttpRequest.cs:175-180, HttpHeaders.cs:36-44). No test covers a pre-set Authorization, and Documentation~/Modules/Auth.md recommends WithBearerToken for single requests right after the interceptor section without saying the interceptor wins. The only opt-out is the internal SkipAuthMetadataKey (AuthInterceptor.cs:32; reachable only by passing the literal string to the public WithMetadata, undocumented). Closed #56 proposed an allowed-origin set (default: first request/base URI) and no injection over plain http; only the per-context redirect guard was implemented, and no open issue tracks the rest. Client-wide token attachment matches common HTTP-library behaviour, so the cross-origin part is a design gap against the repo's own 'credentials stay with their origin' rule, not a regression; the silent replacement of a caller-set Authorization is plain wrong behaviour.

### mw-design-13: There is no way to react to a rejected token: AuthInterceptor ignores 401, IAuthTokenProvider has no invalidate hook, and OAuthClient.RefreshTokenAsync silently returns the stored token while it is not locally expired

**medium** · architecture · verdict **C** · `Runtime/Auth/OAuthClient.cs:171` · RFC 6750 section 3.1 · issue #745

- **Evidence.** RefreshTokenAsync first reads the store and returns `existing` whenever `!existing.IsExpired(_utcNow(), _defaultRefreshSkew)` (OAuthClient.cs:170-172); this is the de-duplication of concurrent refreshes, but it cannot tell 'another caller already refreshed' from 'the caller wants a refresh now'. Expiry is decided only from the local clock (OAuthToken.cs:35-38, OAuthClient.cs:264). AuthInterceptor passes the request on and never looks at the response (AuthInterceptor.cs:57-95); IAuthTokenProvider has a single GetTokenAsync (IAuthTokenProvider.cs:10-17). Core.Internal.AuthChallengeParser exists but is used only for proxy 407 (RawSocketTransport.cs:1710-1714).
- **Failure scenario.** The server revokes the access token, or the device clock is set back after the token was issued (manual change, time correction on resume, token restored from persistent storage). Every request gets 401 until the local clock passes ExpiresAtUtc; calling RefreshTokenAsync explicitly returns the same rejected token without contacting the token endpoint. The only recovery is RemoveAsync on the app's own ITokenStore, which is impossible with the default store (mw-design-16).
- **Fix direction.** Make the de-duplication compare tokens instead of clocks (skip the refresh only when the stored token differs from the one the caller holds), add an explicit force/invalidate entry point, and give AuthInterceptor an opt-in single retry on 401 that invalidates through the provider.
- **Verifier.** Traced. RefreshTokenAsync returns the stored token whenever it is not locally expired (Runtime/Auth/OAuthClient.cs:170-172) before building the refresh form, so an explicit refresh call cannot force a token-endpoint round trip; expiry is local wall clock only (OAuthToken.cs:35-38, OAuthClient.cs:264, default clock DateTime.UtcNow at OAuthClient.cs:38). ### mw-runtime-05: DecompressionBodySource does not delegate DrainAsync/DisposeAsync to the wrapped source: it inflates the rest of the body for up to 2 s, replacing the transport's bounded drain (HTTP/1.1) and immediate RST_STREAM (HTTP/2).

**medium** · resource-management · verdict **C** · `Runtime/Middleware/DecompressionHandler.cs:393` · issue #777 · also reported as mw-design-26

- **Evidence.** DrainAsync (DecompressionHandler.cs:351-370) loops ReadAsync (inflate + CRC32/Adler) into a 16 KB buffer; DisposeAsync (393-435) drains that way under a 2 s timer whenever `_completed` is 0, with no byte budget, and only then calls `_inner.DisposeAsync()`; GetTrailersAsync (387-388) does the same. The policies it overrides: Http11ResponseBodySource.DisposeAsync drains only keep-alive bodies whose remaining length fits `_bufferedDrainReuseThresholdBytes` and otherwise closes at once (Http11ResponseBodySource.cs:279-316, 450-476); Http2ResponseBodySource.DisposeAsync resets the stream without draining (Http2ResponseBodySource.cs:276-279). architecture.md 'Body wrappers (decompression, ...) delegate DrainAsync, Abort, GetTrailersAsync'. DecompressionEarlyDisposeTests.cs:15-19,38 states that an early dispose never reaches the trailer; with this code the dispose drain does read to the trailer, fails the CRC, and the failure is swallowed at DecompressionHandler.cs:410-416 with the inner source aborted, so the test passes for a different reason.
- **Failure scenario.** `await using` a streamed 200 MB gzip download and leave after the first kilobyte (user cancels): instead of closing the connection or sending RST_STREAM, the wrapper keeps downloading and inflating at full speed for 2 s (tens of MB of mobile data, one busy core), DisposeAsync takes 2 s, then the source is aborted anyway. A redirect or retry that discards a compressed 3xx/5xx body (RedirectHandler.DiscardBodyAsync -> ResponseBodyDiscardHelper.DrainAsync) inflates and checksums bytes nobody reads, and a corrupt or over-limit discarded body aborts a connection the transport could have reused.
- **Fix direction.** In DrainAsync and DisposeAsync drop the decoder and delegate to `_inner.DrainAsync(ct)` / `_inner.DisposeAsync()` so the transport decides between drain and close; mark the wrapper completed. Keep decode-to-end only where validation is the point. Fix the test's stated reason.
- **Verifier.** Code is as described. DecompressionBodySource.DisposeAsync (DecompressionHandler.cs:393-435) drains through ReadAsync (inflate + checksum) under a 2 s timer with no byte budget whenever _completed is 0, then disposes the inner source; DrainAsync (351-370) and GetTrailersAsync (387-388) do the same. UHttpStreamingResponse.DisposeAsync always reaches it (UHttpStreamingResponse.cs:111-118, 228-238; only sync Dispose aborts an unfinished body, 155-160). The inner policies it replaces: Http11ResponseBodySource.DisposeAsync closes at once unless keep-alive and the remainder fits the 64 KB threshold (279-316, 450-476); Http2ResponseBodySource.DisposeAsync resets the stream (276-279). InflateLayerStream's own contract says 'disposing before the end skips the checks by design' (InflateLayerStream.cs:22-23) and architecture.md:102 asks wrappers to delegate. DecompressionEarlyDisposeTests.cs:27-41: the 256 KB mock body is drained by the dispose, the corrupt CRC is hit, ReadAsync throws, and DisposeAsync's bare catch (410-416) swallows it, so the test passes for a different reason than its doc comment states. The older phase-22a.5 review accepted the decoding DrainAsync only because the decoder stays in use; that does not hold in DisposeAsync, where the decoder is discarded.

### mw-runtime-06: OAuthClient's refresh gate serializes failures instead of sharing them: after a failed refresh every waiter repeats the token request one by one, and the wait is not covered by the request timeout.

**medium** · concurrency · verdict **C** · `Runtime/Auth/OAuthClient.cs:166` · issue #744

- **Evidence.** RefreshTokenAsync takes a per-key SemaphoreSlim (OAuthClient.cs:164-166), re-checks the store (170-172) and sends the token request (184); on any failure it releases the gate (218-221) with nothing recorded, so the next waiter finds the same expired token and sends its own request. - **Failure scenario.** The token endpoint is unreachable (each attempt runs to the 30 s default timeout). ### mw-runtime-07: Each compressed response allocates about 16 KB of unpooled buffers plus a redundant BufferedStream copy layer, and the production transport never reaches the pooled, copy-free buffered decode path.

**medium** · performance · verdict **C** · `Runtime/Middleware/DecompressionHandler.cs:269` · issue #775

- **Evidence.** DecompressionBodySource's constructor (DecompressionHandler.cs:268-270) builds BodySourceStream -> BufferedStream(8 KB) -> InflateLayerStream per coding. BufferedStream allocates its 8 KB array on first read and InflateLayerStream allocates `_in = new byte[InputBufferBytes]` (8 KB, InflateLayerStream.cs:76; deliberately unpooled, 41) per layer, then a DeflateStream per gzip member (on Mono plus a 4 KB managed io_buffer and native state). InflateLayerStream asks its source for `_in.Length - start` bytes with `start` up to HistoryBytes (PrepareInflaterFill, 612-616, 627-628), which is below BufferedStream's 8 KB bypass threshold after the first fill, so every compressed byte is copied inner -> BufferedStream buffer -> `_in` -> inflater. BufferedStream adds nothing: InflateLayerStream already buffers its input. Per response also: List<CompressionKind>(4) + ToArray + Substring per token (742-780) and a full header clone (77). Because RawSocketTransport only produces streaming sources (see mw-runtime-03), the SegmentedBuffer path of #74 (187-232) is not used for real traffic and buffered sends pay inflater -> rented 16 KB -> SegmentedBuffer.Write (ResponseCollectorHandler.cs:175-187).
- **Failure scenario.** A game polls a JSON API that answers with 400-byte gzip bodies: each response costs roughly 20 KB of short-lived managed arrays (8 KB + 8 KB + 4 KB on Mono) and about ten objects for a 400-byte payload; at 20 responses per second that is 400 KB/s of garbage on Boehm/incremental GC from decompression alone.
- **Fix direction.** Remove the BufferedStream layer (read the body source straight into `_in`); size `_in` from the known compressed Content-Length when it is small; parse Content-Encoding without the List/Substring for the single-token case. Consider decoding through the segment path when the wrapped source reports a small known length.
- **Verifier.** Facts hold. Per coding layer: BodySourceStream + BufferedStream(8 KB) + InflateLayerStream (DecompressionHandler.cs:268-270) with `_in = new byte[8192]` (InflateLayerStream.cs:76) and a DeflateStream per member (447). The first fill asks BufferedStream for 8192 bytes (bypass), every later fill asks for less (PrepareFill/PrepareInflaterFill keep the window, 567-574, 612-616), so BufferedStream allocates its 8 KB array and adds a copy while InflateLayerStream already buffers its own input. Content-Encoding parse allocates a List, an array and a Substring per token (742-780) and the headers are cloned (77). The pooled segment path (81-135, 187-232) is unreachable from RawSocketTransport because both body sources return false from TryGetBufferedData. The unpooled `_in` is a documented, sound trade-off (InflateLayerStream.cs:41: a dispose racing a read must not return a buffer in use); the BufferedStream layer and the unused buffered path have no such reason. #434 tracks per-read allocations of the streaming inflate path on Mono, not this fixed per-response cost. The 4 KB Mono io_buffer figure is from Mono's DeflateStreamNative and was not re-measured.
