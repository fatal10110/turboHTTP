# Packaging and build size: review findings

Scope: asmdef graph, link.xml, bootstrap, package.json, build processors. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**pluggability, modularity, build size** (17 findings, 65 files read in full). The asmdef graph itself is sound: references match the architecture table exactly, optional modules depend only on Core, test assemblies are gated by UNITY_INCLUDE_TESTS, .meta coverage is complete, licences are consistent, and the runtime is almost reflection-free (two reflection sites outside the vendored library), so the package is well placed for stripping. What defeats that is rooting, not references: the linker processor applies every module's link.xml whenever the module compiles (always), 32 of 44 rules protect statically reachable code, and TurboHTTP.Complete is an always-linked, non-excludable bootstrap, so a stripped 'HTTP/1.1 GET with JSON' player still links HTTP/2 + HPACK (8.4 KLOC, unreachable without the opt-in ALPN provider), the WebSocket transport, the rooted parts of TurboHTTP.Unity with its startup hooks, and at Minimal stripping the whole WebSocket and Unity assemblies (about 55 of 75 first-party KLOC versus roughly 26 needed). On unstripped Mono players everything ships, including the 138 KLOC vendored BouncyCastle library and the Testing module, because neither asmdef is constrained (#258 understates this). The main correctness risk at this boundary is that the Android cleartext platform policy is installed by an optional assembly that stays linked only through an unrelated link.xml rule, so the size clean-up must give that hook an explicit root first. Other packaging defects: undeclared built-in module dependencies in package.json, a WebGL build guard with no opt-out, a raw link.xml that breaks Assets-embedded installs, and asmdef invariants enforced only by Unity tests that PR CI does not run. Restructurings by payoff per effort: (1) define-constrain TurboHTTP.SecureProtocol (one line, megabytes on Mono); (2) delete the TurboHTTP-type link.xml rules after rooting the cleartext hook, and wrap the Observability monitor registration in UNITY_EDITOR (small edits, removes Unity/Observability dead weight and startup hooks); (3) add an opt-out define for Complete and trim its references; (4) move HTTP/2 behind a registration seam or define (medium effort, largest first-party saving); (5) split audio out of TurboHTTP.Unity and declare engine-module dependencies; (6) move the asmdef invariants into check_repo.py.

Not read in full: Plugins/**/*.meta other than the two iOS plugin metas, TurboHttpBackground.androidlib.meta, TurboHttpBackgroundPlugin.java.meta and build.gradle.meta (folder and remaining file metas not opened); Tests/Editor/MonoConfigurationLinkXmlTests.cs (related test; first 60 of 103 lines); Tests/Editor/HttpMonitorEditorTests.cs, Tests/Editor/HttpMonitorRedactionSettingsTests.cs (related tests, not opened); Tools~/ci/test_*.py (related tests, not opened); Tools~/ci/shadow_build.py (outside scope; lines 1-130 read for the define set); Runtime/Transport/BouncyCastle/Lib/** (vendored, out of scope; counted only)

### pkg-pluggability-01: The linker processor treats 'the module's DLL was compiled' as 'the module is in the build', so link.xml rules that name TurboHTTP types root optional modules (Unity, JSON, WebSocket.Transport, Transport) in every stripped player; 32 of the 44 rules protect code that nothing reaches by reflection.

### pkg-pluggability-02: TurboHTTP.Complete cannot be excluded from a package install, so the documented lean configuration is unreachable and untested; its bootstrap statically pulls the WebSocket transport, JSON and JsonUtility into every player, and 10 of its 15 asmdef references (including TurboHTTP.Testing) are unused.

**medium** · pluggability · verdict **C** · `Runtime/TurboHTTP.Complete.asmdef:27` · also reported as unity-design-04

- **Evidence.** Runtime/TurboHTTP.Complete.asmdef:27 has 'defineConstraints: []' and :26 'autoReferenced: true'; Runtime/Bootstrap/AssemblyInfo.cs:8 adds [assembly: AlwaysLinkAssembly] and TurboHttpBootstrap is [Preserve] with two [RuntimeInitializeOnLoadMethod] methods (TurboHttpBootstrap.cs:31-50, 82-91). A UPM package from a Git URL or registry is immutable, so a consumer has no define, setting or link.xml that removes this assembly; yet the 'projects that exclude TurboHTTP.Complete call EnsureRegistered themselves' path is documented in TurboHttpBootstrap.cs:27-29, RawSocketTransport.cs:81-83, RawSocketWebSocketTransport.cs:48-50, JsonModuleRegistration.cs:12-17, ProjectJsonBridge.cs:8-10, Documentation~/APIReference.md:199-202 and Development~/docs/agents/architecture.md:70-72. No document says how to exclude it and no test compiles or runs without it (DefaultTransportRegistrationTests only call EnsureRegistered with Complete present). The bootstrap calls RawSocketWebSocketTransport.EnsureRegistered() (TurboHttpBootstrap.cs:54), JsonModuleRegistration.EnsureRegistered() and JsonUtilitySerializer.RegisterAsDefaultIfBuiltIn() (:89-90) unconditionally, so Complete.dll references TurboHTTP.WebSocket.Transport, TurboHTTP.WebSocket (IWebSocketTransport), TurboHTTP.JSON and UnityEngine.JSONSerializeModule. Add a shadow-build variant or EditMode test that compiles with the opt-out define and exercises the three EnsureRegistered calls, and document the lean setup in one place.
- **Verifier.** Runtime/TurboHTTP.Complete.asmdef:26-27 has autoReferenced true and defineConstraints []; Runtime/Bootstrap/AssemblyInfo.cs:8 is [assembly: AlwaysLinkAssembly]; TurboHttpBootstrap is [Preserve] with two SubsystemRegistration hooks (TurboHttpBootstrap.cs:31, 45-50, 82-87) that call RawSocketTransport.EnsureRegistered, RawSocketWebSocketTransport.EnsureRegistered, JsonModuleRegistration.EnsureRegistered and JsonUtilitySerializer.RegisterAsDefaultIfBuiltIn unconditionally (:53-54, :89-90). ### pkg-pluggability-03: The Android cleartext platform policy is installed by a private startup hook in the optional TurboHTTP.Unity assembly, which has no AlwaysLinkAssembly; it survives stripping only because the unrelated decoder link.xml happens to root that assembly, and there is no public call to install it by hand.

**medium** · architecture · verdict **P** · `Runtime/Unity/Mobile/Android/AndroidCleartextTrafficPolicy.cs:28` · also reported as unity-design-05

- **Evidence.** AndroidCleartextTrafficPolicy.Install is 'private static' with only [RuntimeInitializeOnLoadMethod(SubsystemRegistration)] (AndroidCleartextTrafficPolicy.cs:25-33) inside an 'internal static class' (:21) of TurboHTTP.Unity. Runtime/Unity/AssemblyInfo.cs has only InternalsVisibleTo; the only [assembly: AlwaysLinkAssembly] are in Runtime/Bootstrap/AssemblyInfo.cs:8 and Runtime/Transport/BouncyCastle/AssemblyInfo.cs:6, both with comments explaining that an unreferenced package assembly is otherwise skipped by UnityLinker and its hooks never run. TurboHTTP.Complete does not reference any TurboHTTP.Unity type (TurboHttpBootstrap.cs:1-7), so in a project whose scripts use only Core/Transport the single thing that makes UnityLinker process TurboHTTP.Unity is Runtime/Unity/link.xml (decoder types), delivered through TurboHttpLinkerProcessor. When the hook does not run, CleartextTrafficPolicy.PlatformPolicy stays null and CleartextTrafficPolicy.IsPermitted returns true for any host once AllowCleartext is true (Runtime/Core/CleartextTrafficPolicy.cs:70-74: 'if (platformPolicy == null) return true'). The documentation promises the opposite: 'TurboHTTP refuses it unless AllowCleartext = true and the app's policy permits the host' (Documentation~/PlatformNotes.md:168-172), and Core's own doc says 'On Android players the TurboHTTP Unity module installs a platform policy' (CleartextTrafficPolicy.cs:23-24). No test asserts the root (compare TransportBootstrapTests.cs:45-64, which does assert [Preserve] and AlwaysLinkAssembly for the transport bootstrap).
- **Failure scenario.** Someone removes the decoder rules from Runtime/Unity/link.xml (the obvious clean-up, see finding 01 and #158), or a project copies the package without the Editor assembly so the linker processor does not run. An Android IL2CPP app that uses only UHttpClient with AllowCleartext = true and a network security config permitting cleartext for one debug host now sends http:// to every host: TurboHTTP.Unity is not processed by the linker, Install never runs, and the platform check silently disappears. Confirm with a stripped Android player whose scripts reference no TurboHTTP.Unity type: log CleartextTrafficPolicy.PlatformPolicy != null at startup with and without the Unity link.xml.
- **Fix direction.** Give the security hook an explicit root that does not depend on other modules' rules: install the Android policy from the TurboHTTP.Complete bootstrap (already UnityEngine-aware and always linked) through a small registration API, or mark TurboHTTP.Unity [assembly: AlwaysLinkAssembly] with [Preserve] on Install and accept that cost knowingly. Expose a public EnsureRegistered for lean builds, and add a test like TransportBootstrapTests that fails if the root is removed.
- **Verifier.** Code is as described. AndroidCleartextTrafficPolicy.Install is private static with only [RuntimeInitializeOnLoadMethod(SubsystemRegistration)] inside an internal static class (Runtime/Unity/Mobile/Android/AndroidCleartextTrafficPolicy.cs:21-33); Runtime/Unity/AssemblyInfo.cs has only InternalsVisibleTo; the only AlwaysLinkAssembly attributes are Runtime/Bootstrap/AssemblyInfo.cs:8 and Runtime/Transport/BouncyCastle/AssemblyInfo.cs:6; nothing in Runtime/Bootstrap references a TurboHTTP.Unity type. The repo's own build record shows the risk is real: at Stripping High an unreferenced package assembly with a [Preserve] startup hook (TurboHTTP.Observability) is absent from the linker output (2026-11-player-build-smoke.md:67), so in a project whose scripts use no TurboHTTP.Unity type the hook depends on Runtime/Unity/link.xml (decoder rules) reaching UnityLinker and on UnityLinker then honouring the hook attribute in that assembly. Neither is recorded for a Core-only project (the smoke project uses TurboHTTP.Unity), so today's state is unverified rather than shown broken; the stated failure needs the decoder rules removed or the linker processor absent. Impact is bounded: AllowCleartext defaults to false on Android players (CleartextTrafficPolicy.cs:29-33), so only apps that opted in and rely on a per-host network security config are exposed. The built-in Android policy has no public install call (IsCleartextTrafficPermitted is internal), though CleartextTrafficPolicy.PlatformPolicy itself is a public setter.

### pkg-pluggability-05: The HTTP/2 stack (22 files, 8,358 lines, 38% of TurboHTTP.Transport) is statically referenced by RawSocketTransport and linked into every player, although without the opt-in BouncyCastle provider no Unity runtime can negotiate h2.

**medium** · pluggability · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:74` · also reported as http2-design-01, net-design-07

- **Evidence.** RawSocketTransport's constructor creates 'new Http2ConnectionManager(http2Options, _streamingOptions)' unconditionally (Runtime/Transport/RawSocketTransport.cs:74) and the dispatch paths call _h2Manager.GetIfExists/GetOrCreateAsync (:586, 629, 690, 868, 971, 1137), so Http2Connection (4 partial files, 3,381 lines), Http2Stream (864), Http2ResponseBodySource (689), HpackEncoder/Decoder/Huffman/static and dynamic tables (1,389) and the frame codec are reachable from the default transport. Runtime/Transport/link.xml:65-66 additionally preserves SingleReaderChannel`1 and Http2ResponseBodySource 'all'. The transport's own capability probe says when this code can run: ProbeCapabilities (RawSocketTransport.cs:126-139) reports Http2 only when SslStream supports ALPN, commented 'never on Unity's runtimes', or when the BouncyCastle provider is registered. README.md:12 and Documentation~/Modules/Transport.md:20-21 say the same ('Unity's SslStream has no ALPN, so connections use HTTP/1.1'). There is no h2c/prior-knowledge path (Http2Connection.cs:52 'If h2c is introduced...'). TURBOHTTP_BOUNCYCASTLE is off by default, so in the default configuration the selection is a runtime branch the linker cannot remove.
- **Failure scenario.** Default install, IL2CPP, any stripping level: the player carries the full HTTP/2 + HPACK implementation (Huffman tables, static table, flow control, read loop, pooled streams) and its generic instantiations, none of which can execute because ALPN never selects h2. For the 'HTTP/1.1 GET with JSON' build this is the single largest avoidable block of first-party code: about 8.4 of the roughly 26 KLOC that build actually needs to link next to it.
- **Fix direction.** Put HTTP/2 behind a registration seam the linker can cut: an internal IHttp2Dispatcher set by a small TurboHTTP.Transport.Http2 assembly (or a TURBOHTTP_HTTP2 define implied by TURBOHTTP_BOUNCYCASTLE and by a future native ALPN backend, #429), with RawSocketTransport holding only the interface. Drop the two Http2 link.xml rules. This is the highest-payoff restructuring after the BouncyCastle asmdef constraint, at medium effort because Http2ConnectionManager is constructed and consulted inline today.
- **Verifier.** RawSocketTransport's constructor creates Http2ConnectionManager unconditionally (Runtime/Transport/RawSocketTransport.cs:74) and the dispatch paths consult _h2Manager, so the HTTP/2 stack is statically reachable from the default transport; Runtime/Transport/link.xml:65-66 additionally preserves SingleReaderChannel`1 and Http2ResponseBodySource 'all'. Runtime/Transport/Http2 is 23 files (finding says 22), 8,358 lines, of 21,837 in TurboHTTP.Transport outside BouncyCastle (38%). ProbeCapabilities (RawSocketTransport.cs:126-139) reports Http2 only with SslStream ALPN ('never on Unity's runtimes') or the opt-in BouncyCastle provider; README.md:12 and Documentation~/Modules/Transport.md:20-21 say the same; there is no h2c or prior-knowledge path (only the remark at Http2Connection.cs:52). So in the default configuration the selection is a runtime branch the linker cannot cut and the code cannot execute. This is a size and modularity cost of a deliberate single-assembly design, not wrong behaviour; nothing tracks it (#429 is about a native ALPN backend, not about separating the stack).
