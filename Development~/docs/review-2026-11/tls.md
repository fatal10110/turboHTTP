# TLS: review findings

Scope: provider selection, SslStream provider, BouncyCastle glue, managed and native certificate verifiers. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (16 findings, 27 files read in full). The TLS slice is carefully fail-closed and well commented: one SslStream creation point, a single documented order of checks for BouncyCastle (TurboTlsAuthentication.NotifyServerCertificate), no static reference from Transport to the BouncyCastle glue, and a narrow link.xml for the glue. The main design risks are at the edges of that core. (1) The opt-in is only half real: the vendored TurboHTTP.SecureProtocol asmdef has no define constraint, so 681 files / 138.5k lines compile in every project and the DLL is copied into default Mono players without the define (the repo's own player-smoke record shows it). (2) ITlsProvider is a public abstraction that is not actually pluggable: the selector is a closed enum with one hard-coded BouncyCastle slot, the backend value is stored twice (pool and transport) and can disagree, provider identity is a string compare, and the only third-party entry is an object-typed WebSocket option. (3) The trust decision is not in one place in the shipped binary: a second, test-only trust engine (test anchors + X509Chain with AllowUnknownCertificateAuthority) and several test seams are compiled into production and reachable through InternalsVisibleTo for five unsigned, non-shipped assembly names; on iOS/Android/Linux the test anchors bypass the production verifier entirely. (4) Error classification leaks BCL exception types: every non-certificate TLS failure becomes CertificateError and the real reason is buried in an inner exception. The rest is low-severity cleanup: a diagnostics API that reports constants and stale state, stale comments from the pre-verifier and reflection eras, duplicated SecTrust logic in two languages, and redundant link.xml roots. All 27 in-scope files were read in full; related tests and tooling were consulted by grep and excerpts.

**RFC conformance, protocol implementation, security** (12 findings, 27 files read in full). The fail-closed core of this slice is solid: Auto always resolves to SslStream with no runtime fallback (TlsProviderSelector.cs:217-229), SslStream accepts only SslPolicyErrors.None plus a TLS 1.2 floor and an iPAddress-SAN check, and the BouncyCastle path accepts a chain only through CertificateVerificationResult.IsTrusted after the OS verifier (crypt32 / SecTrust / Android trust manager) returned a path that starts at the server's leaf; every bridge error, timeout, unknown status and missing verifier (Linux, other platforms) rejects. I found no path that fails open on an error, exception or fallback. BouncyCastle offers TLS 1.2/1.3 with ECDHE+AEAD only, no SHA-1 signature algorithms, no resumption, refuses renegotiation, omits SNI for IP literals and requires close_notify. The main risk is host-name verification on Android: the managed matcher is the only host check there and still honours the subject CN when no subjectAltName exists, which the Android platform verifier and RFC 9525 do not, so the BouncyCastle path can accept a certificate the platform rejects. The remaining findings are lower: the BouncyCastle stream turns a failed reply-record write into a failed read, ALPN selection is not checked against the offer, the SslStream ALPN options keep renegotiation enabled for h2, Windows verification rejects chains that need a root or intermediate download, and several contract/documentation mismatches. Revocation is off on every provider by recorded decision (not reported). Related tests were searched, not read in full; BouncyCastleChainValidationTests asserts the CN fallback.

**performance, resource management, concurrency, platform compatibility** (16 findings, 26 files read in full). The TLS slice is in good shape on ownership and fail-closed handling: every native handle (crypt32 stores/contexts, CF objects, the iOS malloc'd path buffer, JNI local frames and the single global ref) is released exactly once on every path, P/Invoke signatures and struct layouts match the native headers, the BouncyCastle handshake is raced against the token and a 30 s deadline, and the duplex stream's lock/gate design keeps record order without awaiting under a lock. The main runtime risks are on the BouncyCastle adapter: Dispose still performs a blocking close_notify write (sync-over-async on the SAEA and poll/select streams, and the one path the thread-pool test deliberately skips), and certificate verification parks the handshake's pool thread in Thread.Join for up to 10 s per connection. The default SslStream provider has no handshake deadline of its own, so a silent TLS peer holds a connection and its permits for the whole request timeout. On Windows the crypt32 verifier disables root auto-update, so BouncyCastle can reject chains SChannel/SslStream accept on the same machine. The rest are hot-path costs (one record and one socket send per write call, Task allocations per I/O, a 16 KiB SAEA send buffer that splits every full record) and small races. ALPN is no longer built by reflection (#303 is down to device proof); stripping coverage for the glue ([Preserve], AlwaysLinkAssembly, link.xml naming System) looks consistent.

## Medium (8)

### tls-design-03: ITlsProvider is a public abstraction that third parties cannot plug in for HTTP: the selector is a closed enum with a hard-coded BouncyCastle slot and provider identity is a string compare

**medium** · architecture · verdict **C** · `Runtime/Transport/Tls/TlsProviderSelector.cs:54` · issue #933

- **Evidence.** ITlsProvider, TlsResult and TlsProviderSelector are public (ITlsProvider.cs:12, TlsResult.cs:9, TlsProviderSelector.cs:11), but selection is GetProvider(TlsBackend) over a three-value Core enum (TlsProviderSelector.cs:54-68; an unknown value silently maps to Auto in the default arm). The only registration hook is internal and provider-specific: one static field _bouncyCastleProvider (:19), RegisterBouncyCastleProvider (:105-112, internal, reachable only through InternalsVisibleTo), IsBouncyCastleAvailable (:80). HTTP has no provider option at all: TcpConnectionPool's resolver is a test seam on an internal constructor (TcpConnectionPool.cs:282-283, :385). The single place a third-party ITlsProvider is accepted is WebSocketConnectionOptions.TlsProvider, typed object and cast at run time (Runtime/WebSocket/WebSocketConnectionOptions.cs:107-111, RawSocketWebSocketTransport.cs:286-296). Concrete providers leak through the abstraction: callers identify the provider by tlsResult.ProviderName == "SslStream" (TcpConnectionPool.cs:688, RawSocketTransport.cs:1520) and the HTTP/2 capability probe names both providers (RawSocketTransport.cs:129-139). The interface itself has no options parameter (client certificates, pinning #117, minimum version) and does not state who disposes innerStream on failure: SslStream can throw before it owns the stream (SslStreamTlsProvider.cs:169-196: argument checks, ShouldNegotiateAlpn :410, ResolveAlpnOptions :294) and BouncyCastle documents 'on any failure the inner stream is disposed' (BouncyCastleTlsProvider.cs:60-62) yet throws at :98 without disposing; all three callers compensate with their own Dispose.
- **Failure scenario.** The planned native TLS backend (#429) or a customer provider needs a new TlsBackend enum value in Core, another Register*/Is*Available pair in the selector, another term in ProbeCapabilities and another string in the viability checks; a customer can implement the public ITlsProvider today but can use it only for WebSocket, not for UHttpClient. Any future parameter added to WrapAsync is a breaking change for those WebSocket implementers. A custom provider that returns ProviderName "SslStream" is counted as the platform provider by the diagnostics state.
- **Fix direction.** Either make the abstraction real (a registry keyed by backend with one internal Register(TlsBackend, ITlsProvider), an options object on WrapAsync, a documented innerStream ownership rule, provider identity by reference) or make ITlsProvider/TlsResult internal and type the WebSocket option accordingly. Remove the string comparisons in favour of a property on the provider.
- **Verifier.** The facts hold. ITlsProvider, TlsResult and TlsProviderSelector are public (ITlsProvider.cs:12, TlsResult.cs:9, TlsProviderSelector.cs:11); selection is a closed switch whose default arm maps unknown values to Auto (TlsProviderSelector.cs:54-68) with one hard-coded internal slot (:19, :105-112). HTTP has no provider option (the resolver is an internal test constructor, TcpConnectionPool.cs:282-283, :384-386); the only public entry for a custom provider is WebSocketConnectionOptions.TlsProvider typed object (WebSocketConnectionOptions.cs:107-111) cast at run time (RawSocketWebSocketTransport ResolveTlsProvider). Provider identity is a string compare (TcpConnectionPool.cs:688, RawSocketTransport.cs:1520). Ownership of innerStream on failure is not in the interface docs (ITlsProvider.cs:13-37); BouncyCastle documents 'on any failure the inner stream is disposed' (BouncyCastleTlsProvider.cs:60-62) yet throws at :93-98 without disposing, and SslStream can throw before it owns the stream (SslStreamTlsProvider.cs:169-196, :409); the pool compensates (TcpConnectionPool.cs:703). No wrong behaviour today: this is a public-API/pluggability finding (a public interface that cannot gain a parameter without breaking implementers, relevant to #429 and #117), not a runtime defect.

### tls-design-04: TLS failures are classified by BCL exception type only: every non-certificate handshake failure becomes UHttpErrorType.CertificateError and the actual reason is only in a nested inner exception

**medium** · code-smell · verdict **C** · `Runtime/Transport/BouncyCastle/BouncyCastleTlsProvider.cs:226` · issue #906

- **Evidence.** The provider/transport contract is 'AuthenticationException = final verdict, IOException = transient'. BouncyCastleTlsProvider.IsNonTransientAlert (:241-275) maps 26 alerts to AuthenticationException, including handshake_failure, protocol_version, insufficient_security, unexpected_message, decode_error, illegal_parameter, missing_extension and no_application_protocol; SslStreamTlsProvider.EnsureMinimumTlsVersion throws AuthenticationException for a TLS 1.0/1.1 peer (SslStreamTlsProvider.cs:418-426) and SslStream itself throws it for any handshake failure. RawSocketTransport maps every AuthenticationException to CertificateError (RawSocketTransport.cs:819-821), documented in Core as 'SSL/TLS certificate validation failure' (UHttpError.cs:20-21). The message is the generic alert text: MapFatalAlert builds 'TLS handshake failed: fatal alert X sent to the server' (:226-233) and the specific reason raised by TurboTlsAuthentication (host mismatch with the SAN list, 'TlsBackend.BouncyCastle is unsupported on Linux...', verifier detail) lives only in the TlsFatalAlert two levels down; Tools~/tls-interop/Program.cs:270 has to search ex.ToString() for it. Related misclassifications on the same boundary: a provider PlatformNotSupportedException (TlsProviderSelector.cs:224, SslStreamTlsProvider.cs:294/:410) hits 'case NotSupportedException' and becomes a retryable NetworkError 'Unsupported HTTP response: ...' (RawSocketTransport.cs:814-818); the missing-define InvalidOperationException becomes Unknown (:826-827). Open issue #451 tracks only the test side of this (negative rows pass on a broken TLS stack); it does not propose changing the production classification.
- **Failure scenario.** A server that only offers CBC suites or TLS 1.1 answers the BouncyCastle ClientHello with handshake_failure/protocol_version: the app receives UHttpErrorType.CertificateError with message 'fatal alert handshake_failure(40) received from the server' and reports a certificate problem to the user or to security telemetry. On Linux with BouncyCastle selected, UHttpError.Message is 'fatal alert certificate_unknown(46) sent to the server'; the actionable 'unsupported on Linux, use Auto' text is only in InnerException.InnerException.Message.
- **Fix direction.** Have the providers throw one TurboHTTP TLS exception type that carries a category (certificate, negotiation, platform capability, configuration) and the detail text, and map that explicitly in RawSocketTransport instead of switching on BCL types; include the TlsFatalAlert detail in the outer message. If the public enum cannot grow before 1.0, at least put the reason in UHttpError.Message.
- **Verifier.** Traced. IsNonTransientAlert maps handshake_failure, protocol_version, insufficient_security, unexpected_message, decode_error, illegal_parameter, missing_extension, no_application_protocol and others to AuthenticationException (BouncyCastleTlsProvider.cs:226-275); SslStreamTlsProvider.EnsureMinimumTlsVersion throws it for TLS < 1.2 (SslStreamTlsProvider.cs:418-426); MapDispatchAttemptFailure turns every AuthenticationException into CertificateError with only the outer message (RawSocketTransport.cs:819-821), documented as 'SSL/TLS certificate validation failure' (UHttpError.cs:20-21). The detail raised in TurboTlsAuthentication (host mismatch, Linux-unsupported text) is only in the nested TlsFatalAlert; the interop harness has to search ex.ToString() (Tools~/tls-interop/Program.cs:270). Also confirmed: PlatformNotSupportedException from the selector/provider (TlsProviderSelector.cs:224, SslStreamTlsProvider.cs:294, :409) matches 'case NotSupportedException' first and becomes NetworkError 'Unsupported HTTP response: ...' (RawSocketTransport.cs:814-818), which IsRetryable() treats as retryable (UHttpError.cs:72-74); the missing-define InvalidOperationException (TlsProviderSelector.cs:90) falls to Unknown (:826-827). #451 states the same root cause but tracks only the test side (negative rows passing on a broken TLS stack); the production classification and message are not tracked, so the issue understates it.

### tls-protocol-01: BouncyCastle host-name check falls back to the subject CN, which on Android accepts certificates the platform verifier rejects

**medium** · security · verdict **C** · `Runtime/Transport/Tls/TlsCertificateNameMatcher.cs:64` · RFC 9525 section 6 (CN-ID removed); RFC 6125 6.4.4 (CN only a MAY) · issue #929

- **Evidence.** TlsCertificateNameMatcher.Matches returns `commonNames.Count == 1 && MatchesDnsPattern(commonNames[0], target)` when the certificate has no subjectAltName (lines 64-69). TurboTlsAuthentication.ValidateHostname (Runtime/Transport/BouncyCastle/TurboTlsAuthentication.cs:106-149) is the BouncyCastle host check. On Windows and Apple the platform SSL policy also receives the host (WindowsCertificateVerifier.cs:162-181, MacSecTrustVerifier.cs:103, TurboHttpSecTrustVerifier.mm:181) and can still reject, but on Android the verifier explicitly does not match the host: AndroidTrustManagerVerifier.cs:23-25 ('it does not match the host name (Android leaves that to HostnameVerifier), so TlsCertificateNameMatcher stays the host check'). Android's default HostnameVerifier stopped using the CN in Android 9, and RFC 9525 removed CN-ID. Tests assert the fallback: Tests/Runtime/Transport/Tls/BouncyCastleChainValidationTests.cs:79-81 (LeafCnOnly accepted) and TlsCertificateNameMatcherTests.cs:86. The decision predates the native verifiers (Development~/docs/implementation-journal/2026-11-bc-chain-validation.md:56).
- **Failure scenario.** Android player with TlsBackend.BouncyCastle. A CA the device trusts (a dNSName name-constrained sub-CA, or a private/enterprise CA) issues a certificate with CN=api.victim.com and no subjectAltName. dNSName name constraints do not apply to a CN, so the Android trust manager returns a path; the managed matcher then matches the CN and the handshake succeeds. HttpsURLConnection/OkHttp on the same device reject that certificate. This is 'a certificate the platform would reject' (CLAUDE.md section 3).
- **Fix direction.** Drop the CN fallback from TlsCertificateNameMatcher (SAN only, RFC 9525), or at least disable it where no platform host policy runs (Android). Update the two tests that assert CN acceptance.
- **Verifier.** Traced. TlsCertificateNameMatcher.cs:64-69 accepts a single subject CN when the leaf has no subjectAltName; TurboTlsAuthentication.ValidateHostname (TurboTlsAuthentication.cs:106-149) is the only host check the BouncyCastle path owns. On Android the registered verifier calls X509TrustManagerExtensions.checkServerTrusted(chain, "RSA", host) (AndroidTrustManagerVerifier.cs:118-122), which uses the host for per-domain config/pins only; the file says so itself (lines 23-25: 'it does not match the host name ... TlsCertificateNameMatcher stays the host check'). So a CN-only leaf under any anchor the Android trust manager accepts passes; Android's own HostnameVerifier ignores the CN since Android 9. Apple is guarded (SecPolicyCreateSSL with host: TurboHttpSecTrustVerifier.mm:181, MacSecTrustVerifier.cs:103, which rejects CN-only), Windows crypt32's SSL policy (WindowsCertificateVerifier.cs:162-181) also honours the CN, so the divergence from the platform is Android-only. Tests pin the behaviour (BouncyCastleChainValidationTests.cs:79-81). No guard found. Mitigating: deliberate and documented (journal 2026-11-bc-chain-validation.md:56, RFC 6125 6.4.4 MAY, which CLAUDE.md names as oracle), and exploitation needs a trusted CA to issue a SAN-less certificate (forbidden for public CAs), so it is a hardening/policy gap against CLAUDE.md section 3 rather than a directly exploitable hole. Whether Android's path validator applies dNSName constraints to the CN (the sub-CA scenario) is not settled statically. Not tracked by an open issue.

### tls-protocol-02: A failed write of a reply record (close_notify answer, KeyUpdate) fails the BouncyCastle read that already holds decrypted data or a clean close

**medium** · protocol-impl · verdict **P** · `Runtime/Transport/BouncyCastle/BouncyCastleTlsStream.cs:332` · RFC 8446 section 6.1 · issue #912

- **Evidence.** ReadCoreAsync: after ProcessCiphertext(read) succeeds, `await FlushPendingOutputAsync()` (line 332; sync twin line 195) runs outside any try, so an inner WriteAsync failure propagates out of the read. ProcessCiphertext may have just queued plaintext and processed the peer's close_notify, for which the engine queues its own close_notify (Lib/tls/TlsProtocol.cs HandleClose -> RaiseAlertWarning(close_notify)). The loop only returns plaintext on the next iteration (TryReadPlaintext, line 316), which is never reached. The handshake path and Dispose treat the same flush as best effort (lines 143-150, 283-286).
- **Failure scenario.** Server answers early (for example 413 with Connection: close) while the client is still uploading, sends the response and close_notify, then closes with unread request bytes, so the kernel resets the connection. The client's inner read still returns the response records and the close_notify; the engine queues the close_notify reply; the body writer has already failed and released the gate, so the reader takes it and its write fails with EPIPE/ECONNRESET. The read throws IOException: response bytes that arrived in the same read are dropped and a close-delimited body that ended with a proper close_notify is reported as a network error. Confirm with a loopback server that sends data + close_notify and resets before the client flushes.
- **Fix direction.** After ProcessCiphertext succeeded, make the read-path flush best effort when plaintext is queued or the engine is closed (catch the write failure, deliver the plaintext/EOF, let the write path report the dead socket).
- **Verifier.** Code is as described. ReadCoreAsync (BouncyCastleTlsStream.cs:319-333): after ProcessCiphertext succeeds, FlushPendingOutputAsync at :332 is outside any try, so an inner WriteAsync failure (DrainOutputHoldingGateAsync :497) propagates out of the read before the loop reaches TryReadPlaintext (:316); sync twin at :195. The engine does queue a reply on the read path: Lib/tls/TlsProtocol.cs:242-247 -> HandleClose :268-289 raises close_notify on receipt of the peer's. The same flush is best effort in HandshakeAsync (:143-150), in the ProcessCiphertext-failure branch (:328) and in Dispose (:283-286), so the asymmetry is real and no caller compensates (HTTP callers do not re-read after IOException, although the plaintext is still queued). No test covers a failing reply write (BouncyCastleOutputBacklogTests covers only the gate-held backlog). Outcome is runtime dependent: the write fails only if the socket is already reset when the reader takes the gate (server closed with unread client bytes, e.g. early response during upload or h2 GOAWAY + close racing client frames); after a plain FIN the first write succeeds locally, and on Windows an RST discards the unread data anyway. Not settled statically.

### tls-runtime-01: BouncyCastleTlsStream.Dispose sends close_notify with a blocking, unbounded synchronous write on the inner stream, which is sync-over-async on the SAEA and poll/select streams.

**medium** · concurrency · verdict **C** · `Runtime/Transport/BouncyCastle/BouncyCastleTlsStream.cs:271` · issue #910 · also reported as tls-design-13

- **Evidence.** Dispose (BouncyCastleTlsStream.cs:258-294) calls _protocol.Close(), then if _writeGate.Wait(0) succeeds runs DrainOutputHoldingGate (line 501-508), which calls _inner.Write(_writeBuffer, 0, count) synchronously; _inner.Dispose() is only reached in the finally after that write returns. SaeaStream.Write is WriteAsync(...).GetAwaiter().GetResult() (Runtime/Transport/Tcp/SaeaStream.cs:91-92) and PollSelectStream.Write is the same (PollSelectStream.cs:86-87). On Mono/IL2CPP Socket.SendAsync(SocketAsyncEventArgs) completes through the I/O selector and a pool worker (the repo's own analysis on #206 and the test header of Tests/Runtime/Transport/Tls/BouncyCastleHandshakeThreadPoolTests.cs:15-17 state that a synchronous Read/Write over SaeaStream needs a second pool thread). In NetworkStream mode it is a blocking Socket.Send with no SendTimeout (no SendTimeout is set anywhere under Runtime/). Every BouncyCastle connection close goes through this: PooledConnection.Dispose -> Stream.Dispose (TcpConnectionPool.cs:139-142), from pool scavenging and async continuations (pool workers) and from UHttpClient.Dispose (usually the Unity main thread). The thread-pool test avoids the path on purpose (BouncyCastleHandshakeThreadPoolTests.cs:184-185: 'Dispose's best-effort close_notify is synchronous by contract ... the stream is released by the socket cleanup instead'), and BouncyCastleSocketModeTests also disposes the socket, not the TLS stream, so no test covers Dispose over SAEA.
- **Failure scenario.** SocketIoMode.Saea + TlsBackend.BouncyCastle (the HTTP/2 configuration): N connections are closed from pool workers while the pool is saturated (burst of failures, scavenger, shutdown). Each Dispose blocks its worker in GetResult() waiting for a send completion that itself needs a free worker; with all workers inside Dispose nothing completes until Mono injects threads (about one per 500 ms), or never with a capped pool. From the main thread, UHttpClient.Dispose blocks one selector round trip per idle connection. In any mode, if the kernel send buffer is full and no writer holds the gate, the write never returns and _inner.Dispose() is never reached (no token, no timeout).
- **Fix direction.** Do not block in Dispose: skip close_notify unless it can be handed off without waiting (e.g. start the async drain with an owner that disposes the inner stream when it ends or after a short bound), and add a DisposeAsync that awaits the async drain for callers that can. Add a test that disposes the TLS stream over SaeaStream with the pool clamped.
- **Verifier.** Traced. Dispose (BouncyCastleTlsStream.cs:258-294) calls _protocol.Close(), then on _writeGate.Wait(0) runs DrainOutputHoldingGate (:501-508) -> _inner.Write synchronously; _inner.Dispose() is only in the finally after the write returns. SaeaStream.Write is WriteAsync(...).GetAwaiter().GetResult() (SaeaStream.cs:91-92), PollSelectStream.Write likewise (PollSelectStream.cs:86-87): sync-over-async, which CLAUDE.md section 4 bans. Every pooled BouncyCastle connection closes through it (PooledConnection.Dispose -> Stream.Dispose, TcpConnectionPool.cs:139-143). No SendTimeout exists under Runtime/ (rg), so in NetworkStream mode the write is an unbounded blocking send when the kernel buffer is full and no writer holds the gate. The repo acknowledges and sidesteps it in the test (BouncyCastleHandshakeThreadPoolTests.cs:15-17 and :184-185 'Dispose's best-effort close_notify is synchronous by contract ... released by the socket cleanup instead'), so nothing covers Dispose over SAEA. Limits on impact: SocketIoMode.Saea is opt-in (default NetworkStream, ConnectionPoolOptions.cs:62) and BouncyCastle is opt-in; in the default mode a 31-byte send normally returns at once; under SAEA the stall lasts until the pool injects a thread unless the pool is capped. Not tracked (#447 is the handshake path, #168 is SaeaSocketChannel.Dispose).

### tls-runtime-04: The Windows crypt32 verifier disables root auto-update, so BouncyCastle rejects chains whose root Windows has not lazily installed yet, although SslStream/SChannel on the same machine accepts them.

**medium** · platform-compat · verdict **P** · `Runtime/Transport/Tls/WindowsCertificateVerifier.cs:39` · issue #938 · also reported as tls-protocol-07

- **Evidence.** ChainFlags = CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL | CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE | CERT_CHAIN_DISABLE_AIA (WindowsCertificateVerifier.cs:39-40), passed to CertGetCertificateChain (line 148). Windows keeps only part of the Microsoft root programme in the ROOT store; the others are listed in the AuthRoot CTL and installed on first use, which this flag forbids. The class remarks admit it (lines 16-17: 'A root the machine has not cached yet is therefore untrusted here even where SChannel would fetch it'). The stated reason (ServerCertificateVerifier.cs:104-106: evaluation runs synchronously on the handshake thread and the deadline cannot interrupt it) no longer holds as written: the call now runs on its own thread bounded at 10 s by PlatformVerifierRunner (PlatformCertificateVerifier.cs:131) and WrapAsync abandons the handshake at the deadline regardless (BouncyCastleTlsProvider.cs:122). The untrusted result maps to unknown_ca -> AuthenticationException -> non-retryable CertificateError (TurboTlsAuthentication.cs:218-220).
- **Failure scenario.** Windows Editor or Windows player on a fresh install/VM (or a machine whose browsers use their own root store), TlsBackend.BouncyCastle selected for HTTP/2, server chain ends at a programme root no CryptoAPI client on that machine has used yet: every request fails with a certificate error 'crypt32 chain status 0x00010020/0x00000020', while the same URL works with TlsBackend.SslStream and in a browser. Needs confirmation on a clean Windows image with a host whose root is not preinstalled.
- **Fix direction.** Allow the AuthRoot auto-update (drop CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE, keep AIA and revocation off) now that the call is bounded by the runner's timeout, or document the limitation in PlatformNotes and surface a distinct error detail so it is not read as a server fault.
- **Verifier.** Code is as described: ChainFlags = CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL | CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE | CERT_CHAIN_DISABLE_AIA (WindowsCertificateVerifier.cs:39-40) passed to CertGetCertificateChain (:148); an untrusted/partial result maps to UntrustedRoot (:218-219) -> unknown_ca -> AuthenticationException (TurboTlsAuthentication.cs:218-220), a non-retryable CertificateError. The limitation is deliberate and stated in the class remarks (:16-17) and, in general terms, in customer docs (Documentation~/Modules/Transport.md:26 'The verifiers never fetch from the network (no revocation check, no intermediate or root download)'), but the Windows consequence (roots that Windows installs lazily from the AuthRoot CTL are untrusted until some other CryptoAPI client has used them) is not spelled out, and the stated reason in ServerCertificateVerifier.cs:104-106 (the deadline cannot interrupt the evaluation) is weaker now that the call runs on a bounded worker (PlatformCertificateVerifier.cs:131). Note that lifting the flag means a Windows Update fetch during verification, which contradicts the verifier contract (PlatformCertificateVerifier.cs:23), so the fix is a trade-off, not a one-line change. Whether real machines hit it (clean installs, Chromium-only users, a Let's Encrypt or similar root not yet installed) cannot be settled statically; no test or record covers a clean Windows image. Not tracked by an open issue.

### tls-runtime-15: An abandoned BouncyCastle handshake keeps its stream, engine and buffers alive until the pending inner read ends, which IL2CPP may never deliver.

**medium** · resource-management · verdict **P** · `Runtime/Transport/BouncyCastle/BouncyCastleTlsProvider.cs:122` · issue #344

The issue is open for the device run; its comments record simulator passes only. Nothing beyond #344.

### tls-runtime-16: Concurrent BouncyCastle handshakes over SAEA run all handshake CPU work and certificate evaluation inline on the socket-completion pool workers, which is consistent with the clamped-pool stall still seen on 2021.3 IL2CPP iOS.

**medium** · concurrency · verdict **P** · `Runtime/Transport/BouncyCastle/BouncyCastleTlsStream.cs:131` · issue #447

- **Evidence.** The client path has no synchronous inner I/O (BouncyCastleTlsStream.cs:109-136), but each continuation runs inline on the SAEA completion worker (SaeaCompletionSource.cs:37, no RunContinuationsAsynchronously) and performs key agreement, signature verification and certificate evaluation there under _protocolLock. In the failing fixture test anchors are registered, so on iOS ServerCertificateVerifier takes the X509Chain path (ServerCertificateVerifier.cs:290-291) and runs X509Chain.Build on that worker; in production it is the Thread.Join of tls-runtime-02. Every SAEA send and receive completion needs a free worker, so 16 handshakes on 8 workers have no slack.
- **Failure scenario.** As reported in #447: 16 concurrent handshakes with the pool clamped to the processor count stall for about 60 s in 3 of 8 runs on the x86_64 simulator.
- **Fix direction.** When classifying #447 on a device, capture which workers are inside OfferInput/X509Chain.Build at the stall; moving handshake input processing off the pool (tls-runtime-02) would remove the dependency.
