# WebSocket: review findings

Scope: protocol core, permessage-deflate, client and resilient client, raw-socket WebSocket transport. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (29 findings, 44 files read in full). The protocol core (frame reader/writer, assembler, negotiator, close handshake, ref-counted resource release) is careful and well commented, module references follow the asmdef rules, JSON is reached through a registered bridge rather than reflection, and permessage-deflate/ResilientWebSocketClient/JsonWebSocketSerializer are only reachable from opt-in entry points so they strip when unused. The main risks are in the client layer above the connection: the documented factory WebSocketClient.Create(options) throws ArgumentNullException whenever reconnect is not enabled (untested; breaks the docs quick start, UHttpClient.WebSocket and UnityWebSocketClient without auto-reconnect), ResilientWebSocketClient keeps reconnecting after CloseAsync/Abort (CloseAsync blocks for the whole backoff loop and can leave a live zombie connection), and user event handlers run unguarded inside FinalizeClose so one throwing handler wedges a connection with its socket open. Architecturally the module duplicates logic the package already has and the copies have diverged: a third HTTP response-head parser, a second proxy settings/bypass matcher, a second CONNECT tunnel state machine, and two client classes with copy-pasted receive plumbing; the wrapper-on-wrapper design also stacks three receive queues. The error model is weaker than the HTTP client's (connect-phase timeout/DNS/TLS-certificate/usage errors all become retryable ConnectionClosed/NetworkError, closed sends throw InvalidOperationException) and about twenty plumbing types plus two non-UHttpException exception types are public. For build size, an HTTP-only project that keeps TurboHTTP.Complete still links the WebSocket transport and part of TurboHTTP.WebSocket (bootstrap registration plus link.xml preserve), and metrics collection can be neither disabled nor stripped.

**RFC conformance, protocol implementation, security** (21 findings, 44 files read in full). The RFC 6455 wire core is in good shape: handshake validation (101, Upgrade/Connection tokens, Sec-WebSocket-Accept, offered-only subprotocol and extensions, 8 KiB head bound), framing (RSV vs negotiated mask, reserved opcodes, 64-bit MSB, masked-server-frame rejection, CSPRNG mask keys), fragmentation rules, close-code/reason validation, Close echo and server-first TCP close, and the permessage-deflate bounds and RSV1 rules all trace correctly and match the Autobahn expectations. The main risk is above the wire, in ResilientWebSocketClient: a CloseAsync or Abort issued during backoff does not stop the reconnect loop (a live authenticated connection reappears after OnClosed, and CloseAsync can hang), and unread pull-queue messages are discarded when the connection ends terminally, which re-creates the message-loss defect that #217 fixed for WebSocketClient. Second tier is liveness: a stalled data write holds the frame lock with no deadline and starves ping, pong reply and protocol-error Close, and keep-alive counts only Pong frames, so a large in-flight frame on a slow link produces a false PongTimeout. Interop: the default MaxFragmentCount of 64 rejects messages well under MaxMessageSize from servers that fragment at small frame sizes. The rest are low-severity conformance and contract gaps (close status misreported in two close paths, non-minimal lengths accepted, 1xx before 101, weaker custom-header validation than the HTTP stack, decompression close codes, option capture order).

**performance, resource management, concurrency, platform compatibility** (33 findings, 44 files read in full). The single-reader / serialised-writer core of WebSocketConnection is sound: the resource refcount, the two send locks, BoundedAsyncQueue (no lost wake-ups, completion and cancellation are correct) and pooled-buffer ownership inside the library all traced clean, and I found no double return or use-after-return. The main risk is lifecycle robustness around it: FinalizeClose runs user callbacks before teardown, so one throwing handler leaves an un-closable connection with a leaked socket, and ResilientWebSocketClient does not own its reconnect loop (CloseAsync/Abort do not stop it, Dispose and ConnectAsync race it, user callbacks can kill or spin it). Abort/Dispose during ConnectAsync leaks the stream that arrives afterwards, and a stalled write holds the frame lock with nothing that can unblock it. On performance the receive path is unbuffered (2-3 stream reads per frame), masking is bytewise, large frames go out as a header write plus 8 KB chunks, permessage-deflate allocates a deflater and payload-sized arrays per message, and each message crosses two or three queues with a per-message copy on the event path. Platform items are minor (one missing ConfigureAwait(false), unvalidated TimeSpan ranges, suspend/resume and main-thread cost that need a device). Several lifecycle items overlap what a protocol-lens reviewer would see (reconnect after CloseAsync, stalled write); they are reported here for their task-ownership and resource side.

### ws-design-03: User event handlers run unguarded inside FinalizeClose and other critical sections, so one throwing handler leaves the connection permanently half-finalized with its socket open

**high** · best-practices · verdict **C** · `Runtime/WebSocket/WebSocketConnection.Lifecycle.cs:111` · issue #1116 · also reported as ws-runtime-01

- **Evidence.** FinalizeClose sets `_finalized` (Lifecycle.cs:101) and then invokes `Error` (110-111) before it resolves `_remoteCloseTcs`, cancels the keep-alive/lifecycle sources, completes `_receiveQueue`, moves the state to Closed or disposes the stream (114-157); the later state transition invokes `StateChanged` (81-82) before TrackAbandonedReceiveLoop/SafeDispose(stream)/ReleaseResources (155-157). WebSocketClient forwards both straight to user delegates with no try/catch: HandleConnectionError -> OnError (WebSocketClient.cs:529-536), HandleConnectionStateChanged -> RaiseClosedFromConnection -> OnClosed (510-560). Because `_finalized` is already 1, every later FinalizeClose/Abort/Dispose returns at line 101-102 and the stream is never disposed. Same pattern elsewhere: MetricsUpdated is raised inside the receive loop and inside the send funnel (TryPublishMetricsUpdate, Lifecycle.cs:267-268, called from Extensions.cs:70), where a throwing handler is mapped to SendFailed and aborts the connection after a successful send (SendReceive.cs:623-646); OnConnected is raised at the end of ConnectAsync (WebSocketClient.cs:206-207) so a throw reports a failed connect while the socket and listener stay alive; OnReconnecting/OnError are raised inside RunReconnectLoopAsync (ResilientWebSocketClient.cs:561, 571-572), where a throw ends reconnection without completing the queue or raising OnClosed. Only OnMessage is isolated (RaiseMessage). The HTTP side's contract (architecture.md, handler callbacks) requires a throwing callback to leave every completion source resolved.
- **Failure scenario.** A plain WebSocketClient user subscribes OnError and touches a Unity API from it (the event is raised on a pool thread, so UnityException is thrown), or simply has a bug in the handler. The network drops: FinalizeClose throws out of the receive loop after `_finalized = 1`; State stays Open, ReceiveAsync never completes, the socket and receive buffers stay allocated, and Dispose() is a no-op for the stream. With a throwing OnReconnecting handler the resilient client silently stops reconnecting and pull consumers hang.
- **Fix direction.** Finish all internal teardown first and raise events last, each invocation wrapped so a handler fault cannot abort teardown (route it to a diagnostics sink); never raise user events inside the send funnel or the receive loop's try block. Add tests with throwing OnError/OnClosed/OnConnected/OnMetricsUpdated/OnReconnecting handlers asserting Closed state, completed queues and a disposed stream.
- **Verifier.** Traced. FinalizeClose sets _finalized (Lifecycle.cs:101) and invokes Error (:110-111) before resolving _remoteCloseTcs, cancelling the token sources, completing _receiveQueue, the Closed transition and SafeDispose(stream) (:114-157). WebSocketClient.HandleConnectionError invokes OnError with no try/catch (WebSocketClient.cs:529-536); a throw leaves State Open, the queue uncompleted and the stream undisposed, and every later Abort/Dispose/FinalizeClose returns at :101-102 (AbortCore only calls FinalizeClose, :59-70; the transport's Dispose only sets a flag, RawSocketWebSocketTransport.cs:281-284). Same for StateChanged -> OnClosed (Lifecycle.cs:81-82, WebSocketClient.cs:510-560) raised before stream disposal. MetricsUpdated inside the send funnel (Extensions.cs:70) is mapped to SendFailed + abort (SendReceive.cs:623-646) and inside the receive loop (:309) to ReceiveFailed (:370-375). OnConnected is raised unguarded at the end of ConnectAsync (WebSocketClient.cs:206-207); OnReconnecting unguarded at ResilientWebSocketClient.cs:571-572 (a throw exits the loop with the queue open and no OnClosed). Only OnMessage is isolated (RaiseMessage). Scope note: UnityWebSocketBridge re-dispatches all handlers to the main thread (UnityWebSocketBridge.cs:208-265), so the Unity bridge/component paths are shielded; plain WebSocketClient/ResilientWebSocketClient users (the documented quick start) are exposed, with events raised on pool threads. Requires a throwing user handler.

### ws-protocol-01: ResilientWebSocketClient keeps reconnecting after CloseAsync or Abort issued during backoff, leaving a live connection after OnClosed, and CloseAsync can block for the whole retry budget.

**high** · protocol-impl · verdict **C** · `Runtime/WebSocket/ResilientWebSocketClient.cs:568` · issue #1105 · also reported as ws-design-02, ws-runtime-02

- **Evidence.** _manualClose is read once, at the top of RunReconnectLoopAsync (ResilientWebSocketClient.cs:552). The loop `while (!ct.IsCancellationRequested && policy.ShouldReconnect(...))` (568) awaits Task.Delay(delay, ct) (574) and then calls ConnectReplacementClientAsync (586) without re-checking it. ct is the lifecycle token, which only Dispose/DisposeAsync cancel (277, 302); CloseAsync (227-250) and Abort (252-268) set _manualClose and null _client but do not cancel it. CloseAsync then awaits the pump task that is running this very loop (StopReceivePumpAsync 676-692; the pump ends in HandleUnexpectedDisconnectAsync, 451). On a successful reconnect _client = nextClient (361), a new pump starts (372), OnReconnected fires (381), and ReleaseDisconnectedClientAsync returns early for the current client (618). Tests cover only DisposeDuringBackoff_CancelsReconnectLoop (Tests/Runtime/WebSocket/WebSocketReconnectionTests.cs:84).
- **Failure scenario.** The network drops and the client is in backoff. The app calls Abort() or CloseAsync() (for example on logout) and receives OnClosed. When the server is reachable again the loop connects with the stored URI and CustomHeaders (auth), raises OnReconnected, State is Open, SendAsync works and OnMessage keeps firing; the connection lives until Dispose. With WebSocketReconnectPolicy.Infinite and an unreachable server CloseAsync never returns; with Default it blocks through all retries (delays plus a 10 s handshake timeout each).
- **Fix direction.** Cancel a per-connect CancellationTokenSource from CloseAsync and Abort, and re-check _manualClose/_disposed after the delay and after a successful connect (dispose the replacement instead of publishing it). Add tests for CloseAsync and Abort during backoff.
- **Verifier.** Traced. RunReconnectLoopAsync reads _manualClose only at entry (ResilientWebSocketClient.cs:552); the loop condition (:568) and the code after Task.Delay (:574-591) test only ct, the lifecycle token, which only Dispose/DisposeAsync cancel (:277, :302). Abort (:252-268) and CloseAsync (:227-250) set _manualClose and null _client but cancel nothing. After the delay the loop calls ConnectReplacementClientAsync, which publishes the new child unconditionally (:361), starts a pump (:372) and raises OnReconnected (:381-382) after OnClosed was already raised. CloseAsync additionally awaits the pump task that is running this loop (StopReceivePumpAsync :676-692, no ct), so it blocks for the remaining attempts and never returns with WebSocketReconnectPolicy.Infinite (WebSocketReconnectPolicy.cs:17) and an unreachable server. UnityWebSocketClient.CloseConnectionAsync (Runtime/Unity.WebSocket/UnityWebSocketClient.cs:499-502) goes through this CloseAsync. No guard found; the only backoff test is DisposeDuringBackoff_CancelsReconnectLoop (Tests/Runtime/WebSocket/WebSocketReconnectionTests.cs:84). One detail of the scenario is wrong: OnMessage does not keep firing. The queue was completed by Abort/CloseAsync, so the first inbound message throws AsyncQueueCompletedException in the new pump (AsyncBoundedQueue.cs:92, :152), the loop is re-entered, sees _manualClose (:552) and returns, and ReleaseDisconnectedClientAsync skips disposal because the client is still _client (:618). The child stays Open (socket, pings, SendAsync works, State == Open, later ConnectAsync throws at :107) until Dispose.

### ws-protocol-02: ResilientWebSocketClient discards messages still queued for ReceiveAsync when the connection ends terminally (server Close with a non-reconnect code, or retries exhausted).

**high** · protocol-impl · verdict **C** · `Runtime/WebSocket/ResilientWebSocketClient.cs:610` · issue #1106

- **Evidence.** In pull-only mode the pump moves every message into _incomingQueue (405). When the child reports the close, RunReconnectLoopAsync ends with CompleteAndDrainQueue(terminalError) (610; also 554), which calls queue.Complete and then queue.Drain(dispose) (694-702). BoundedAsyncQueue.DequeueAsync would still hand out queued items after Complete (AsyncBoundedQueue.cs:175-179), which is how WebSocketClient keeps messages that arrived ahead of the peer's Close (#217: WebSocketClient.cs:456-459 completes without draining; Tests/Runtime/WebSocket/WebSocketReceiveAfterCloseTests.cs). The resilient wrapper's Drain throws them away. No resilient-client test covers messages ahead of a close.
- **Failure scenario.** A server sends five result messages and then Close(1000). The inner client delivers all five to the pump, which enqueues them and then sees ConnectionClosed with code 1000; ShouldReconnect is false, so the queue is drained. An app pulling with ReceiveAllAsync that has consumed only the first message (one message per Unity frame) gets ConnectionClosed next: messages 2-5 are lost without any error. The same happens when retries are exhausted after an abnormal drop.
- **Fix direction.** On connection-end paths complete _incomingQueue without draining it (drain only in Dispose and on an explicit CloseAsync/Abort), as WebSocketClient does, and add a regression test equivalent to WebSocketReceiveAfterCloseTests for ResilientWebSocketClient.
- **Verifier.** Traced. Pull-only pump moves each message into _incomingQueue (ResilientWebSocketClient.cs:405). When the child reports the close, RunReconnectLoopAsync falls through to CompleteAndDrainQueue(terminalError) (:610), which does queue.Complete then queue.Drain(dispose) (:700-701). BoundedAsyncQueue.DequeueAsync would return queued items before reporting completion (AsyncBoundedQueue.cs:175-179), so it is the Drain that discards them. For Close(1000) DefaultReconnectOnCloseCode returns false (WebSocketReconnectPolicy.cs:129-134) and with policy None Enabled is false, so the terminal path is taken on every normal close. WebSocketClient deliberately does not drain on this path (#217: WebSocketClient.cs:456-459, :523-526) and Documentation~/Modules/WebSocket.md:94-97 and :108 promise that messages ahead of the close stay readable and that pull-only delivery is lossless, for both clients. No resilient-client test covers messages ahead of a close (WebSocketReceiveAfterCloseTests uses WebSocketClient only). Loss needs the consumer to lag the pump at the moment the close is processed (frame-paced or slow consumer); a consumer already parked in ReceiveAsync normally wins because the close is finalized only after the server closes TCP.

### ws-design-04: WebSocketClient.Create(options) inspects only ReconnectPolicy and then discards the options, so the same options must be passed again to ConnectAsync and a mismatch silently changes behaviour

**medium** · architecture · verdict **C** · `Runtime/WebSocket/WebSocketClient.cs:46` · issue #1109 · also reported as docs-accuracy-04

### ws-design-05: Connect-phase and protocol failures are collapsed into ConnectionClosed/ProtocolViolation, so timeouts, DNS, TLS certificate failures and usage errors are all reported as retryable network errors, unlike the HTTP client

**medium** · code-smell · verdict **C** · `Runtime/WebSocket/WebSocketConnection.cs:354` · issue #1139

- **Evidence.** WebSocketConnection.ConnectAsync maps every non-WebSocketException to `new WebSocketException(WebSocketError.ConnectionClosed, ex.Message, ex)` (WebSocketConnection.cs:352-355) and the handshake timeout to ConnectionClosed too (338-347); WebSocketException.MapErrorType turns ConnectionClosed into UHttpErrorType.NetworkError (WebSocketException.cs:127-133). The transport lets the TLS provider's AuthenticationException, the DNS TimeoutException (RawSocketWebSocketTransport.cs:343) and its own ArgumentException for a non-ws scheme (:386-390) propagate, so all of them arrive as ConnectionClosed/NetworkError with IsRetryable() == true. The HTTP transport maps the same faults to UHttpErrorType.CertificateError (Runtime/Transport/RawSocketTransport.cs:821) and UHttpErrorType.Timeout; WebSocketError has no Timeout or Certificate member and UHttpErrorType.Timeout/CertificateError are never produced in this module. On the receive side TryHandleProtocolErrorAsync rewraps every WebSocketProtocolException as WebSocketError.ProtocolViolation (SendReceive.cs:508-512), so InvalidFrame, FrameTooLarge, InvalidUtf8, MaskedServerFrame, UnexpectedContinuation, ReservedOpcode, PayloadLengthOverflow and MessageTooLarge are never observable on WebSocketException.Error although they are public enum members listed in IsRetryable. Server-side faults map to UHttpErrorType.InvalidRequest (WebSocketException.cs:108-125), a handshake rejection carries no UHttpError.StatusCode (only HandshakeStatusCode), FrameTooLarge falls to Unknown, and ProxyTunnelFailed is NetworkError (HttpError.IsRetryable() true) but WebSocketException.IsRetryable() false. ResilientWebSocketClient uses neither definition (IsPermanentConnectFailure, :639-652).
- **Failure scenario.** The server certificate expires while a ResilientWebSocketClient with WebSocketReconnectPolicy.Infinite is connected: every reconnect fails TLS validation, surfaces as ConnectionClosed/NetworkError and is retried forever; the app cannot tell a certificate failure or a handshake timeout from a dropped connection except by inspecting InnerException. Code switching on `ex.Error == WebSocketError.MessageTooLarge` never matches.
- **Fix direction.** Map connect failures by cause at one place (timeout -> a Timeout error and UHttpErrorType.Timeout, AuthenticationException -> a certificate error, ArgumentException -> rethrow as usage error), keep the specific WebSocketError of a protocol exception when rewrapping, pass the handshake status into UHttpError, and derive one retryability rule that the resilient client also uses (certificate and usage errors permanent).
- **Verifier.** Traced. WebSocketConnection.ConnectAsync maps the handshake timeout to ConnectionClosed (WebSocketConnection.cs:338-347) and every other non-WebSocketException to ConnectionClosed (:352-355); ConnectionClosed -> UHttpErrorType.NetworkError and IsRetryable() true (WebSocketException.cs:66-73, 127-133). The transport lets TimeoutException (RawSocketWebSocketTransport.cs:343), the TLS provider's AuthenticationException (WrapAsync :230, rethrown :245-249) and ArgumentException for a bad scheme (:386-390, called inside the connection's try at WebSocketConnection.cs:191) propagate. The HTTP transport maps AuthenticationException to CertificateError (RawSocketTransport.cs:819-821). TryHandleProtocolErrorAsync rewraps every WebSocketProtocolException as ProtocolViolation (SendReceive.cs:508-512), the specific code survives only as InnerException (tests asserting MessageTooLarge/MaskedServerFrame do so on the reader/assembler directly, WebSocketMessageLimitTests.cs:27-31, WebSocketFramingTests.cs:199-204). IsPermanentConnectFailure handles only ProxyAuthenticationRequired and 4xx handshakes (ResilientWebSocketClient.cs:639-652), so a certificate failure is retried for as long as the policy allows. No certificate is accepted that should not be; this is error classification, not a TLS weakening.

### ws-design-06: Sending on a closed or reconnecting client throws InvalidOperationException from a client-level pre-check, contradicting the connection's WebSocketException contract; a test pins it

**medium** · best-practices · verdict **C** · `Runtime/WebSocket/WebSocketClient.cs:569` · issue #1113

- **Evidence.** WebSocketConnection deliberately fails sends on a closing/closed connection with WebSocketException(ConnectionClosed) carrying the close status, 'whichever side of a concurrent abort, pong timeout or close the send lands on' (ThrowIfCannotSend, SendReceive.cs:814-835, #84). WebSocketClient.SendAsync first runs EnsureOpenState, which throws InvalidOperationException for any state other than Open (WebSocketClient.cs:569-577), so the connection's mapping is reached only when the close lands between the check and the send. ResilientWebSocketClient.RequireOpenClient throws InvalidOperationException whenever the child is not Open, including the whole reconnect window (ResilientWebSocketClient.cs:664-674). Tests/Runtime/WebSocket/WebSocketClientTests.cs:97-113 (SendAfterClose_ThrowsInvalidOperationException) asserts the pre-check behaviour.
- **Failure scenario.** The peer or the network closes the connection; the application's next SendAsync throws InvalidOperationException("SendAsync requires Open state. Current state: Closed.") instead of a UHttpException, so `catch (WebSocketException)`/`catch (UHttpException)` handlers and retry logic miss it, and the same failure yields a different exception type depending on a race. During auto-reconnect every send fails with a usage-error type the caller cannot distinguish from a programming error.
- **Fix direction.** Keep InvalidOperationException for None/Connecting-before-first-connect only; for Closing/Closed and for the resilient client's reconnect window throw WebSocketException(ConnectionClosed) with the close status (drop the pre-check and let the connection decide). Update the test to the error-model rule.
- **Verifier.** Traced. WebSocketClient.SendAsync calls EnsureOpenState first (WebSocketClient.cs:217, 224), which throws InvalidOperationException for any state other than Open (:569-577), so the connection's deliberate mapping (ThrowIfCannotSend, SendReceive.cs:814-835: None/Connecting = InvalidOperationException, Closing/Closed = WebSocketException, #84) is reached only when the close lands after the pre-check. ResilientWebSocketClient.RequireOpenClient throws InvalidOperationException whenever the child is null or not Open, including the reconnect window (:664-674). The test SendAfterClose_ThrowsInvalidOperationException pins the pre-check (WebSocketClientTests.cs:96-113), but only for a close the application itself made; no doc comment on IWebSocketClient.SendAsync (IWebSocketClient.cs:68-75) states the contract. The exception type for a peer/network close therefore depends on a race.

### ws-design-07: WebSocketProxySettings re-implements proxy configuration and bypass matching that Core already exposes, with different rule semantics than the HTTP client

**medium** · architecture · verdict **C** · `Runtime/WebSocket/WebSocketProxySettings.cs:82` · issue #1157

- **Evidence.** Core has public ProxySettings (Address, NetworkCredential Credentials, BypassList, UseEnvironmentVariables, AllowPlaintextProxyAuth) and public ProxyBypassMatcher.IsBypassed (Runtime/Core/ProxySettings.cs:9-157), whose documented rules include `.example.com` (apex plus subdomains), CIDR, an optional `:port` and bracketed IPv6. WebSocket, which references Core, defines its own WebSocketProxySettings (ProxyUri, ProxyCredentials struct, BypassList) with ShouldBypass supporting only exact names and `*.domain` (WebSocketProxySettings.cs:82-112); a bracketed IPv6 rule is compared as written (comment at :125-127) against a host the transport already stripped of brackets (RawSocketWebSocketTransport.cs:355-361, 85), so `[::1]` never matches. Environment proxies (HTTP_PROXY/NO_PROXY) are not consulted, Basic-over-cleartext consent reuses AllowCleartext instead of AllowPlaintextProxyAuth (ProxyTunnelConnector.cs:110-116), and UnityWebSocketExtensions.BuildWebSocketOptions copies TlsBackend, AllowCleartext and headers from the UHttpClient but cannot copy its proxy because the types differ.
- **Failure scenario.** A project configures the HTTP client with BypassList { ".corp.example", "10.0.0.0/8" }. The same list given to WebSocketProxySettings matches neither ws://api.corp.example nor ws://10.1.2.3, so those sockets are sent through the proxy (or fail there) while HTTP requests to the same hosts go direct; `client.WebSocket(uri)` ignores the client's proxy entirely.
- **Fix direction.** Accept Core's ProxySettings on WebSocketConnectionOptions (or make WebSocketProxySettings a thin adapter) and call ProxyBypassMatcher.IsBypassed(host, port, rules) so both stacks share one rule grammar, credential type and consent flag; then let the Unity extension carry the HTTP client's proxy over.
- **Verifier.** Traced. Core exposes public ProxySettings and ProxyBypassMatcher.IsBypassed with '.domain', CIDR, ':port' and bracket-insensitive IPv6 rules (Runtime/Core/ProxySettings.cs:9-31, 69-157). WebSocketProxySettings.ShouldBypass supports only exact match and '*.domain' (WebSocketProxySettings.cs:82-112); rules keep their brackets (comment :125-127) while the transport passes a bracket-stripped host (RawSocketWebSocketTransport.cs:78, 85, 355-361), so a '[::1]' rule never matches (a bare '::1' rule does).
