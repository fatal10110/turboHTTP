# Utility modules: review findings

Scope: JSON, Files, Observability, Testing, Editor. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (33 findings, 54 files read in full). The utility modules respect the asmdef rule (each references only Core; Editor references Core + Observability) and the JSON bridge no longer uses reflection, but several pluggability goals are not met in practice. The Observability registration is a [Preserve]d RuntimeInitializeOnLoadMethod that roots the whole Editor monitor (about 1,900 lines) in every player, TurboHTTP.Testing has no define/platform constraint so it and its link.xml rules reach every player build's linker input, and the only public control over Core's diagnostic sink lives in the optional Observability module. The main design risk is shared mutable global state with two owners: Editor preferences overwrite MonitorInterceptor's public static configuration (including a custom RedactionPolicy), the Editor window redacts with RedactionPolicy.Default instead of the active policy, and the JSON bridge routes library-internal DOM parsing (record/replay files, redaction, OAuth) through the user-replaceable JsonSerializer.Default, which breaks RecordReplayTransport under a Newtonsoft-style serializer. Redaction logic is duplicated between Observability and Testing (tracked by #117) and has diverged. The rest is dead or unreachable public surface (PooledBuffer<T>, PoolHealthReporter.Register, MockRoute, MonitorInterceptor.DiagnosticLogger), options that are not honoured as documented (LoggingInterceptor levels, DownloadOptions.ExpectedSha256 without VerifyChecksum, the System.Text.Json define) and comments that contradict the platform (span-based Encoding overloads). Solid parts: FileDownloader's commit/resume state handling, LiteJson's strict reader with size and depth caps, RecordReplay's fail-closed redaction and the linker processor's per-module link.xml gating.

**RFC conformance, protocol implementation, security** (27 findings, 53 files read in full). The slice is in decent shape on the basics: LiteJson's reader is strict RFC 8259 (number grammar, escapes, surrogates, BOM, trailing garbage, depth 64, 16 MiB input cap), FileDownloader's Range/If-Range/Content-Range handling and .part/commit flow follow RFC 9110 closely, header and URL-query redaction is on by default in Logging, Monitor, Export and RecordReplay, and the Editor build processors do what they say. The main risk is that redaction is name- and site-based and has holes that default configurations hit: Monitor timeline data (redirect from/to URLs, cache keys) and error text carry raw query strings, URL-valued headers such as Location are never redacted, bodies are captured and exported raw (#117), and the RecordReplay body hash is an offline guessing oracle because its HMAC key is stored in the same file. RecordReplay also has three functional traps: content-coded JSON bodies are silently replaced by the placeholder (recording cannot be replayed), recordings above 16 MiB can be written but not loaded, and a caller cancellation during the body is recorded as a failed interaction. MockTransport and Replay never enforce request.Timeout or a pre-cancelled token, so tests on them cannot see the transport-owned timeout contract. LiteJson is exposed to hash flooding and roughly 30x memory amplification under the 16 MiB cap, and MultipartFormDataBuilder leaves the per-part Content-Type open to CR/LF injection. Testing is compiled into player builds through TurboHTTP.Complete but nothing in it self-registers; TransportBehaviorFlags.SelfDrainsResponseBody is write-only (no reader), so the mocks setting it has no effect either way.

**performance, resource management, concurrency, platform compatibility** (24 findings, 54 files read in full). Slice: JSON, Files, Observability, Testing and the Editor assembly, read in full (54 files) through the performance / resource / concurrency / platform lens. Solid: LiteJson is reflection-free, depth-bounded (64, about 3 small frames per level) and culture-invariant; the Monitor ring buffer and byte budget are consistently locked; MonitorInterceptor costs only a flag check when nobody is viewing; FileDownloader's stream, hash and pooled-buffer ownership is released on every path; no sync-over-async or banned reflection APIs in the slice. Main risk: the observability handlers complete late, on body dispose, and there touch state that is no longer theirs: a client-owned request already disposed by the fluent SendStreamingAsync (ObjectDisposedException out of response disposal with MetricsInterceptor, silently missing Monitor entries, FileDownloader failing after a successful download) and pooled capture buffers that race with a concurrent read. Second tier: the Editor window marshals to the main thread through EditorApplication.delayCall from pool threads and re-decodes multi-megabyte bodies on every OnGUI; the JSON bridge and multipart builder copy bodies needlessly (the claim that span-based Encoding overloads are unavailable is wrong); MockHttpServer misses ConfigureAwait(false); RecordReplay can write recordings its own Replay mode rejects. None of these is tracked by an open issue; device-dependent items are marked plausible.

## High (1)

### util-runtime-01: MetricsHandler and MonitorInterceptor read the request (Content / TryGetBufferedContent) when a streamed body is disposed, after the fluent SendStreamingAsync has already disposed the client-owned request, so response disposal throws ObjectDisposedException and the completion is never recorded.

**high** · resource-management · verdict **C** · `Runtime/Observability/MetricsHandler.cs:101` · issue #1053

- **Evidence.** UHttpRequest.SendStreamingAsync (Runtime/Core/UHttpRequest.cs:390-405) calls Dispose() in its finally as soon as headers arrive; for a client-owned request that sets _disposeRequested, and ThrowIfDisposed (UHttpRequest.cs:564-575) then throws for every later call of the Content getter (:49-55) and TryGetBufferedContent (:70-72), even though the lease is still held by the response. For a streamed body MetricsHandler defers completion to ObservedResponseBodySource's dispose callback (MetricsHandler.cs:61-67, 120-123); CompleteResponse sets _completionRecorded, reads RequestBodyBytesSent (0 for a body-less request) and then evaluates `_request.Content.Length` (MetricsHandler.cs:96-104) -> ObjectDisposedException before Successful/FailedRequests and RecordCompletion run. The callback runs in the finally of ObservedResponseBodySource.DisposeAsync (ObservedResponseBodySource.cs:141-159), so the exception escapes through UHttpStreamingResponse.DisposeAsyncCore (Runtime/Core/UHttpStreamingResponse.cs:227-237) to the caller (the sync Dispose path swallows it in AbortAfterFailedBodyDispose). MonitorInterceptor.BuildMonitorEvent hits the same guard at MonitorInterceptor.cs:350 (`request.TryGetBufferedContent`); Capture's catch (MonitorInterceptor.cs:317-334) turns it into LogCaptureFailure, which is silent because nothing in the package sets DiagnosticLogger (MonitorInterceptor.cs:907-911). HTTP/1.1 bodies never expose buffered data (Http11ResponseBodySource.TryGetBufferedData returns false), so every real streamed response takes this path. All tests in Tests/Runtime/Observability and UHttpClientStreamingContextLifetimeTests use `new UHttpRequest(...)` (not client-owned, guard never trips), so nothing covers it.
- **Failure scenario.** Client with a MetricsInterceptor; the documented pattern `await using var s = await client.Get(url).SendStreamingAsync(ct);` (Documentation~/Modules/Core.md:100) or FileDownloader.DownloadFileAsync (FileDownloader.cs:399 uses the fluent send, :370-374 disposes in finally). At the end of the block DisposeAsync throws ObjectDisposedException(UHttpRequest): FileDownloader has already committed the file but the call fails; SuccessfulRequests/FailedRequests and the average are never updated for any streamed GET. In the Editor the HTTP Monitor silently shows no entry for any streamed request sent through the fluent API.
- **Fix direction.** Snapshot what the handlers need (content length / buffered request body reference / capture note) while the request is live (in the interceptor lambda or OnRequestStart) instead of touching the UHttpRequest in the dispose callback; make observer dispose callbacks non-throwing (catch in InvokeDisposeCallback). Add tests that send a client-created request with request.SendStreamingAsync() through Metrics and Monitor.
- **Verifier.** Traced end to end. UHttpRequest.SendStreamingAsync disposes the request in its finally (UHttpRequest.cs:397-404); for a client-owned request Dispose sets _disposeRequested (428) while the response hold keeps the lease, and ThrowIfDisposed throws whenever _disposeRequested != 0 (573-574), which guards the Content getter (49-55) and TryGetBufferedContent (70-72). UHttpClient passes the client-owned request unchanged into the pipeline (UHttpClient.cs:471-473) and Metrics is canonically outermost (Documentation~/Modules/Interceptors.md:55), so MetricsHandler._request is that object (MetricsInterceptor.cs:36-43). Real transports never expose buffered data (Http11ResponseBodySource.cs:93-97), so completion is deferred to the dispose callback (MetricsHandler.cs:61-67,120-123); for a body-less request sentBytes is 0 and CompleteResponse evaluates _request.Content (101) -> ObjectDisposedException after _completionRecorded is set and before Successful/FailedRequests and RecordCompletion (106-111). The callback runs in the finally of ObservedResponseBodySource.DisposeAsync (155-158) and escapes UHttpStreamingResponse.DisposeAsyncCore (UHttpStreamingResponse.cs:227-237). FileDownloader uses exactly this path (FileDownloader.cs:384,399; DisposeAsync in finally 370-374, after CommitPartFile 359), so a download with a MetricsInterceptor throws after the file is committed. MonitorInterceptor.BuildMonitorEvent hits the same guard at MonitorInterceptor.cs:350; Capture swallows it (331-334) and LogCaptureFailure is silent without a DiagnosticLogger (907-911), so the event is dropped when no interceptor above the monitor copied the request. No refuting test: MetricsInterceptorTests.cs:228 and UHttpClientStreamingContextLifetimeTests.cs:191 use new UHttpRequest (not client-owned); no test combines request.SendStreamingAsync() with Metrics/Monitor.

### util-design-01: ObservabilityModuleRegistration is a [Preserve]d RuntimeInitializeOnLoadMethod compiled for players, so the Editor-only HTTP Monitor is rooted in every player build although UHttpClient only consults the hook under UNITY_EDITOR.

**medium** · pluggability · verdict **C** · `Runtime/Observability/ObservabilityModuleRegistration.cs:23` · issue #1060

- **Evidence.** ObservabilityModuleRegistration.cs:23-28 marks EnsureRegistered with [Preserve] and [RuntimeInitializeOnLoadMethod(SubsystemRegistration)] with no #if UNITY_EDITOR; it registers CreateMonitorInterceptor (30-45), which references MonitorInterceptor.CaptureEnabled and new MonitorInterceptor(). The only consumer, EditorMonitorHook.TryAppend, is called from Runtime/Core/UHttpClient.cs:794-796 and 801-823 inside #if UNITY_EDITOR, so in a player the registered factory is never invoked. UnityLinker roots methods carrying RuntimeInitializeOnLoadMethod/[Preserve] at every stripping level, so everything reachable from the factory stays: MonitorInterceptor.cs (943 lines), MonitorHandler.cs (163), HttpMonitorEvent.cs (312), ObservedResponseBodySource.cs (199), RedactionPolicy.cs (239), plus Core's EditorMonitorHook (58) and their generic instantiations (ReadOnlyDictionary<string,string>, ValueTuple<string,UHttpErrorType?,HttpMonitorFailureKind>, List<HttpMonitorTimelineEvent>...). TurboHTTP.Observability.asmdef is autoReferenced with no platform or define constraint, so the assembly is always in the linker input. A side effect of the hook design is that the pipeline a client runs differs between Editor play mode (extra innermost interceptor appended by Core) and players.
- **Failure scenario.** A project that uses only Core + Transport (never references TurboHTTP.Observability) builds an IL2CPP player with Managed Stripping High: about 1,900 source lines of Editor monitor code and the startup registration call are still compiled into the player, and the registration runs at every player start for a hook nothing reads.
- **Fix direction.** Compile the registration (and the [Preserve]/RuntimeInitializeOnLoadMethod attributes) only under UNITY_EDITOR, or move the registration into TurboHTTP.Editor through a narrow Core entry point. Keep MonitorInterceptor usable in players only when application code references it explicitly.
- **Verifier.** Runtime/Observability/ObservabilityModuleRegistration.cs:23-28 has [Preserve] + [RuntimeInitializeOnLoadMethod(SubsystemRegistration)] with no UNITY_EDITOR guard (rg finds no UNITY_EDITOR in Runtime/Observability) and registers a factory that constructs MonitorInterceptor (30-45). The only reader, EditorMonitorHook.TryAppend, is called solely from Runtime/Core/UHttpClient.cs:794-796/801-823 inside #if UNITY_EDITOR (rg EditorMonitorHook: no other runtime caller). TurboHTTP.Observability.asmdef has no platform or define constraint. So in a player the method runs at startup for a hook nothing reads and roots MonitorInterceptor and what it reaches. That UnityLinker treats these attributes as roots is Unity's documented behaviour, not measured here (no player build run). The mechanism came from #186 (closed), which did not consider the player side. Build-size and startup cost only, no functional defect.

### util-design-03: The JSON bridge forwards library-internal DOM parsing to the user-replaceable JsonSerializer.Default, so RecordReplayTransport (and OAuth token parsing) silently break when the project registers a Newtonsoft/System.Text.Json adapter.

**medium** · architecture · verdict **C** · `Runtime/JSON/JsonModuleRegistration.cs:34` · issue #1034

- **Evidence.** JsonModuleRegistration.cs:32-37: the only IJsonBridge implementation calls JsonSerializer.Serialize/Deserialize, i.e. JsonSerializer.Default (JsonSerializer.cs:43-53), which documentation tells users to replace (JsonSerializer.cs:23-28, LiteJsonSerializer.cs:41-46). Internal consumers need LiteJson's DOM shape: RecordReplayTransport.Serialization.cs:105-112 loads entries only when the value 'is List<object>' and otherwise leaves Entries empty without an error, 90-93 requires the root to be Dictionary<string, object>; RecordReplayTransport.Redaction.cs:242-285 returns false for any node that is not Dictionary<string,object>/List<object>/primitive and the caller then stores the placeholder (119-149, 194-199); Runtime/Auth/OAuthClient.cs:437-441 does 'result as Dictionary<string, object> ?? new Dictionary' (empty on any other shape). Tests/Runtime/Testing/RecordReplayRedactionTests.cs:104-116 covers only the fail-closed redaction path with a fake serializer; no test loads a recording under a non-Lite serializer. The design also stacks two static registries (ProjectJsonBridge -> JsonSerializer.Default) behind a single-implementation internal interface, and errors are wrapped twice (ProjectJsonBridge.cs:75-80 and RecordReplayTransport.Serialization.cs:258-282 both wrap in InvalidOperationException).
- **Failure scenario.** Project calls JsonSerializer.SetDefault(new NewtonsoftAdapter()). Record mode: every JSON request/response body parses to a JObject, TryRedactJsonNode returns false and the body is recorded as "[REDACTED]". Replay mode: the file's "Entries" deserializes to a JArray, 'is List<object>' is false, LoadRecordings returns with zero entries and every request fails with 'No replay recording matched request key' (or silently hits the network under Warn/Relaxed).
- **Fix direction.** Split the bridge contract: a DOM pair (parse to Dictionary<string,object>/List<object>, write the same) bound to LiteJsonSerializer.Instance regardless of JsonSerializer.Default, and a typed pair that follows Default for user payloads (MockResponseBuilder.Json<T>, WithJsonBody<T>, WebSocket messages). Make FromSerializableObject throw when Entries has an unexpected shape.
- **Verifier.** The single IJsonBridge forwards to the user-replaceable JsonSerializer.Default (Runtime/JSON/JsonModuleRegistration.cs:32-37; JsonSerializer.cs:23-28,43-53 advertise Newtonsoft). Internal consumers require LiteJson's DOM: RecordReplayTransport.Serialization.cs:105-112 fills Entries only when the value 'is List<object>' and otherwise returns an empty recording without error (a Newtonsoft-style adapter returns Dictionary<string, object> at the root, passing line 90, with a JArray for Entries); RecordReplayTransport.Redaction.cs:124-136,242-285 returns the placeholder for any non-Dictionary/List node, so every JSON body is recorded as [REDACTED]. That redaction fallback is deliberate fail-closed (comment 239-241, test RecordReplayRedactionTests.cs:105-117), but the silent empty load is not guarded and no test loads a recording under a non-Lite serializer. The OAuth part is weaker: OAuthClient.cs:437-441 gets a real Dictionary<string, object> from a Newtonsoft-style adapter for a flat token response, so it breaks only for adapters returning another root type or element wrappers. Outcome depends on the user's adapter, but the documented one triggers it.
