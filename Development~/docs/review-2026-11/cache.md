# Cache, Retry, RateLimit: review findings

Scope: HTTP cache, retry policy, rate limiting. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (29 findings, 23 files read in full). Module boundaries are clean: Cache, Retry and RateLimit reference only TurboHTTP.Core, use no UnityEngine, reflection, static registries, [Preserve] or link.xml, and nothing in Core or the Complete bootstrap roots them, so an unused module strips away (Cache ~3.7k lines / 11 files, Retry ~530, RateLimit ~660). Cache-Control parsing exists only in Cache (no duplicate in Middleware/Core); HTTP-date parsing is duplicated and diverged across Cache, Retry and Files. The main risk is the cache's storage abstraction and its guards: the Authorization guard and the #55 ordering check work only for the AuthInterceptor type, Cache-outside-Redirect is undetected and stores the final response under the original URL, and ICacheStorage cannot really be used for a persistent or large custom store (in-memory variant index that is never rebuilt, capacity sniffed from MemoryCacheStorage, storage errors failing foreground requests, storage callbacks under an internal lock). CachePolicy has two flags whose combinations give a no-op or immortal entries, must-revalidate is treated as no-cache, and MemoryCacheStorage's sweep deletes exactly the stale entries that revalidation needs. RateLimit's ConcurrencyLimiter takes the global permit before the per-host one, which lets a burst to one host block every other host, and RequestQueue<T> is shipped but unwired. Retry is small and solid; its retry condition is hard-coded in three places with no extension point.

**RFC conformance, protocol implementation, security** (29 findings, 23 files read in full). All 23 in-scope files were read in full. The cache is conservative where it matters most by default: no-store, Vary: *, Set-Cookie and Authorization responses are not stored, 206/Range are bypassed, stores need natural EOF plus trailers, Expires/Date/Age arithmetic and unsafe-method invalidation follow RFC 9111, and Retry gates on idempotency, replayability and a capped Retry-After. The main risk is peer-controlled directive values: a large stale-while-revalidate overflows DateTime in CacheEntry and poisons MemoryCacheStorage for every host (01), and large delta-seconds throw instead of being clamped (05). Freshness semantics are wrong in three places: must-revalidate is handled as no-cache (03), request max-age/min-fresh/only-if-cached are ignored (04), and DoNotCacheWithoutFreshness=false stores entries that never expire (02). The cache trusts its pipeline position: with a redirect or a credential-adding interceptor inside it, responses are stored under the wrong URL or without the Authorization guard (06, 07), and the tee can commit a truncated body after an early trailer read (08). Bounds and privacy gaps remain in the variant index (09), in timeline events and storage keys that carry URLs and Vary values (10, 25) and in the missing partition key (#117). Retry and RateLimit are small and mostly sound; the notable defects are the limiter's global-before-host permit order (12) and Retry-After edge cases (26, 27); 429 handling and a token bucket are open as #118.

**performance, resource management, concurrency, platform compatibility** (21 findings, 23 files read in full). Ownership of pooled store bodies is sound on the sequential paths: the tee/buffered snapshot is handed over exactly once, the queued store disposes it on success, cancellation and skip, and background work is observed and cancelled on Dispose. The main costs are in what the cache does before it knows a response is storable (every candidate body is copied twice and flattened to a byte[]), in a storage sweep that evicts expired-but-revalidatable entries so the 304 path is rarely reached, and in redundant deep header clones on hit and store. The main concurrency and resource risks are the tee accumulator being returned to the pool by Abort/DisposeAsync while a read may still be writing into it, stale-while-revalidate starting one background request per stale hit, a per-bucket variant key set that is not bounded, and ConcurrencyLimiter taking the global permit before the per-host permit, which lets one saturated host block all others. Retry and RateLimit have no ownership leaks; their findings are a time-only discard budget for suppressed 5xx bodies (the SelfDrainsResponseBody flag is dead), wall-clock use for Retry-After dates and cache freshness, per-request allocation churn, and a RequestQueue enqueue/shutdown race. No disk cache exists in scope, so there is no file I/O or serialisation format to review. Nothing here was run; device- and runtime-dependent items are marked plausible.

## High (1)

### cache-protocol-01: A peer-chosen stale-while-revalidate value overflows DateTime in CacheEntry.IsStaleWhileRevalidate, which makes the URL unfetchable and breaks every later MemoryCacheStorage.SetAsync

**high** · security · verdict **C** · `Runtime/Cache/CacheEntry.cs:161` · RFC 9111 1.2.2; RFC 5861 3

- **Evidence.** ParseCacheControl (CacheInterceptor.Parsing.cs:103-112) accepts any stale-while-revalidate that fits TimeSpan (up to ~9.22e11 s) and stores it unclamped. CacheEntry.IsStaleWhileRevalidate (CacheEntry.cs:160-161) computes `ExpiresAtUtc.Value + StaleWhileRevalidate.Value` once the entry is stale and has a validator; for a value above ~2.52e11 s the sum exceeds DateTime.MaxValue and DateTime.op_Addition throws ArgumentOutOfRangeException (ExpiresAtUtc is clamped by AddClamped, this sum is not). Callers: the foreground lookup at CacheInterceptor.cs:352 (throws before the entry can be removed at :378), and CacheEntry.ShouldEvict (CacheEntry.cs:173) used by MemoryCacheStorage.RemoveExpiredEntriesUnsafe (MemoryCacheStorage.cs:274), which SetAsync runs at :92 after it already removed the key being replaced (:89-90) and before `_nextExpiredSweepUtc` is advanced (:285-286). GetCountAsync/GetSizeAsync (:169, :185) hit the same sweep. No test uses a stale-while-revalidate other than 60.
- **Failure scenario.** Any origin the client talks to (or a MITM on http) answers one GET with `Cache-Control: max-age=1, stale-while-revalidate=300000000000` and an ETag. After 1 s: (1) every GET of that URL throws ArgumentOutOfRangeException from the cache interceptor and never reaches the network; (2) the next due sweep throws inside SetAsync and, because the sweep deadline is never advanced, every later SetAsync for any key of any host throws: nothing new is cached (logged as 'Store failed'), and a 304 revalidation of an unrelated entry first loses that entry (removed at :89-90) and then fails the caller's request, because CompleteNotModifiedRevalidationAsync awaits the store (CacheInterceptor.StreamingDispatch.cs:60-63). The poisoned entry is never evicted (the LRU loop is after the throwing sweep); only ClearAsync, Dispose or an unsafe-method invalidation of that URL removes it.
- **Fix direction.** Clamp stale-while-revalidate when parsing (RFC 9111 section 1.2.2 style, e.g. to 2^31 s) and compute the window with an overflow-safe add (reuse AddClamped) in IsStaleWhileRevalidate. Make the storage sweep tolerant of a throwing entry (evict it). Add a regression test with a stale entry carrying stale-while-revalidate=300000000000.
- **Verifier.** Traced. ParseCacheControl stores stale-while-revalidate unclamped (Runtime/Cache/CacheInterceptor.Parsing.cs:103-112); values between ~2.52e11 s (DateTime.MaxValue minus now) and ~9.22e11 s fit TimeSpan. CacheEntry.IsStaleWhileRevalidate (Runtime/Cache/CacheEntry.cs:160-161) evaluates `ExpiresAtUtc.Value + StaleWhileRevalidate.Value` only once now >= ExpiresAtUtc; DateTime.op_Addition throws ArgumentOutOfRangeException. ExpiresAtUtc is clamped (AddClamped, Parsing.cs:200-209), this sum is not. Callers have no guard: foreground lookup CacheInterceptor.cs:352 (EnableRevalidation defaults true, :26) throws before the removal at :378; MemoryCacheStorage.RemoveExpiredEntriesUnsafe (:274) calls ShouldEvict -> IsStaleWhileRevalidate (CacheEntry.cs:173), and MaybeSweepExpiredEntriesUnsafe advances _nextExpiredSweepUtc only after the sweep returns (:285-286), so once the 15 s interval elapses every SetAsync throws at :92, after it already removed the key being replaced (:89-90). StorePreparedEntryAsync swallows it as 'Store failed' (CacheInterceptor.cs:983-986), but the 304 path uses StorePreparedEntryCoreAsync without a catch (:1039-1048) and is awaited in the foreground (CacheInterceptor.StreamingDispatch.cs:60-63), so unrelated revalidations lose their entry and fail. GetCountAsync/GetSizeAsync (:169, :185) hit the same sweep. No test uses a stale-while-revalidate other than 60 (rg over Tests/Runtime/Cache). No open issue.

## Medium (15)

### cache-design-03: MemoryCacheStorage's expiry sweep deletes stale entries that still have validators, so conditional revalidation only happens when no other store ran in between

**medium** · architecture · verdict **C** · `Runtime/Cache/MemoryCacheStorage.cs:92` · RFC 9111 section 4.3 · also reported as cache-runtime-06

- **Evidence.** SetAsync calls MaybeSweepExpiredEntriesUnsafe on every store once 15 s have passed since the last sweep (MemoryCacheStorage.cs:17, 92, 280-287), and GetCountAsync/GetSizeAsync force it (169, 185). RemoveExpiredEntriesUnsafe removes every entry whose CacheEntry.ShouldEvict is true (267-278); ShouldEvict (CacheEntry.cs:164-174) is true as soon as now >= ExpiresAtUtc outside a stale-while-revalidate window and does not look at CanRevalidate(). ICacheStorage's contract says the opposite: 'Expiry/revalidation decisions are handled by cache middleware' (ICacheStorage.cs:13-15), and the interceptor's own path keeps a stale entry to send If-None-Match (CacheInterceptor.cs:365-376). The sweep uses DateTime.UtcNow while the interceptor uses its _utcNow seam, so the fake-clock tests never exercise it. Entries without ExpiresAtUtc (no-cache + ETag) are never swept, so behaviour is also inconsistent between 'no-cache' and 'max-age=0'.
- **Failure scenario.** A is stored with 'Cache-Control: max-age=60' and an ETag. At t=70 s any other response is stored: the sweep removes A. At t=80 s GET A is a plain miss and downloads the full body instead of a conditional request answered by 304. With the common 'max-age=0' + ETag pattern the entry is removed by the first store that runs 15 s later, so EnableRevalidation rarely saves a body in an app with steady cacheable traffic.
- **Fix direction.** Do not evict on freshness in the storage: rely on the LRU/size bounds, or evict only expired entries that cannot be revalidated (no ETag/Last-Modified). If a sweep stays, drive it from the interceptor's clock and policy.
- **Verifier.** CacheEntry.ShouldEvict (Runtime/Cache/CacheEntry.cs:164-174) returns true once now >= ExpiresAtUtc outside a stale-while-revalidate window and never consults CanRevalidate(). MemoryCacheStorage.SetAsync calls MaybeSweepExpiredEntriesUnsafe with DateTime.UtcNow (MemoryCacheStorage.cs:87-92; interval 15 s at :17, :280-287), forces it when full (:99-100) and in GetCountAsync/GetSizeAsync (:169, :185); RemoveExpiredEntriesUnsafe removes every such entry (:267-278). The interceptor's conditional revalidation needs the expired entry returned by GetAsync (CacheInterceptor.cs:365-376), and the ICacheStorage contract says expiry decisions belong to the middleware (ICacheStorage.cs:13-15). A 304 merge is itself a SetAsync (CacheInterceptor.cs:1039-1047), so one revalidation sweeps every other expired validator-bearing entry. No test contradicts this: CacheInterceptor_RevalidatesExpiredEntries_ThatHaveValidators (Tests/Runtime/Cache/CacheInterceptorTests.VariantsAndAsync.cs:306-349) does two back-to-back requests, inside the 15 s interval, and nothing under Tests/Runtime exercises the sweep. Entries without ExpiresAtUtc (no-cache + validator) are never swept (CacheEntry.cs:166-167), so the behaviour is inconsistent. RFC 9111 does not require keeping stale entries, so this is cache-efficacy loss, not a protocol violation.

### cache-design-04: The Vary variant index lives only in the interceptor and cannot be rebuilt from ICacheStorage, so a persistent or shared custom store loses every Vary response and can serve an invalidated variant

**medium** · pluggability · verdict **C** · `Runtime/Cache/CacheInterceptor.cs:105` · RFC 9111 section 4.1, section 4.4

- **Evidence.** Lookup derives storage keys from the in-memory _variantIndex (CacheInterceptor.cs:105-112, 534-553); with no bucket it tries only the unvaried key 'base|~' (535-536, Variants.cs:110-113). The comment states the index 'is intentionally not persisted across process restarts in v1'. ICacheStorage (ICacheStorage.cs:10-42) has no key enumeration, prefix lookup or metadata record from which the index could be rebuilt, and InvalidateBaseKeyCoreAsync removes only the unvaried key plus keys the index knows (CacheInterceptor.cs:1071-1083). DecompressionInterceptor sits inside the cache in the canonical order, so every 'Vary: Accept-Encoding' response gets a varied key ('base|accept-encoding=~;'). The interface also forces a full-body load per lookup (CacheEntry.Body is ReadOnlyMemory<byte>, ICacheStorage.cs:44-47), even when the lookup ends in revalidation or removal. MemoryCacheStorage is the only shipped implementation, so the abstraction's only purpose is custom (persistent) stores.
- **Failure scenario.** A disk-backed ICacheStorage holds 500 CDN responses with 'Vary: Accept-Encoding'. After an app restart (or from a second CacheInterceptor sharing the store) every lookup tries 'base|~' and misses: 0% hit rate for Vary responses at cold/offline start, and the old entries stay orphaned. Worse: a pre-restart variant (Accept-Language: fr) survives a POST invalidation after restart (index empty); a later GET with 'en' re-registers the signature and the next 'fr' GET is served the pre-POST entry as HIT.
- **Fix direction.** Persist the variant signature list through the storage (e.g. a small per-base-key record stored under the unvaried key, as RFC 9111 section 4.1 suggests) and resolve variants from it on lookup and invalidation; split metadata lookup from body retrieval so disk stores need not load bodies for decisions.
- **Verifier.** TryLookupAsync builds candidate keys only from GetSignatureSnapshot; with no bucket it tries the unvaried key 'base|~' alone (CacheInterceptor.cs:534-545, Variants.cs:110-113, :152-162). A response with Vary: Accept-Encoding stored while Decompression sits inside the cache gets key 'base|accept-encoding=~;' (BuildVaryKey, Variants.cs:54-87), which a fresh index can never derive. ICacheStorage has no enumeration or prefix lookup (ICacheStorage.cs:10-42), and InvalidateBaseKeyCoreAsync removes only the unvaried key plus index-known keys (CacheInterceptor.cs:1071-1083). The stale-variant trace holds for a persistent store: after a restart POST removes 'base|~' only; a later GET with another Accept-Language re-registers the signature (Variants.cs:185-186) and the next GET with the old value finds the pre-POST entry and serves it as HIT if still fresh. The code itself names this hazard for index eviction (Variants.cs:242-244) and guards it there, but not for an empty index over a non-empty store. The comment at CacheInterceptor.cs:105-107 calls the index an 'accelerator only' and 'intentionally not persisted'; the first part is wrong, since it is the only route to Vary entries. Only custom persistent or shared stores are affected (MemoryCacheStorage is the only shipped one, and dies with the process), hence medium.

### cache-design-06: Storage exceptions on the foreground paths (lookup, 304 merge, post-revalidation removal, unsafe-method invalidation) fail the HTTP request, while background stores are best-effort

**medium** · best-practices · verdict **C** · `Runtime/Cache/CacheInterceptor.StreamingDispatch.cs:143`

- **Evidence.** Background stores catch and log storage faults (CacheInterceptor.cs:968-987) and the comment at 1164-1168 states mutations are best-effort. The foreground paths have no such handling: TryLookupAsync awaits Storage.GetAsync unguarded (CacheInterceptor.cs:545) and the stale-entry removal at 378; the 304 path awaits ReplaceStoredEntryAsync/StorePreparedEntryQueuedAsync and RemoveStoredEntryAsync (StreamingDispatch.cs:61-63, 69); CompleteModifiedRevalidationAsync aborts the fresh response body and rethrows when the removal fails (92-98); UnsafeInvalidationHandler aborts the body and rethrows when invalidation fails (143-152). The exception leaves the dispatch as a non-UHttpException (mapped to Unknown by the bridge). Tests cover only a failing SetAsync in the background store (CacheInterceptorTests.VariantsAndAsync.cs:505-545).
- **Failure scenario.** A custom file-backed ICacheStorage throws IOException from RemoveAsync (disk full, file locked). POST /orders is processed by the server and returns 201; invalidation throws, the response body is aborted and the caller sees a failed request, so the app retries the non-idempotent POST. Likewise a GetAsync fault fails a GET that the network could have answered, and a SetAsync fault on a 304 fails a request for which a valid stored body is in hand.
- **Fix direction.** Treat storage as best-effort everywhere: a failed lookup is a miss, a failed 304 merge still serves the entry, and a failed removal/invalidation is logged (optionally followed by dropping the index bucket) while the response is delivered untouched.
- **Verifier.** Foreground storage calls are unguarded: Storage.GetAsync in TryLookupAsync (CacheInterceptor.cs:545), Storage.RemoveAsync for a stale non-revalidatable entry (:378), ReplaceStoredEntryAsync/StorePreparedEntryQueuedAsync/RemoveStoredEntryAsync in the 304 path (CacheInterceptor.StreamingDispatch.cs:61-63, :69; the Core methods at CacheInterceptor.cs:1039-1069 have no catch), CompleteModifiedRevalidationAsync aborts the body and rethrows (StreamingDispatch.cs:87-98) and UnsafeInvalidationHandler does the same after a 2xx/3xx to an unsafe method (:141-153). Background stores catch and log (CacheInterceptor.cs:968-987) and :1164-1168 calls mutations best-effort, so the policy is inconsistent. Non-UHttpException faults are wrapped as UHttpErrorType.Unknown (UHttpClient.cs:429-434). The only storage-fault test is the background SetAsync case (Tests/Runtime/Cache/CacheInterceptorTests.cs:138-159, VariantsAndAsync.cs:506). MemoryCacheStorage itself throws only when disposed or cancelled, so this is reachable in practice with a custom store (or a shared storage disposed early); the POST case reports failure for a request the server already processed.

### cache-design-11: Stale-while-revalidate starts one background revalidation per stale hit with no per-key de-duplication or bound

**medium** · architecture · verdict **C** · `Runtime/Cache/CacheInterceptor.cs:352` · RFC 5861 section 3 · also reported as cache-protocol-20, cache-runtime-03

- **Evidence.** Wrap serves the stale entry and unconditionally clones the request and calls StartBackgroundRevalidation (CacheInterceptor.cs:352-363). StartBackgroundRevalidation/RunBackgroundRevalidationAsync (454-511) keep no record of an in-flight revalidation for the base key; the pending-mutation map only sequences storage writes. The entry stays stale until the first revalidation has stored its result, so every hit in that interval launches another conditional request through 'next' (bypassing outer interceptors such as logging and metrics). Tests cover a single stale hit (CacheInterceptorTests.VariantsAndAsync.cs:353).
- **Failure scenario.** A list view requests the same avatar or config URL 50 times while it is inside its stale-while-revalidate window and the origin takes 300 ms: 50 concurrent background conditional GETs are sent, each with its own request clone and context, and 50 stores are queued for one key.
- **Fix direction.** Track in-flight background revalidations per base key (reuse the pending-mutation dictionary pattern) and skip starting a second one; consider a small global cap on concurrent background revalidations.
- **Verifier.** Traced. Runtime/Cache/CacheInterceptor.cs:352-362: every stale-while-revalidate hit serves the entry, clones the request and calls StartBackgroundRevalidation unconditionally. StartBackgroundRevalidation (454-468) and RunBackgroundRevalidationAsync (470-511) only hop to the thread pool and call RevalidateAsync through 'next'; there is no in-flight set keyed by baseKey/storage key (rg for inflight/dedup/coalesce in Runtime/Cache finds nothing). The only per-key sequencing is _pendingMutations, which TryLookupAsync awaits (527-532) but which is populated only when the store is queued after the validation response arrives, so nothing is pending during the network round trip and IsStaleWhileRevalidate (CacheEntry.cs:154-162) stays true for every hit in that interval. QueueBackgroundWork (1212-1225) is just a fault logger, no cap. Tests cover only a single stale hit (CacheInterceptorTests.VariantsAndAsync.cs:353, RangeAndStreaming.cs:342) and dispose-cancel (548). Mitigation, not a refutation: the requests go through 'next', so an inner ConcurrencyInterceptor (role order Cache outside Concurrency, InterceptorOrdering.cs:10-18) or the connection pool bounds simultaneous sockets, but the N conditional GETs, N clones/contexts and N queued stores are still issued. RFC 5861 does not mandate de-duplication, so this is a resource/design defect, not a protocol violation; medium is right. No open issue tracks it.

### cache-protocol-02: With DoNotCacheWithoutFreshness=false and heuristic freshness off, responses without any freshness information are stored with ExpiresAtUtc=null and served as fresh forever

**medium** · rfc-compat · verdict **C** · `Runtime/Cache/CacheInterceptor.cs:631` · RFC 9111 4.2, 4.2.2 · also reported as cache-design-09

- **Evidence.** PrepareEntryForStorage (CacheInterceptor.cs:631-645): when ResolveExpiry returns null and the response is not no-cache/must-revalidate, the entry is only rejected if DoNotCacheWithoutFreshness is true; otherwise it is stored with expiresAtUtc null unless EnableHeuristicFreshness is also set. CacheEntry.IsExpired returns false for a null ExpiresAtUtc (CacheEntry.cs:137-138), so IsFresh (:119-122) is always true and the lookup at CacheInterceptor.cs:342 serves a HIT without ever revalidating, even when the entry has an ETag. ShouldEvict (CacheEntry.cs:166-167) never sweeps it either. MergeNotModifiedEntry repeats the logic at :728-741. Documentation~/Modules/Interceptors.md:153 states 'There is no default TTL: an entry lives exactly as long as the response's own freshness allows'. The only test with the flag off also enables heuristics (CacheInterceptorTests.RepresentationDates.cs:128-131).
- **Failure scenario.** An app sets `new CachePolicy { DoNotCacheWithoutFreshness = false }` to also keep validator-only responses. GET /api/config answers 200 with an ETag and no Cache-Control/Expires. Every later GET of that URL for the life of the process is answered from memory (X-Cache: HIT) and the origin is never contacted again; a default-cacheable 404/410 without freshness is pinned the same way. RFC 9111 section 4.2 treats a response with neither explicit nor heuristic freshness as stale: it must be validated before reuse.
- **Fix direction.** Treat a missing freshness lifetime as lifetime 0 (stale immediately): store such an entry only when it has a validator and revalidate it on each use, or drop it. Reserve ExpiresAtUtc == null for nothing, or give it an explicit 'always validate' meaning in IsFresh. Add a test with the flag off and heuristics off.
- **Verifier.** Traced. PrepareEntryForStorage (Runtime/Cache/CacheInterceptor.cs:631-645): with ResolveExpiry == null the entry is rejected only when DoNotCacheWithoutFreshness is true (:638); heuristic expiry is assigned only when EnableHeuristicFreshness is also set (:643), otherwise the entry is built with expiresAtUtc null (:657). CacheEntry.IsExpired returns false for null (CacheEntry.cs:137-138), so IsFresh (:119-122) is always true and the lookup serves HIT at CacheInterceptor.cs:342; ShouldEvict returns false (CacheEntry.cs:166-167). MergeNotModifiedEntry repeats it (:728-741). Note heuristics are reachable only with DoNotCacheWithoutFreshness=false, so flipping that flag alone gives never-expiring entries, contradicting Documentation~/Modules/Interceptors.md:153. Non-default opt-in configuration; the only test with the flag off also enables heuristics (Tests/Runtime/Cache/CacheInterceptorTests.RepresentationDates.cs:128-131). Lifetime is bounded only by LRU eviction/process life (or not at all with a persistent ICacheStorage).

### cache-protocol-03: must-revalidate is treated like no-cache: a response with `max-age=N, must-revalidate` is never served fresh and is revalidated (or dropped) on every request

**medium** · rfc-compat · verdict **C** · `Runtime/Cache/CacheInterceptor.cs:629` · RFC 9111 5.2.2.2, 5.2.2.4, 4.2.4 · also reported as cache-design-10

- **Evidence.** PrepareEntryForStorage folds three directives into one flag: `mustRevalidate = responseCacheControl.NoCache || responseCacheControl.MustRevalidate || pragmaNoCache` (CacheInterceptor.cs:629; same at :726 for the 304 merge). CacheEntry.IsFresh is `!MustRevalidate && !IsExpired(utcNow)` (CacheEntry.cs:119-122), so the lookup at CacheInterceptor.cs:342 never takes the HIT branch for such an entry: with a validator it sends a conditional request every time (:365-375); without one it removes the entry and refetches (:378-379), so the store was wasted. RFC 9111 section 5.2.2.2 only forbids reuse of the response once it is stale; while fresh it is reusable without validation. The only must-revalidate tests use max-age=0 (CacheInterceptorTests.Representation.cs:154, DecodedRevalidation.cs:42).
- **Failure scenario.** Origin sends `Cache-Control: max-age=3600, must-revalidate` (a very common combination) with an ETag. Expected: one network request per hour. Actual: every request performs a conditional round trip; without ETag/Last-Modified every request is a full download and a store that is thrown away on the next lookup. The cache is ineffective for these responses.
- **Fix direction.** Keep two flags on the entry: 'always validate' (no-cache, Pragma) and 'no stale reuse' (must-revalidate). IsFresh should consult only the first; IsStaleWhileRevalidate and any future stale serving consult both. CacheEntry's public constructor needs the extra field (public API change).
- **Verifier.** Code is as described: mustRevalidate = NoCache || MustRevalidate || pragmaNoCache (Runtime/Cache/CacheInterceptor.cs:629, :726) and IsFresh = !MustRevalidate && !IsExpired (CacheEntry.cs:119-122), so `max-age=3600, must-revalidate` never takes the HIT branch at :342; with a validator every request is a conditional round trip (:365-375), without one the entry is removed and refetched (:378-379) after the body was copied for the store. No comment, phase doc or issue documents this as a deliberate trade-off (rg must-revalidate over Development~/docs/phases and Documentation~ finds nothing); tests only use max-age=0 with must-revalidate. Correction to the finding: this is not an RFC violation (a cache may always validate); it is an effectiveness defect that makes the cache useless for a common header combination. No stale or wrong data is served.

### cache-protocol-05: Large delta-seconds values throw OverflowException from TimeSpan.FromSeconds instead of being clamped; a 304 carrying one fails the caller's request

**medium** · rfc-compat · verdict **C** · `Runtime/Cache/CacheInterceptor.Parsing.cs:99` · RFC 9111 1.2.2

- **Evidence.** max-age, s-maxage and stale-while-revalidate are parsed with long.TryParse and passed to TimeSpan.FromSeconds (CacheInterceptor.Parsing.cs:80-86, 93-99, 106-112). TimeSpan.FromSeconds throws OverflowException above ~922,337,203,685 s, so any 12- to 19-digit value throws out of ParseCacheControl; a value of 20+ digits fails long.TryParse and the directive is silently dropped (falling back to Expires, :140-159). RFC 9111 section 1.2.2 requires treating such values as 2^31. Callers: PrepareEntryForStorage (CacheInterceptor.cs:593, background store: the response is not cached and 'Background store failed' is logged), MergeNotModifiedEntry (:722, called in the foreground from CompleteNotModifiedRevalidationAsync, CacheInterceptor.StreamingDispatch.cs:50, after the 304 body was disposed) and the request-header parse in Wrap (:318). Tests cover only the Expires-Date overflow (CacheInterceptorTests.RepresentationDates.cs:95-118).
- **Failure scenario.** A stale entry is revalidated and the origin (or a hostile peer) answers 304 with `Cache-Control: max-age=999999999999`. MergeNotModifiedEntry throws OverflowException inside RevalidationHandler.OnResponseStartAsync: the caller gets a handler fault (not a UHttpException and not the stored response) for a revalidation that succeeded, and this repeats on every request until the entry is removed. On a 200 the same header means the response is never cached; `max-age=99999999999999999999, Expires: <past>` is treated as already expired instead of long-lived.
- **Fix direction.** Parse delta-seconds with one helper that accepts only digits, saturates on overflow and clamps to 2^31 seconds (section 1.2.2) before building the TimeSpan; use it for all three directives and for the request side. Add tests for 12-digit and 20-digit values on 200 and 304.
- **Verifier.** Traced. max-age, s-maxage and stale-while-revalidate go long.TryParse -> TimeSpan.FromSeconds without a bound (Runtime/Cache/CacheInterceptor.Parsing.cs:80-86, 93-99, 106-112); FromSeconds throws OverflowException above ~9.22e11 s, so 12- to 19-digit values throw out of ParseCacheControl, and 20+ digit values fail long.TryParse and the directive is dropped (fallback to Expires, :140-159). RFC 9111 section 1.2.2 requires treating such values as 2^31. No catch on the paths: MergeNotModifiedEntry (:722) runs in the foreground inside CompleteNotModifiedRevalidationAsync (CacheInterceptor.StreamingDispatch.cs:50) after the 304 body was disposed, so the exception leaves RevalidationHandler.OnResponseStartAsync and fails the caller; StoreResponseAsync catches only OperationCanceledException (CacheInterceptor.cs:959), so on a 200 the store faults and is logged by QueueBackgroundWork (:1212-1225); the request-side parse at :318 is also unguarded. Tests cover only the Expires-Date overflow (CacheInterceptorTests.RepresentationDates.cs:95-118). Impact is limited to the responses of the origin that sends such a value (unlike cache-protocol-01), hence medium.
