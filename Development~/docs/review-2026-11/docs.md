# Documentation and samples: review findings

Scope: README, Documentation~, Samples~ against the real API and defaults. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**documentation and sample accuracy** (40 findings, 36 files read in full). The customer docs are in better shape than usual for a pre-release: 61 of 67 C# snippets and all five samples are compiled by the shadow build, the interceptor order, cleartext policy, proxy rules and BouncyCastle opt-in are described accurately, and defaults quoted in Interceptors.md and PlatformNotes.md match the code. The main risk is that the doc gate is compile-only: the Plugins example throws on every run, the documented WebSocket entry points lose options and early messages, and every relative-URL example uses a leading slash that Unix-like runtimes (macOS, Linux, iOS, Android) parse as a file:// URI, with no test that sends such a request. Release metadata is ahead of reality: README tells users to install tag v1.0.0-pre.1, which does not exist on GitHub, and CHANGELOG has had no entry for about 100 later commits and contradicts the code on HTTP/2 through CONNECT. Several claims are stronger than the code (timeline traces with DNS/SSL/TTFB, off-main-thread texture decode, adaptive concurrency/retries, Linux 'verified', zero-allocation WebSocket), and security-relevant guidance is missing where defaults are foot-guns (AuthInterceptor sends its token to every origin the client talks to, client proxy/cleartext policy is dropped for standalone requests and WithMetadata(dictionary), streaming bodies have no deadline). XML docs on UHttpStreamingResponse are absent and several on UHttpClientOptions/UHttpResponse are stale.

### docs-accuracy-02: README and CHANGELOG tell users to install tag v1.0.0-pre.1, but the public repository has no tags and no releases

**medium** · docs · verdict **C** · `README.md:34` · issue #614 · reviewer rated it high

- **Evidence.** README.md:25-47 says 'Install a tagged release', gives https://github.com/fatal10110/turboHTTP.git#v1.0.0-pre.1 for the Package Manager and manifest.json, and says to keep the tag. CHANGELOG.md:8 dates [1.0.0-pre.1] 2026-11-02 and :22 repeats the URL. 'gh api repos/fatal10110/turboHTTP/tags' returns [], 'gh release list' is empty and 'git ls-remote --tags origin' prints nothing (repository is PUBLIC). .github/workflows/release.yml only runs when a v*.*.* tag is pushed. Issue #101 covers versioning in general, not this.
- **Failure scenario.** A user pastes the documented Git URL into Package Manager: Unity cannot resolve revision v1.0.0-pre.1 and the install fails. Dropping the fragment installs moving main, which README warns against, and whose behaviour no CHANGELOG section describes.
- **Fix direction.** Push the v1.0.0-pre.1 tag (or the next pre-release tag from current main with a matching CHANGELOG section), or until then word the README as 'no tagged release yet' and give the commit-hash form.
- **Verifier.** README.md:25-47 and CHANGELOG.md:8,22 give https://github.com/fatal10110/turboHTTP.git#v1.0.0-pre.1. 'gh api repos/fatal10110/turboHTTP/tags' returns [], 'gh release list' is empty, 'git ls-remote --tags origin' prints nothing, and the repository is public, so the documented Git URL cannot resolve. Cutting the first tag is a known open step: #101 was rescoped on 2026-11-02 to the release process (semver tags v1.0.0-pre.N, a GitHub Release per tag, Git URL instructions) and Development~/docs/implementation-journal/2026-11-release-layout.md:63 lists 'Cutting the first tag v1.0.0-pre.1' as not done. What #101 does not say is that the README already presents the tag as installable. Medium: nothing has been released yet, but the first documented step fails.

### docs-accuracy-03: The documented IHttpPlugin example declares PluginCapabilities.None and then calls RegisterInterceptor, which throws for a plugin without interceptor capabilities

**medium** · docs · verdict **C** · `Documentation~/APIReference.md:350` · issue #592

- **Evidence.** APIReference.md:346-359: CustomLoggerPlugin has 'Capabilities => PluginCapabilities.None' and InitializeAsync calls context.RegisterInterceptor(new LoggingInterceptor(...)). PluginContext.RegisterInterceptor (Runtime/Core/PluginContext.cs:50-62) throws PluginException 'Plugin does not have interceptor capabilities.' unless ObserveRequests, ReadOnlyMonitoring, MutateRequests, MutateResponses or HandleErrors is set; UHttpClient.RegisterPluginAsync wraps it as 'failed during initialization' (UHttpClient.cs:252-259). The block is a declaration snippet, so Tools~/ci/doc_snippets.py compiles it, which is why CI passes. No customer doc explains PluginCapabilities.
- **Failure scenario.** A user copies the Plugins example and calls client.RegisterPluginAsync(new CustomLoggerPlugin()): it always throws PluginException and no interceptor is registered.
- **Fix direction.** Give the example the capability it needs (ObserveRequests for a logging interceptor), document what each PluginCapabilities flag allows, and add a runtime test that registers the documented plugin.
- **Verifier.** Documentation~/APIReference.md:346-359 declares Capabilities => PluginCapabilities.None (value 0, Runtime/Core/IHttpPlugin.cs:23) and calls context.RegisterInterceptor in InitializeAsync. PluginContext.RegisterInterceptor throws PluginException 'Plugin does not have interceptor capabilities.' when none of ObserveRequests, ReadOnlyMonitoring, MutateRequests, MutateResponses, HandleErrors is set (Runtime/Core/PluginContext.cs:50-62); RegisterPluginAsync passes plugin.Capabilities unchanged and wraps the throw as 'failed during initialization' (Runtime/Core/UHttpClient.cs:236-259). No path relaxes the check, so the documented example always fails at registration. PluginCapabilities appears nowhere else in Documentation~, README or Samples~. The snippet only compiles in CI, which is why it passes.

### docs-accuracy-05: client.WebSocket(url) returns an already connected bridge, and messages that arrive before the caller subscribes OnMessage are disposed; the documented snippet subscribes after the await

**medium** · best-practices · verdict **C** · `Documentation~/Modules/WebSocket.md:27` · issue #606

- **Evidence.** WebSocket.md:27-28: 'IWebSocketClient ws = await httpClient.WebSocket(url); ws.OnMessage += ...'. UnityWebSocketExtensions.WebSocket (Runtime/Unity.WebSocket/UnityWebSocketExtensions.cs:38-41) builds the bridge and awaits ConnectAsync before returning. The bridge subscribes the inner client's OnMessage in its constructor (UnityWebSocketBridge.cs:59), which puts the inner client in event mode, and HandleMessage disposes the message when the bridge's own OnMessage has no handler yet (UnityWebSocketBridge.cs:216-226). OnConnected can never be observed for the same reason. The example host echo.websocket.events sends a greeting as soon as the connection opens.
- **Failure scenario.** Server sends a first message right after the handshake (auth challenge, snapshot, greeting). The await resumes on the main thread a frame later; the receive loop has already raised the message, the bridge found no handler and disposed it. The application never sees it and no drop event or warning is raised.
- **Fix direction.** Offer an overload that takes handlers or a configure callback before connecting (or return an unconnected bridge), or buffer messages in the bridge until the first OnMessage subscription; document the ordering in WebSocket.md.
- **Verifier.** client.WebSocket(uri) constructs the bridge and awaits ConnectAsync before returning (Runtime/Unity.WebSocket/UnityWebSocketExtensions.cs:38-41). The bridge subscribes the inner OnMessage in its constructor (UnityWebSocketBridge.cs:59), so the inner listener takes the event path for every message (Runtime/WebSocket/WebSocketClient.cs:409-431), and HandleMessage disposes the event copy when the bridge's own OnMessage has no handler (UnityWebSocketBridge.cs:216-226). HandleConnected likewise returns when OnConnected is null (:208-214), so OnConnected can never be seen through this entry point. WebSocket.md:27-28 subscribes after the await and no doc states the ordering. One correction to the finding: the message is not lost entirely. PublishDroppingOldest also puts the original in the pull queue (WebSocketClient.cs:429, :466-470), so bridge.ReceiveAsync can still return it until newer messages evict it; only event-only consumers, the documented pattern, miss it. A caller can avoid it by building UnityWebSocketBridge or UnityWebSocketClient, subscribing, then connecting.

### docs-accuracy-07: AuthInterceptor attaches the token to every origin a client is used for; the Authentication sample says it is never sent to another host and no doc warns about third-party URLs

**medium** · security · verdict **C** · `Samples~/04-Authentication/AuthenticationExample.cs:12` · RFC 9110 section 11.6.2 · issue #618

- **Evidence.** The sample comment (:12-13) says the interceptor 'keeps the token bound to the origin it was first used with, so it is never sent to another host'. AuthInterceptor.IsBoundOrigin binds per RequestContext, that is per call: the first hop of every request is always the bound origin (Runtime/Auth/AuthInterceptor.cs:112-129), so only redirect hops are protected. There is no allowed-origin option. Auth.md:18 words it correctly ('for each call') but gives no guidance for requests to other hosts through the same client.
- **Failure scenario.** A client with BaseUrl https://api.game.com and AuthInterceptor is also used for client.GetTextureAsync('https://cdn.thirdparty.net/a.png') or a user-supplied URL: the request carries Authorization: Bearer <api token> to the third party.
- **Fix direction.** Correct the sample comment, add a warning to Auth.md to use a dedicated client per authenticated origin, and consider an optional origin allow-list on AuthInterceptor so the non-negotiable 'credentials stay with their origin' is enforceable.
- **Verifier.** IsBoundOrigin stores the first request Uri in RequestContext state and compares later hops against it (Runtime/Auth/AuthInterceptor.cs:112-129). Each send creates a new RequestContext (Runtime/Core/UHttpClient.cs:395), so the first hop of every call is the bound origin and gets the token; only redirect hops are filtered. There is no origin allow-list. The class XML doc (AuthInterceptor.cs:13-20) and Auth.md:18 ('for each call') describe this correctly; the sample comment at Samples~/04-Authentication/AuthenticationExample.cs:12-13 ('bound to the origin it was first used with, so it is never sent to another host') does not, and neither Auth.md nor Interceptors.md warns against using an authenticated client for other hosts. This is conventional behaviour for an auth interceptor, so the defect is the sample's claim plus the missing guidance; the token does go to any host a shared client is used for, which the project's own 'Authorization stays with its origin' rule forbids.

### docs-accuracy-08: Docs say the request timeout 'covers each request', but a streaming response body has no deadline, and neither the docs nor the FileDownload sample tell the caller to bound body reads

**medium** · docs · verdict **C** · `Documentation~/Modules/Core.md:130` · issue #596

- **Evidence.** Core.md:130: 'WithTimeout (or DefaultTimeout) covers each request'. For a streaming dispatch the HTTP/1.1 body source gets CancellationToken.None instead of the timeout token (RawSocketTransport.cs:1825-1829) and the timeout source is disposed when the dispatch returns at the headers (:439-441). The streaming example at Core.md:98-109 passes a ct declared as default, QuickStart.md:167 recommends streaming or FileDownloader for large downloads, FileDownloader streams (Runtime/Files/FileDownloader.cs:399) with no stall bound, and Samples~/03-FileDownload/FileDownloadExample.cs:38 passes no token.
- **Failure scenario.** Mobile network drops silently in the middle of a streamed download (half-open connection): Body.ReadAsync / FileDownloader.DownloadFileAsync never completes, the connection and its per-host permit stay held, and no Timeout error is raised.
- **Fix direction.** State in Core.md and APIReference.md that the timeout ends when the response headers arrive for streaming responses, show a per-read or overall CancelAfter in the streaming and download examples, and consider an idle-read timeout option for streaming bodies.
- **Verifier.** DispatchCoreAsync creates the timeout source with 'using' (Runtime/Transport/RawSocketTransport.cs:439-441), and for a streaming dispatch the HTTP/1.1 body source gets CancellationToken.None instead of that token (:1825-1829). Http11ResponseBodySource uses the requestTimeout argument only for the error text (Runtime/Transport/Http1/Http11ResponseBodySource.cs:63, :706-712). I looked for another bound and found none that covers a silent peer: StreamingOptions.Http2StallTimeoutSeconds covers a consumer that stops reading and blocked writes (Runtime/Core/StreamingOptions.cs:70-79), and SO_KEEPALIVE is enabled with OS default timing, about two hours (Runtime/Transport/Connection/HappyEyeballsConnector.cs:457-474). FileDownloader streams with only the caller's token (Runtime/Files/FileDownloader.cs:399) and the sample passes none (Samples~/03-FileDownload/FileDownloadExample.cs:38). Core.md:130 says the timeout 'covers each request'; no file in Documentation~ nor the DefaultTimeout/Timeout XML docs says it ends at the headers for streaming. No open issue tracks it.
