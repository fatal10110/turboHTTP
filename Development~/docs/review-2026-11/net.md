# Transport core: review findings

Scope: RawSocketTransport, connection pool, socket I/O modes, proxy/CONNECT, Happy Eyeballs, NAT64. Part of the [2026-11 full-library review](README.md) at commit `0e0f1bc`.

Verdict column: **C** confirmed by the verifier re-tracing the code, **P** plausible (depends on runtime, device or peer behaviour that a static review cannot settle), **U** not verified (low severity findings were not sent to a verifier).

## Reviewer summaries

**architecture, code quality, best practices, pluggability** (20 findings, 30 files read in full). The transport core is functionally careful (ownership hand-offs, IL2CPP catch-ladder rules, #384 descriptor holds are all commented and mostly consistent), but its structure is the main risk: RawSocketTransport is a 2434-line class that owns registration, routing, HTTP/1.1 retry, proxy/CONNECT, Expect-continue and error mapping, and its copy-pasted blocks (HTTP/2 hand-off x4, stale retry x2, TLS wrap x2, socket channels x2) have already diverged in behaviour. Proxy routing is decided in Core at request creation and smuggled to the transport through the request metadata bag, so the transport trusts an unvalidated object and cannot re-decide per hop. For build size, nothing in the slice is strippable when unused: the whole HTTP/2 stack (8.3k lines, never negotiable with the default SslStream backend on Unity runtimes), both alternative socket channels, proxy and NAT64 are statically reachable, and link.xml adds preserve=all rules that its own comments say are no longer needed (they also root dead code and widen List<T>/SslStream preservation for the whole app). Registration works through the Complete bootstrap; the secondary ModuleInitializer path uses replace semantics and can silently overwrite a custom registration on runtimes that run it lazily. Unsafe code is not used anywhere in the reviewed core (only two desktop TLS verifier files need it). Public surface is wider than intended (pool, lease, pooled connection, connector) and several public option/proxy types have no XML docs.

**RFC conformance, protocol implementation, security** (21 findings, 31 files read in full). The transport core is in good shape on the hard security items: header/CONNECT injection is closed (token/CR/LF/NUL validation, validated wire host for Host, absolute-form and CONNECT authority), the CONNECT reply and both 407 drains are bounded, proxy Basic credentials go out only after a Basic challenge and only with AllowPlaintextProxyAuth, the cleartext policy is applied before any socket for both the target and the proxy leg, and the RFC 9110 9.2.2 replay rules for stale HTTP/1.1 connections and HTTP/2 unprocessed streams are implemented carefully. The main risks are behavioural rather than exploitable: the non-Expect HTTP/1.1 send path never reads an early error response after a body write fails (RFC 9112 9.5), the default 10 s first-byte watchdog plus its retry-lease stopgap turns a slow but healthy idempotent endpoint into a hard failure on reused connections, and proxy selection is decided once in UHttpClient and never by the transport (request-level WithProxy skips validation and the bypass list, and a redirect keeps the first hop's decision). Happy Eyeballs has two timing defects with real cost: no attempt starts when the in-flight one fails fast (every localhost connect to an IPv4-only listener waits 250 ms), and the default cap of two in-flight attempts stops the race after two blackholed addresses. The proxy path lacks the direct path's stale-connection hardening (no first-byte watchdog, retry takes the next idle connection) and tunnels are keyed without the proxy credentials. The remaining items are low-severity RFC gaps (1xx to CONNECT, NAT64 Well-Known Prefix with non-global literals, NO_PROXY=*) and error-model edges.

**performance, resource management, concurrency, platform compatibility** (24 findings, 31 files read in full). The default NetworkStream path is in good shape for this lens: lease/permit accounting in TcpConnectionPool is exactly-once on every path I traced, SocketHandleHold/HoldingNetworkStream keep the descriptor until pending I/O ended, the abandon gate is bounded, Happy Eyeballs owns and observes every attempt, and header-phase cancellation really tears the socket down. The main risks sit in the two opt-in socket modes: a PollSelect channel disposed from a continuation on its own poll thread joins itself for 500 ms and abandons its buffers, SAEA can touch its pooled buffers after Dispose returned them (receive copy-out and next-chunk copy-in), and both channels' own token registrations close the socket first, bypassing the shutdown-first order that #384/#410 introduced. On the performance side, a burst of requests to a cold HTTP/2 origin dials one TCP+TLS connection per request and throws all but one away, Happy Eyeballs waits out the stagger timer after a fast failure (every new connection to an IPv4-only localhost server costs 250 ms), the idle queue is FIFO (stalest connection first), and one HTTP/1.1 request on a reused connection costs three CancellationTokenSources, two timers and about seven async frames. Transport/pool disposal neither cancels in-flight HTTP/1.1 exchanges nor wakes requests queued on a per-host permit. Documented trade-offs I did not report as defects: PollSelect's thread per connection with 50 wake-ups per second while a receive is pending (#38), the baselined sync Read/Write overrides, and the 1 s process-wide abandon gate.

## Medium (15)

### net-design-01: RawSocketTransport is a 2434-line multi-responsibility class whose HTTP/2 hand-off sequence is copy-pasted four times and has already diverged

**medium** · architecture · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:622`

- **Evidence.** One sealed class holds: factory registration and capability probing (79-139), dispatch entry and the error-model mapping (141-258, 746-836), HTTP/2 routing with extra-dial claims (583-646, 1029-1045), the HTTP/1.1 stale-retry policy (284-395, 648-739), the whole proxy feature - forward proxy, CONNECT tunnel, Basic 407 handling, tunnel pool keys, lease rebinding (838-1296, 1310-1581, about 730 lines), the first-byte watchdog (1969-2016) and the Expect: 100-continue state machine (2018-2364, about 350 lines). The sequence 'lease.TransferOwnership(); GetOrCreateAsync; lease = null; DispatchOnH2ConnectionAsync' exists four times: 622-644 and 964-992 wrap GetOrCreateAsync in a try/catch that calls FallBackAfterFailedExtraDial and call ReleaseExtraDial afterwards; the two stale-retry copies 686-696 and 1133-1150 have neither. The 'ShouldSurfaceCommittedNonReplayableBodyFailure -> CreateCommittedNonReplayableBodyFailure' clause exists four times (715-723, 730-738, 1168-1176, 1183-1191). The comment at 510-511 says one filtered clause, not two, because IL2CPP nests the clauses of a filtered try (#320), yet the try at 650 and the try at 1091 each carry two filtered clauses (665+730, 1106+1183); they are only safe because the two filters happen to be mutually exclusive on request.Content.Replayability.
- **Failure scenario.** A change to one hand-off or retry copy (as already happened with the #238 extra-dial fallback and the #47 fresh-socket retry, see net-design-02) is not applied to its siblings, and nothing in the type system or tests points at the other three places. A future edit that makes the two filters of 665/730 overlap re-introduces the #320 IL2CPP mis-catch with no compiler or analyzer signal.
- **Fix direction.** Split by responsibility: a ProxyConnector (forward/CONNECT/auth, owns tunnel pool keys), an Http11Exchange (send, Expect-continue, first-byte watchdog, stale retry as one method parameterised by a lease factory), an H2 hand-off helper used by all four sites, and keep RawSocketTransport as the router plus error mapping. Make the stale retry one implementation that takes 'acquire fresh lease' as a delegate so direct and proxy paths cannot diverge.
- **Verifier.** File is 2434 lines and holds every responsibility listed. The h2 hand-off exists four times: RawSocketTransport.cs:622-644 and :964-992 with the FallBackAfterFailedExtraDial catch, :686-696 and :1133-1150 without. That difference is not itself a bug: both stale-retry copies run after the claim was released (:646, :994), so there is nothing to fall back to; the finding stands as duplication, not as a defect at those two sites. The committed-non-replayable clause exists four times (:715-723, :730-738, :1168-1176, :1183-1191), and the two inner copies are dead code: the enclosing clause is entered only when CanRetryHttp11RequestAfterTransportFailure passed, i.e. Replayability != NonReplayable (:288-289), while the inner filter requires NonReplayable (:372). The tries at :650 and :1091 each carry two filtered clauses (:665+:730, :1106+:1183) although the comments at :510-511 and :748-751 state that IL2CPP lets a later clause catch what an earlier clause threw (#320); they are safe only because the two filters are mutually exclusive on Replayability, and nothing enforces that. #182 tracks oversized files in Core only (PluginContext, MainThreadDispatcher, UHttpClient, DecompressionHandler), not this one.

### net-design-02: The HTTP/1.1 stale-connection retry exists in a direct and a proxy copy, and only the direct copy received the fresh-socket retry and the first-byte watchdog

**medium** · code-smell · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:1093` · RFC 9112 Section 9.3.1 · also reported as http1-design-01

- **Evidence.** Direct copy (648-729): DispatchOnLeaseAsync is called with firstByteTimeout: GetReusedConnectionFirstByteTimeout(lease, request) (652-659); the retry leases through _pool.GetNewConnectionAsync (683, skipIdle: true, TcpConnectionPool.cs:434-438) and arms the watchdog again with retryLease: true (708-709). Proxy copy (DispatchProxyHttp11WithRetryAsync 1054-1197): DispatchOnLeaseAsync is called at 1093-1100 and 1155-1162 with the positional interceptBasicProxyChallenge only, so firstByteTimeout is default(TimeSpan) and SendOnLeaseAsync skips the watchdog (1939); the retry leases through AcquirePreparedProxyLeaseAsync (1121) -> _pool.GetConnectionAsync(..., poolKeyOverride, ct) (1218-1223) with skipIdle: false, i.e. the next idle connection. ConnectionPoolOptions.ReusedConnectionFirstByteTimeout documents the behaviour without a proxy exception. No test under Tests/Runtime covers a silent or doubly-stale reused proxy connection (rg FirstByte finds only the direct-path fixtures).
- **Failure scenario.** Editor or desktop player behind an http:// proxy, two idle keep-alive connections to the proxy (or two idle tunnels to one origin), NAT drops both. An idempotent GET on the first one: if it is silent the request waits for the full request timeout (no 10 s watchdog); if it faults, the single retry dequeues the second dead idle connection and the request fails with NetworkError, where the direct path would have recovered on a new socket.
- **Fix direction.** Fold both copies into one retry routine that takes the 'new connection' lease factory as a parameter (for proxies: GetNewConnectionAsync on the proxy key followed by the tunnel setup) and always passes the first-byte bound.
- **Verifier.** Traced. Direct path: first attempt passes firstByteTimeout: GetReusedConnectionFirstByteTimeout(lease, request) (RawSocketTransport.cs:652-659), the retry leases with _pool.GetNewConnectionAsync (:683, skipIdle: true, TcpConnectionPool.cs:434-438) and arms the watchdog again (:708-709). Proxy path: DispatchProxyHttp11WithRetryAsync calls DispatchOnLeaseAsync with seven positional arguments (:1093-1100, :1155-1162), the seventh being interceptBasicProxyChallenge, so firstByteTimeout stays default(TimeSpan) (signature :1765-1773) and SendOnLeaseAsync takes the unguarded branch (:1939-1946). The retry leases through AcquirePreparedProxyLeaseAsync (:1121) -> _pool.GetConnectionAsync(..., poolKeyOverride, ct) (:1218-1223), which is skipIdle: false (TcpConnectionPool.cs:417-425), so it can dequeue the next idle proxy connection or tunnel. Result: a silent reused proxy connection waits for the full request timeout, and a faulting one can retry onto a second dead idle one. No guard found, and no test covers it (rg FirstByte finds only Tests/Runtime/Transport/Http1 fixtures, none under Tests/Runtime/Proxy). #364 covers the direct-path retry only. RFC 9112 Section 9.3.1 makes the retry optional, so this is a robustness gap against the documented ReusedConnectionFirstByteTimeout behaviour, not a protocol violation.

### net-protocol-01: HTTP/1.1 non-Expect send path never reads the server's early final response when the request body write fails

**medium** · rfc-compat · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:1923` · RFC 9112 Section 9.5 · also reported as http1-protocol-01

- **Evidence.** SendOnLeaseAsync (RawSocketTransport.cs:1923-1946) awaits Http11RequestSerializer.SerializeAsync for head and whole body and only then calls ParseHeadAsync. An IOException/SocketException from a body write propagates straight out (the finally at 1933 only records bytes sent); nothing attempts to read a response that is already in the receive buffer. DispatchAttemptAsync then either replays the request on a fresh connection (reused connection + idempotent, 665-669), maps it to 'Connection failed after a non-replayable request body started sending' (730-737), or to NetworkError (805-808). Only the Expect: 100-continue path captures the send failure and still reads the final head (TrySendRequestBodyAsync 2338-2364, ReadExpectContinueFinalHeadAsync 2190-2223, CompleteExpectContinueHead 2234-2264, which cites RFC 9112 9.5), and auto-Expect is off by default (StreamingOptions.AutoExpectContinueThresholdBytes is null, StreamingOptions.cs:27). The only test of the rule is the Expect path (RawSocketTransportConnectionReuseTests.ExpectContinue_BodySendFailure_ErrorFinalResponse_ReturnedAndConnectionNotReused).
- **Failure scenario.** PUT/POST of a 50 MB body without Expect to a server that answers 413/401/403 after the headers and closes: the client's next body write fails with a reset, the caller gets UHttpErrorType.NetworkError (or, for an idempotent PUT on a reused connection, the whole upload is started again on a new connection and fails the same way) and never sees the status code or the error body the server sent.
- **Fix direction.** On a body-write failure in the one-shot path, do what the Expect path already does: keep the send exception, try to parse a final head from the connection (bounded by the request token), return a non-2xx head with KeepAlive=false, and only surface the send failure when no final response can be read. Also stop sending the body once a final head is available.
- **Verifier.** Traced. SendOnLeaseAsync (RawSocketTransport.cs:1923-1936) awaits Http11RequestSerializer.SerializeAsync for head+body; the finally only records bytes sent, and ParseHeadAsync (:1941/:1958) is reached only when the whole write succeeded. A write IOException/SocketException goes to the stale filter (:665-669; CanRetryHttp11RequestAfterTransportFailure :284-300 returns true for any idempotent replayable request, so a PUT on a reused connection is re-uploaded on GetNewConnectionAsync :683), to CreateCommittedNonReplayableBodyFailure (:730-737), or to NetworkError (:805-808). Only the Expect path keeps the send failure and still reads the final head (TrySendRequestBodyAsync :2338-2364, ReadExpectContinueFinalHeadAsync :2190-2223, CompleteExpectContinueHead :2234-2264), and auto-Expect is off unless AutoExpectContinueThresholdBytes is set (:420-422). No guard or test for the one-shot path found. RFC 9112 Section 9.5 is a SHOULD and an RST can discard the unread response on some stacks, so the fix is best effort, but the client never tries.

### net-protocol-02: Default first-byte watchdog fails any idempotent request whose server needs more than 10 s to answer when the first attempt used a pooled connection

**medium** · protocol-impl · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:344` · RFC 9112 Section 9.3.1

- **Evidence.** GetReusedConnectionFirstByteTimeout (344-354) arms the watchdog for every idempotent, replayable request on a reused lease with PlatformConfig.DefaultReusedConnectionFirstByteTimeout = 10 s (PlatformConfig.cs:42-44). AwaitFirstResponseByteAsync (1981-2016) disposes the connection at expiry and throws IOException, which the stale filter (665-669) turns into a second send on GetNewConnectionAsync (683). That retry is armed too (retryLease: true, 708-709; #364/#384 stopgap), and its expiry is not retried: the IOException maps to NetworkError (805-806). A server that is simply slow to produce its first byte is indistinguishable from a dead connection, so the request is sent twice and fails after 2 x 10 s although request.Timeout (30 s desktop, 45 s mobile) has not expired. The same request on a non-pooled connection has no watchdog and succeeds. ConnectionPoolOptions.ReusedConnectionFirstByteTimeout documents the mechanism but not that slow endpoints fail; RetryLeaseFirstByteWatchdogTests asserts the retry's hard failure.
- **Failure scenario.** GET long-poll or report endpoint with a 12-25 s time to first byte: the first call on a new connection succeeds; the next call reuses the pooled connection, is aborted at 10 s, re-sent on a new socket (the server now runs it twice) and fails with NetworkError at 20 s. Behaviour depends on whether an idle connection happened to be pooled.
- **Fix direction.** Do not arm the bound on the fresh retry connection once the #384 descriptor hold is in place (the retry should wait for the request timeout as documented for 'any other fresh connection'), or let the retry's expiry fall back to waiting instead of failing. Document that the bound is a time-to-first-byte limit for idempotent requests and consider a larger default or a liveness probe (SO_KEEPALIVE result, zero-byte read) instead of a response deadline.
- **Verifier.** Traced. GetReusedConnectionFirstByteTimeout (:344-354) arms 10 s (PlatformConfig.cs:42-44) for every idempotent replayable request on a reused lease; AwaitFirstResponseByteAsync (:1981-2016) disposes the connection and throws IOException; the filter at :665-669 resends on GetNewConnectionAsync (:683) with retryLease:true (:708-709); the second expiry is thrown from inside the catch handler, so the sibling filter at :730 does not apply and MapDispatchAttemptFailure maps it to NetworkError (:805-806) at about 20 s, below the 30/45 s request timeout. A slow first byte is indistinguishable from a dead connection, and the request is sent twice. Partly weakens the finding: the public doc does state it (ConnectionPoolOptions.cs:146-160: 'The fresh connection of that one retry is bounded by the same time; when it stays silent too, the request fails with no further attempt'), and the retry arming is a recorded stopgap (PR #405, listed under #384's suggested fix, #364). No open issue tracks the cost for slow endpoints (long-poll GET, report endpoints with TTFB above 10 s), which fail only when an idle connection happens to be pooled. The trade-off is deliberate; its cost for legitimate slow responses is real and untracked.

### net-protocol-03: Proxy selection and bypass are decided once in UHttpClient for the first URI; the transport reuses that decision for redirect targets and never evaluates BypassList itself

**medium** · security · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:1310` · also reported as core-design-03, mw-protocol-10, net-design-03

- **Evidence.** ResolveProxySettings (1310-1326) returns whatever ProxySettings object is in request metadata; it never calls ProxyBypassMatcher or looks at the request URI or scheme. The only caller of ProxyEnvironmentResolver.Resolve is UHttpClient.ApplyDefaultMetadata (UHttpClient.cs:753-758), which runs when the request is created. RedirectInterceptor builds each follow-up request from CloneMetadata(source.Metadata) (RedirectInterceptor.cs:140-141), so the follow-up carries the first hop's ProxySettings (or its absence) to a different host and scheme. A request-level WithProxy(settings) (ProxyRequestBuilderExtensions.cs:7-15) skips resolution entirely, so its BypassList is dead data.
- **Failure scenario.** (a) NO_PROXY=.corp.internal, HTTP_PROXY set: GET http://public.example answers 302 to http://wiki.corp.internal/...; the follow-up, with its path, query and cookies, is sent to the external proxy although the host is on the bypass list. (b) Only HTTP_PROXY is set and AllowHttpProxyFallbackForHttps is false: http://a.example redirects to https://a.example and the https hop is CONNECT-tunneled through HTTP_PROXY, which the configuration forbids. (c) The first URI was bypassed, the redirect target is not: the follow-up goes direct instead of through the proxy.
- **Fix direction.** Resolve the proxy per dispatch against the URI actually being sent: either have the transport apply BypassList/scheme rules to request.Uri in ResolveProxySettings, or carry the unresolved configuration in metadata and have the redirect hop re-run ProxyEnvironmentResolver.Resolve. Add redirect tests across a bypass boundary and across http->https with only HTTP_PROXY set.
- **Verifier.** Traced. ProxyEnvironmentResolver.Resolve is called only from UHttpClient.ApplyDefaultMetadata (UHttpClient.cs:753-758) with the first URI; bypass and scheme rules live only there (ProxySettings.cs:234-258, :281-303). RawSocketTransport.ResolveProxySettings (:1310-1326) returns the metadata object and never looks at request.Uri or BypassList (no ProxyBypassMatcher reference anywhere in Runtime/Transport). RedirectInterceptor.BuildRedirectRequest copies the metadata dictionary (RedirectInterceptor.cs:140-141, :210-216) and dispatches the follow-up through next, not through UHttpClient, so the first hop's decision (proxy object, or its absence) applies to every redirect target. All three scenarios hold: bypass-listed redirect target sent to the proxy, https hop tunneled through HTTP_PROXY with AllowHttpProxyFallbackForHttps false, and a non-bypassed target sent direct after a bypassed first hop. No redirect test in Tests/Runtime/Proxy and no proxy handling in RedirectHandler.cs.

### net-protocol-04: Request-level ProxySettings are never validated: an https:// (or any non-http) proxy address is silently contacted in cleartext, on port 80 when the URI has no explicit port

**medium** · security · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:861`

- **Evidence.** ProxySettings.Validate (ProxySettings.cs:47-65) rejects non-http schemes, but it is only called from ProxyEnvironmentResolver.Resolve for UHttpClientOptions.Proxy (ProxySettings.cs:232). WithProxy (ProxyRequestBuilderExtensions.cs:7-15) stores a clone without validating, and UHttpClient skips resolution when the key is present (UHttpClient.cs:753-754). DispatchViaProxyAsync only checks Address != null (852-857), then computes proxyPort = proxy.Address.IsDefaultPort ? 80 : proxy.Address.Port (861-863) and always leases with secure: false (1218-1223). For https://proxy.example the default port is 443, so IsDefaultPort is true and the transport connects to proxy.example:80 in cleartext; for https://proxy.example:8443 it speaks cleartext HTTP to a TLS port; socks5:// is treated as an HTTP proxy. A ProxySettings with Address null fails with 'Proxy address is required' instead of meaning 'no proxy'. No test calls WithProxy.
- **Failure scenario.** request.WithProxy(new ProxySettings { Address = new Uri("https://secure-proxy.corp"), Credentials = ..., AllowPlaintextProxyAuth = true }): the caller believes the proxy leg is TLS; the CONNECT line with the target host and, after a Basic challenge, Proxy-Authorization are sent unencrypted to secure-proxy.corp:80 (on desktop, where AllowCleartext defaults to true).
- **Fix direction.** Validate at the transport boundary: reject a proxy whose scheme is not http with InvalidRequest (the message must not echo the URI), treat Address == null as no proxy, and use Address.Port directly. Calling Validate() in WithProxy as well gives the caller the error at the call site.
- **Verifier.** Traced. ProxySettings.Validate (ProxySettings.cs:47-65) is called only by ProxyEnvironmentResolver.Resolve (:232). WithProxy stores proxySettings?.Clone() unvalidated (ProxyRequestBuilderExtensions.cs:7-15) and UHttpClient skips Resolve when the key exists (UHttpClient.cs:753-754). DispatchViaProxyAsync checks only Address != null (:852-857), uses IsDefaultPort ? 80 : Port (:861-863), so https://proxy.example becomes proxy.example:80, and always leases secure:false (:1218-1223). A ProxySettings with Address null fails with 'Proxy address is required' (transport treats proxy != null as proxied, :565). No test calls WithProxy (rg over Tests, Samples~, Documentation~: none). Limits on impact: the cleartext policy still applies to the proxy host (:495-501), so a mobile default rejects it; Proxy-Authorization goes out only after a Basic 407 and only with AllowPlaintextProxyAuth = true, so the credential exposure needs that opt-in plus something answering 407 on the cleartext port (an on-path attacker can). In most cases the result is a confusing connect failure, not a leak.

### net-protocol-05: Happy Eyeballs does not start the next address when every in-flight attempt has already failed; it sleeps until the scheduled stagger time

**medium** · protocol-impl · verdict **C** · `Runtime/Transport/Connection/HappyEyeballsConnector.cs:150` · RFC 8305 Section 5 · also reported as net-runtime-06

- **Evidence.** RaceAsync starts an attempt only when schedule[scheduleIndex].Due <= started.Elapsed (140-148). When the only active attempt completes with a failure, activeTasks is empty and the loop computes wait = schedule[scheduleIndex].Due - started.Elapsed and awaits Task.Delay(wait) (150-159). BuildSchedule puts the first alternate-family address at FamilyStaggerDelay = 250 ms and later ones 125 ms apart (322-359, HappyEyeballsOptions.cs:10-11). TcpConnectionPool.ResolveDnsAsync returns [::1, 127.0.0.1] for every localhost name (TcpConnectionPool.cs:719-720, LocalhostNames.cs:48-53) and PreferIpv6 is true by default, so ::1 is tried first. PromoteIdleFamily (240-257) only reorders when a slot frees while another attempt is still in flight; it does not cover the empty case. The sequential path (361-382) does move on immediately. No test covers 'first attempt fails fast, next starts at once' (HappyEyeballsInterleaveTests covers only the saturated-slot case).
- **Failure scenario.** http://localhost:8080 with a dev server bound to 127.0.0.1 only: connect to ::1 is refused in under a millisecond, then the connector idles until t=250 ms before dialling 127.0.0.1. Every new connection (and every stale-connection retry) pays 250 ms. The same happens on an IPv4-only network when the resolver returns AAAA records and the IPv6 connect fails at once with ENETUNREACH, and 125 ms per additional dead address after that.
- **Fix direction.** When activeTasks becomes empty and addresses remain, start the next scheduled attempt immediately (treat a failure as the end of that attempt's delay, as RFC 6555 and every mainstream implementation do), keeping the 10 ms floor between starts. Add a test with a refusing first family and a virtual clock.
- **Verifier.** Traced. RaceAsync starts an attempt only when Due <= elapsed (HappyEyeballsConnector.cs:140-148). After the only in-flight attempt fails, activeTasks is empty and the loop awaits Task.Delay(Due - elapsed) (:150-159). BuildSchedule puts the first alternate at FamilyStaggerDelay 250 ms and later attempts 125 ms apart (:322-359; defaults HappyEyeballsOptions.cs:10-13). PromoteIdleFamily (:240-257) only reorders, it never advances a due time. TcpConnectionPool.ResolveDnsAsync returns [::1, 127.0.0.1] for localhost names (TcpConnectionPool.cs:719-720, LocalhostNames.cs:48-53) and PreferIpv6 is true, so a server bound to 127.0.0.1 costs 250 ms per new connection. The sequential path (:361-382) moves on at once. No test asserts the start time after a fast failure (HappyEyeballsInterleaveTests checks order; HappyEyeballsSameFamilyTests has a 5 s bound). The IPv4-only-network case depends on whether the resolver returns AAAA there; the localhost case is deterministic.

### net-protocol-06: MaxConcurrentAttempts (default 2) stops the Happy Eyeballs race after two blackholed addresses; remaining addresses are never tried before the connect deadline

**medium** · rfc-compat · verdict **C** · `Runtime/Transport/Connection/HappyEyeballsConnector.cs:140` · RFC 8305 Section 5

- **Evidence.** A scheduled attempt starts only while activeTasks.Count < options.MaxConcurrentAttempts (140-142). With the cap reached the loop takes the else branch and awaits Task.WhenAny(activeTasks) with no timer (179-182), so nothing happens until an in-flight connect ends. A blackholed SYN ends only at the OS SYN timeout or the pool connect deadline (10 s, ConnectionPoolOptions.DefaultConnectTimeout), at which point ConnectAsync throws TimeoutException (98-104). RFC 8305 Section 5 keeps starting attempts every Connection Attempt Delay with no in-flight cap. The PromoteIdleFamily comment (230-239) acknowledges the cap's interaction but only fixes the case where one attempt fails fast.
- **Failure scenario.** Client on a network with broken IPv6 (SYNs dropped) resolves a host to one AAAA and two A records where the first A is a dead server (round-robin DNS with one node down). Schedule: v6a at 0, v4a at 250 ms, v4b at 375 ms. v6a and v4a both hang, the cap is reached, v4b (healthy) is never dialled, and the request fails with 'TCP connect timed out after 10000ms'. Every retry repeats it because no address state is remembered.
- **Fix direction.** Do not let the cap block progress: when the cap is reached and the next address is due, cancel the oldest in-flight attempt (or raise the default cap to cover the address list within the connect deadline). Add a test with two blackholed and one healthy address under default options.
- **Verifier.** Traced. With activeTasks.Count == MaxConcurrentAttempts (default 2, HappyEyeballsOptions.cs:12) the start loop (:140-142) does nothing and the else branch awaits Task.WhenAny(activeTasks) with no timer (:179-182). For one AAAA plus two A records the schedule is v6a 0 ms, v4a 250 ms, v4b 375 ms (:336-358). Two blackholed attempts end only at the connect deadline (10 s, ConnectionPoolOptions.cs:54), then ct.ThrowIfCancellationRequested (:138) leads to the TimeoutException (:98-104) and UHttpException Timeout (TcpConnectionPool.cs:788-789); v4b is never dialled. PromoteIdleFamily's comment (:230-239) acknowledges that RFC 8305 Section 5 has no cap and only covers a slot freed by a fast failure. HappyEyeballsTests.LargeDnsSet_BoundedConcurrency shows the cap is deliberate, but no test covers two blackholed plus one healthy address. Needs two dead addresses ahead of a healthy one, so it is an edge case, but the request then fails outright with a reachable address unused.

### net-protocol-07: Proxy paths lack the direct path's stale-connection hardening: no first-byte watchdog, and the one retry takes the next idle connection instead of a new socket

**medium** · protocol-impl · verdict **C** · `Runtime/Transport/RawSocketTransport.cs:1121` · RFC 9112 Section 9.3.1 · also reported as net-runtime-11

- **Evidence.** The direct path arms GetReusedConnectionFirstByteTimeout (659) and retries on _pool.GetNewConnectionAsync (683) with the comment 'A newly connected socket, not the next idle one: a NAT drop kills every idle connection to the host at once (#47)'. ### net-runtime-03: Token cancellation in the SAEA and PollSelect channels closes the socket directly, bypassing the shutdown-first order Dispose uses against the IL2CPP stale-selector-job hazard

**medium** · platform-compat · verdict **P** · `Runtime/Transport/Tcp/SaeaSocketChannel.cs:170` · tracked by #384

- **Evidence.** SaeaSocketChannel.Dispose shuts down, drains and only then closes on selector platforms, with the stated reason 'IL2CPP's close does not remove a pending job from its selector, so closing first would let a new socket reuse the number behind the stale job (#384)' (:326-341). But each operation registers its own cancellation callback that calls Socket.Dispose() directly (ReceiveAsync :170-173, SendAsync :241-244; PollSelectSocketChannel.cs:171 and :231 do the same). That callback is registered per read, i.e. after RawSocketTransport.RegisterDisposeOnCancel (RawSocketTransport.cs:1776, :319-324, which does Shutdown then Dispose), and CancellationTokenSource runs callbacks last-registered-first, so on a request timeout the channel's close-first callback normally runs before the shutdown-first one. In the body phase, the TLS handshake and the HTTP/2 read loop there is no RegisterDisposeOnCancel at all, so close-first is the only path. Afterwards the channel is still not disposed and _recvActive stays 1 if the completion is never posted, so the later Dispose spins 2 x 500 ms (:337-340) and abandons the buffers. #384's open remainder for SAEA mentions only the 500 ms fallback inside Dispose, not this path.
- **Failure scenario.** SocketIoMode.Saea on an iOS/Android IL2CPP player: a request times out while its header or body read is pending. The channel's registration closes the descriptor under the pending receive job; the retry (or any new connection) gets the same descriptor number, queues its receive behind the stale job and loses it, which is the #364/#384 symptom the hold was built to remove; the thread that later disposes the channel blocks up to 1 s. Confirm with the Loop384 scenario run in SAEA mode on the iOS simulator or a device.
- **Fix direction.** Route cancellation through the same sequence as Dispose: the registration should only Shutdown(Both) the socket (which ends the pending operation with the descriptor still open) and leave the close to the channel's Dispose, or call a non-blocking 'begin dispose' that defers the close until the in-flight flags clear.
- **Verifier.** Code as described for SAEA: the per-operation registration calls Socket.Dispose() directly (SaeaSocketChannel.cs:170-173, :241-244), while Dispose uses shutdown, drain, close on selector platforms for the stated #384 reason (:326-341). The transport passes the request token into the stream read (Http11ResponseParser.cs:1379), so the registration is live in the head phase; in the body phase, the TLS handshake and the HTTP/2 read loop no RegisterDisposeOnCancel exists at all. Head-phase order is not guaranteed either way (CancellationTokenSource runs callbacks last-registered-first only within one registration list), and when RegisterDisposeOnCancel (:319-324) runs first the channel's own Dispose does shutdown-first, so the close-first outcome there is timing dependent. The first-byte watchdog path is fine: RegisterDisposeOnCancel is registered on watchdog.Token after the linked source (:1987-1992), so it runs before the linked token reaches the channel. Whether close-first leaves a stale selector job and loses a later receive is IL2CPP device behaviour (needs-device-validation). #384 is open and covers 'no socket is created on a descriptor whose abandoned read has not ended'; its recorded SAEA remainder names only the 500 ms fallback inside Dispose, so this token path is an unlisted instance. The PollSelect half of the title does not hold for the selector hazard: PollSelect runs synchronous calls on its own thread and puts no job in the runtime selector (PR #405 notes), though its registration (PollSelectSocketChannel.cs:171, :231) does close the descriptor under the poll thread.

### net-runtime-08: The idle pool is a FIFO queue: the connection that has been idle longest is reused first

**medium** · performance · verdict **C** · `Runtime/Transport/Tcp/TcpConnectionPool.cs:508`

- **Evidence.** _idleConnections maps a key to a ConcurrentQueue<PooledConnection> (:301-302); returns Enqueue at the tail (:595) and acquisition TryDequeues from the head (:508), so every acquire takes the least recently used connection. Two effects: (1) each connection idles N times longer between uses (N = idle connections), which is exactly what lets NAT bindings and server keep-alive timers expire; PooledConnection.IsAlive cannot see a silent NAT drop (the class comment says so, :74-77), so the stalest candidate is also the likeliest dead one; (2) a steady trickle of requests round-robins all N connections and keeps each one's LastUsed fresh, so the pool never shrinks to what the load needs. The scavenger re-enqueues survivors in the same order (:885-888).
- **Failure scenario.** Mobile client: a burst opens 6 connections, then one idempotent request every 10 s behind a carrier NAT that drops bindings after 30 s of silence. FIFO hands out connections idle for 10, 20, 30, 40 s: the third and fourth requests land on silently dead sockets and each waits the 10 s ReusedConnectionFirstByteTimeout before its retry (a POST fails or waits for the request timeout). With most-recently-used reuse the same traffic always reuses a connection idle for 10 s and the other five expire unused.
- **Fix direction.** Reuse most-recently-returned first (a per-key stack, or a deque that takes from the hot end) and let the scavenger evict from the cold end.
- **Verifier.** Traced. _idleConnections is ConcurrentDictionary<string, ConcurrentQueue<PooledConnection>> (TcpConnectionPool.cs:301-302); EnqueueConnection appends at the tail (:594-595) and AcquireConnectionWithOwnedPermit takes from the head (:508), so the connection idle longest is always reused first; the scavenger re-enqueues survivors in order (:882-888). Nothing reorders by LastUsed, and no test asserts an order (rg fifo/lifo/oldest over Tests/Runtime/Transport finds nothing). Scenario holds with the defaults: mobile idle timeout 45 s (PlatformConfig.cs:60-63), so after a 6-connection burst and one request per 10 s the pool hands out sockets idle 10/20/30/40 s; IsAlive cannot see a silent NAT drop (:73-77) and the only recovery is the 10 s first-byte watchdog, armed for idempotent replayable requests only (RawSocketTransport.cs:344-354). Each reuse also refreshes LastUsed (:522, :590), so a trickle keeps about idleTimeout/period connections alive instead of one. No open issue tracks it (#364 is the retry's lease choice, not the idle order).
