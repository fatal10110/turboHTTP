# 2026-11 proxy-407: one 407 reuse rule, fresh-connection CONNECT retry, challenge-driven forward-proxy auth (#229, #236)

## What
- **One reuse predicate for a 407 CONNECT reply** (#229): `ConnectReply.CanRetryOnSameConnection`
  in `Runtime/Transport/Http1/ConnectReplyReader.cs`. Another CONNECT may follow on the same
  connection only with Content-Length, no Transfer-Encoding, no `Connection: close`, and for an
  HTTP/1.0 status line an explicit `keep-alive` (RFC 9112 sections 6.3 rules 3 and 8, 9.3, 9.6).
  - `ConnectReply.IsHttp10` is new; the reader sets it from the status line.
  - The WebSocket `ProxyTunnelConnector` drops its private copy of the rule and uses the shared
    property. It still fails with `ProxyTunnelFailed` on a non-reusable 407 (it owns one stream and
    cannot reconnect). Its only behavior change: an HTTP/1.0 407 without `keep-alive` is now refused
    too, where the old rule would have retried on a connection the proxy closes.
- **CONNECT retry on a fresh connection** (#229): `RawSocketTransport.EstablishConnectTunnelAsync`
  takes `includeAuth` and returns `null` when a Basic 407 it would answer is not reusable.
  `AcquirePreparedProxyLeaseAsync` loops: it disposes that lease (releasing its pool permit),
  checks the token, takes a new connection from the same pool key and sends the authenticated
  CONNECT there. The new connection gets its own `RegisterDisposeOnCancel` registration. A second
  407 on the fresh connection fails as before ("credentials ... rejected"); there is no third try.
  - Before: the H1 path drained and reused any Basic 407. `Connection: close` led to
    "Proxy closed the connection before sending a CONNECT response" with credentials never sent;
    a close-delimited body was read as the next status line; TE+CL was drained as chunked and reused.
  - `TransportProxyConnectTunnelEstablished` is now recorded after the tunnel is up (it was
    recorded before the CONNECT); `TransportProxyConnectAuthReconnect` marks the fresh-connection retry.
- **Forward-proxy (`http://` target) auth is challenge-driven** (#236):
  - `PrepareHttpProxyForwardRequest(request, proxy, includeCredentials)` always strips a
    caller-supplied Proxy-Authorization; only the `includeCredentials: true` clone carries Basic.
  - `DispatchViaProxyAsync` sends the first attempt without credentials. When credentials are set,
    `AllowPlaintextProxyAuth` is on and the body is not `NonReplayable`, `DispatchOnLeaseAsync`
    intercepts a 407 whose `Proxy-Authenticate` offers Basic before it reaches the handler.
  - The 407 body is drained (keep-alive, empty or Content-Length up to 64 KiB, under
    dispose-on-cancel) and the lease pooled; anything else (close, chunked, close-delimited,
    larger, read failure, Expect-continue early final response, which sets KeepAlive false) closes
    the connection. `DispatchProxyHttp11WithRetryAsync` then returns `false` and the caller sends
    the Basic clone once through the same method (stale-connection retry included). A second 407,
    a non-Basic 407, or a 407 with a non-replayable body reaches the caller unchanged.

## Decisions
- #229: reconnect instead of failing. The issue offers both; reconnecting is what a client does
  after RFC 9112 section 9.6 `close` and is what the acceptance criteria ask for. The H1 path now
  also refuses a chunked-only 407 for reuse (the shared WS rule) and reconnects instead: it costs a
  connection, never correctness.
- HTTP/1.0 persistence (RFC 9112 section 9.3) was added to the shared rule: the same defect class
  as `Connection: close`.
- #236: no opt-in preemptive mode (the issue marks it optional). Every authenticated forward
  request pays one 407 round trip, the price of not sending cleartext credentials unasked.
- #236: a `NonReplayable` body is never retried, even when no body byte was sent (Expect-continue
  early 407): conservative, and what the acceptance criteria state.
- The forward 407 drain is local (`TryDrainProxyChallengeBodyAsync`) rather than an
  `Http11ResponseBodySource`: the body source pools the lease from inside its own drain, after the
  dispose-on-cancel registration could no longer be removed first.
