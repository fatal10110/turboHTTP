# 2026-11 TLS interop job and negative TLS suite (#113, #230)

## What

- **#230**: a non-Unity .NET 8 job, `Tools~/tls-interop/`, links the shadow-built DLLs
  (`TurboHTTP.Core`, `Transport`, `Transport.BouncyCastle`, `SecureProtocol`) and runs the production
  providers against OpenSSL 3 `s_server` on loopback. Two rows pin one AES-256-GCM suite per version
  and go through `BouncyCastleTlsProvider.WrapAsync`, so the bytes flow through the production
  non-blocking `BouncyCastleTlsStream`:
  - TLS 1.2 with `-cipher ECDHE-RSA-AES256-GCM-SHA384` reports `TlsResult.CipherSuite == "0xC030"`.
  - TLS 1.3 with `-ciphersuites TLS_AES_256_GCM_SHA384` reports `"0x1302"`.

  Each row then sends `GET / HTTP/1.1`, reads the `s_server -www` page (HTTP 200) and checks that the
  page names the same suite, so the server agrees on it too. A new `tls-interop` job in `ci.yml` runs
  `Tools~/tls-interop/run.sh`, and the aggregate `ci` check needs it. A missing openssl or a missing
  BouncyCastle provider fails the job. Nothing in it skips.
- **#113**: the same job runs the negative certificate suite for `SslStream`, `BouncyCastle` and
  `Auto` through `RawSocketTransport`, and asserts `UHttpErrorType.CertificateError`. The cases are:
  - self-signed and untrusted root;
  - expired and not yet valid;
  - wrong host, and a CN-only identity when a SAN is present;
  - an IP host whose certificate has only a dNSName `127.0.0.1`;
  - a missing intermediate;
  - a TLS 1.1 server (`-tls1_1 -cipher DEFAULT:@SECLEVEL=0`);
  - `*.com` for `example.com`, run at provider level and expecting `AuthenticationException`.

  Positive controls for each provider (valid leaf at localhost and 127.0.0.1, intermediate sent)
  show that each rejection comes from its own defect. A control row proves the TLS 1.1 server
  really negotiates TLSv1.1 with `openssl s_client`. The per-run PKI is created with
  `CertificateRequest`. Its root is trusted only through `SSL_CERT_FILE`, with `SSL_CERT_DIR`
  pointing at an empty directory, so the production `X509Chain` / `SslStream` validation runs
  unchanged and nothing internal is opened to the harness.
- **#113, Unity side**: `Tests/Runtime/Transport/Tls/TlsNegativeSuiteTests.cs`. It covers the same
  identities, each crossed with SslStream, BouncyCastle and Auto, through `RawSocketTransport` against
  the loopback SslStream server. It adds:
  - a `*.com` case at provider level;
  - a scripted TLS 1.1 server flight;
  - Auto never falling back to BouncyCastle: one connection, `IsSslStreamKnownBroken` false;
  - a BouncyCastle positive control.

  The material is committed in `NegativeSuiteTestCertificates.cs` and generated by
  `Tools~/test-certs/gen_negative_suite_certs.py`. It holds a root DER, an intermediate DER and 10
  PKCS#12 leaves with SHA1/3DES PBE so Mono can read them. Unity Mono cannot create certificates.
- **Defect found and fixed**: on .NET 8 Linux, platform `SslStream` accepted a certificate whose only
  identity was the dNSName `127.0.0.1` for host `127.0.0.1`. RFC 6125 1.7.2 and RFC 5280 4.2.1.6
  match an IP reference identity only against an iPAddress SAN. `SslStreamTlsProvider.WrapAsync` now
  calls `SubjectAltNameIpAddresses.EnsureIpLiteralIdentity` after the TLS 1.2 floor check. The
  new class is internal and parses only the SAN's iPAddress entries; malformed input yields no entries,
  so the check fails closed. The check only ever rejects more, and BouncyCastle already behaved this
  way (`TlsCertificateNameMatcher`). The tests are `SslStreamIpIdentityTests` and the
  `sslstream|auto/reject/ip-host-without-ip-san` rows. Those rows failed (`accepted: HTTP 200`)
  before the fix.

## Decisions

- **"Runs in CI" for #113.** The dotnet job covers every case for all three providers in PR CI. The
  Unity suite runs in the periodic host-editor run, because PR CI runs no Unity tests (#188).
- **The harness does not use `UHttpClient`.** In the editor shadow build,
  `UHttpClient.TryAppendEditorMonitorInterceptor` calls `UnityEngine.Application.isPlaying`, and
  outside Unity that fails at JIT with "ECall methods must be packaged into a system module". The
  harness therefore dispatches through `RawSocketTransport`. That layer is where
  `AuthenticationException` becomes `CertificateError`.
- **Unity SslStream and Auto cannot trust a test root**, so their Unity cases reject at least as
  "untrusted". The per-defect SslStream evidence, with the root trusted, comes from the dotnet job.
  - Unity's SslStream continues a TLS 1.1 handshake as far as the certificate, so its scripted
    TLS 1.1 case is rejected by certificate or version; the provider's floor
    (`EnsureMinimumTlsVersion`) stands behind it.
  - BouncyCastle aborts at the ServerHello with protocol_version.
- **No production accept-all hook** (CLAUDE.md 3). The mutation check is a manual edit, described in
  the test-class header.
