# Parser fuzzing (#112)

Fuzz targets for the parsers that read peer-controlled bytes. The harness is a plain .NET 8 console
app (`TurboHTTP.Fuzz`) that links the shadow-built netstandard2.1 DLLs, like `Tools~/autobahn`. Unity
does not import this folder.

| Target | Code under test | Input | Accepted failures |
| --- | --- | --- | --- |
| `h1-response` | `Http11ResponseParser.ParseAsync`: status line, fields, obs-fold, 1xx, framing, buffered chunked body and trailers (RFC 9112) | raw response to a GET | `IOException`, `FormatException`, `NotSupportedException`, alone or wrapped in `UHttpException` |
| `h1-chunked-body` | `Http11ResponseBodySource`: the streaming chunked decoder and trailers | `[read size][chunked body]` | same as above |
| `hpack` | `HpackDecoder` + Huffman + integer codec + dynamic table (RFC 7541) | `[u16 len][block]...` on one decoder | `HpackDecodingException` |
| `h2-frames` | `Http2FrameCodec.ReadFrameLeaseAsync`, `Http2Settings.ParsePayload`/`Apply` (RFC 9113 4.1, 4.2, 6.5) | server frame stream | `IOException` (EOF), `Http2ProtocolException` |
| `h2-connection` | the whole `Http2Connection` read loop with a GET open on stream 1: HEADERS/CONTINUATION padding and priority, DATA padding, flow control, SETTINGS, PING, GOAWAY, RST_STREAM, PUSH_PROMISE | server frames after the preface | a dispatch or body failure whose root cause is `Http2ProtocolException`, `HpackDecodingException`, `IOException` or `UHttpException`; no completion within 10 s after EOF is a hang |
| `ws-frames` | `WebSocketFrameReader` + `MessageAssembler` + permessage-deflate for RSV1 messages (RFC 6455 5.2-5.5, RFC 7692) | server frame stream | `WebSocketException`, `WebSocketProtocolException`, `IOException` |
| `ws-inflate` | `PerMessageDeflateExtension.TransformInbound` (RFC 7692 7.2.2, bounded output) | `[u16 len][compressed message]...` | `WebSocketException` |
| `json` | `JsonReader` (RFC 8259, depth cap 64) | UTF-8 text | `JsonParseException` |

Any other exception, a frame or message past its configured bound, more output than input where the
format forbids it, a hang or a memory blow-up is a finding.

## Running

```bash
'Tools~/fuzz/run.sh'                                        # replay the committed corpus, every target
'Tools~/fuzz/run.sh' --driver mutate --execs 1000000        # seeded mutation loop
'Tools~/fuzz/run.sh' --driver libfuzzer --runs 1000000 --time 3600 --target hpack
```

Common options: `--target <name>` (repeatable, default all), `--seed N`, `--max-len N` (default 4096),
`--no-shadow-build`. Exit 3 means a tool is missing; exit 1 means a finding, with the input saved
under `.build/fuzz/artifacts/<target>/`.

- **replay** runs every corpus file once. It needs only dotnet and the Unity managed DLLs the shadow
  build uses (`Tools~/ci/fetch-unity-dlls.sh`).
- **mutate** is a fixed-seed mutation loop (bit flips, interesting values, protocol tokens, splices)
  with a watchdog for hangs (30 s per input) and memory (2 GB working set). It has **no coverage
  guidance**: use it where libFuzzer is not available, and do not report its runs as coverage-guided.
- **libfuzzer** is coverage guided. `run.sh` builds with `-p:FuzzDriver=libfuzzer` (adds the SharpFuzz
  package), instruments the TurboHTTP DLL copies in `.build/fuzz/bin` with `sharpfuzz` (never
  `.build/shadow`, which the Autobahn and TLS interop jobs share) and starts `libfuzzer-dotnet` with
  `-timeout=30 -rss_limit_mb=2560`. It needs `sharpfuzz` (`dotnet tool install --global
  SharpFuzz.CommandLine --version 2.3.0`) and `libfuzzer-dotnet` (built with clang from
  [Metalnem/libfuzzer-dotnet](https://github.com/Metalnem/libfuzzer-dotnet); set `LIBFUZZER_DOTNET`
  to its path). New inputs go to `.build/fuzz/work/<target>`; the committed corpus is read only.
  libFuzzer runs the corpus itself first, so this driver skips the separate replay: instrumented DLLs
  only run under `libfuzzer-dotnet` (outside it they fail with `AccessViolationException`).

`.github/workflows/fuzz.yml` runs the libfuzzer driver, one job per target: on pull requests that
touch a parser, up to 1M executions or 10 minutes per target; weekly and on manual dispatch, the
dispatch budget (default 1M executions, 1 hour per target).

## Corpus

`corpus/<target>/seed-*` is generated by `dotnet .build/fuzz/bin/Release/net8.0/TurboHTTP.Fuzz.dll
seeds 'Tools~/fuzz/corpus'` from `Seeds.cs`: the inputs the parser tests use plus the RFC 7541
Appendix C and RFC 7692 Section 7.2.3 examples. `.gitattributes` keeps the files byte-exact. Add a
minimized crash input as `corpus/<target>/regression-<issue>` once its fix lands, so every run
replays it.

## Findings

1. Reproduce on an uninstrumented build (`'Tools~/fuzz/run.sh' --target <target>` rebuilds one):
   `dotnet .build/fuzz/bin/Release/net8.0/TurboHTTP.Fuzz.dll replay <target> <input>`.
2. Dedupe with `Tools~/agent-tools/issue_search.py` and file one issue per distinct defect with the
   issue template (protocol or security crashes go to milestone v1.0-beta). Attach the input as hex.
3. The fix adds a regression test under `Tests/Runtime/<area>/` (the `*FuzzRegressionTests` files
   take an inline input) and the input to the corpus.

The Unity Test Runner side is `Tests/Runtime/{Transport/ParserFuzzRegressionTests,
WebSocket/WebSocketFuzzRegressionTests, JSON/JsonFuzzRegressionTests}.cs`: the same mutator
(`Tests/Runtime/SeededMutator.cs`) with a fixed seed over inline seeds, a few thousand inputs per
target, so the Unity runtime checks the same oracles the harness does.
